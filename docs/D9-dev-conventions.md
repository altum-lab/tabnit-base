#### A-06 관계 지도용 조회 (노드와 간선, 시점 지정)

- 모듈: core
- 수용 기준: 관계 지도 화면이 쓰는 형식으로 돌려준다
- 선행 작업: A-04
- 진행 (2026-11-22): 보드의 카드를 그대로 옮기고 만들었다 (D2 AD-352). core 의 `RelationMapQuery.relationMap(가운데 개체, 기준 날짜, 깊이, 노드의 한도)` 와 `GET /api/v1/relation-map` (D7 4절 "관계 지도", 규격의 `getRelationMap`). 수용 기준의 확인은 core 의 `RelationMapQueryTest` 와 api 의 `RelationMapApiTests` 다. 화면은 없다 (D-08). 남은 것: 구현하면서 정한 것이 D7 "결정 필요" 18번에 있다. 답의 크기는 막히지만 하는 일의 양은 막히지 않는다 (자르기 전의 수를 세려고 깊이 안의 이웃을 끝까지 읽는다): A-07 의 가운데 크기의 자료에서 깊이 1, 2, 3 이 13 ms, 89 ms, 414 ms 였고 큰 자료에서는 재지 않았다. 실행 계획은 확인하지 못했다. 예시 Pack 의 자료로는 확인하지 않았다 (검증 질문에 관계 지도를 묻는 유형이 없다).
- 진행 (2026-11-23, 색인): 관계 테이블에 도착 개체로 찾는 색인을 더했다 (D2 AD-356, 스키마 변경 파일 V18, D5 3절). 자르기 전의 수의 뜻은 그대로 두었다. 같은 자료와 같은 PC 에서 색인이 없을 때와 있을 때를 쟀다 (`bash verify/large.sh ... measure`, 가운데 값).

| | 관계 48만, 색인 없음 | 색인 있음 | 관계 200만, 색인 없음 | 색인 있음 |
|---|---|---|---|---|
| 관계 지도 깊이 1 | 34 ms | 28 ms | 25 ms | 30 ~ 42 ms |
| 관계 지도 깊이 2 | 217 ms | 152 ms | 378 ms | 327 ~ 364 ms |
| 관계 지도 깊이 3 | 3.5 초 | 1.05 초 | 17.1 초 | 4.8 ~ 5.6 초 |
| 영향 범위 계산 | 177 ms (3,660개) | 137 ms | 0.47 초 (10,100개) | 0.47 ~ 0.50 초 |
| 관계 파일 하나 올리기 | 24만 행 128 ~ 130 초 | 129 ~ 131 초 | 100만 행 603 ~ 623 초 | 544 ~ 589 초 |
| 관계 테이블의 크기 | 363 MB | 368 MB | 1,500 MB | 1,520 MB |

  - 관계 200만의 "색인 없음"은 전날의 실행 한 번이고, "색인 있음"은 두 번 돌린 범위다. 관계 48만은 한 번씩이다. 올리는 시간이 실행마다 10% 쯤 흔들린다: 깊이 1 의 차이와 영향 범위 계산의 차이(177 → 137 ms)는 그 흔들림 안이다.
  - 색인이 없을 때는 도착 쪽을 겹침 거부의 색인(출발 개체로 시작한다)으로 읽고 있었다. 색인을 더한 뒤 큰 자료에서 이웃을 찾는 질의의 평균이 2.0초에서 0.06초가 됐다.
  - 실행 계획의 요약 (큰 자료, 색인이 있는 둘째 실행, 0.05초를 넘긴 151건. 기록은 저장소에 올리지 않는다): 새 색인이 쓰인 28건은 모두 관계 지도의 이웃 찾기다 (깊이 3 의 30건 가운데 2건은 테이블을 통째로 읽었다. 0.5초). **영향 범위 계산의 단계 질의는 색인을 더한 뒤에도 도착 쪽을 겹침 거부의 색인으로 읽는다.** 시점 조회는 0.05초를 넘긴 적이 없어 기록에 없다: 새 색인을 쓰는지 모른다. 관계 지도의 간선 읽기는 겹침 거부의 색인으로 읽고 평균 105 ms 다: 깊이 1 과 2 에서는 이것이 저장소 시간의 큰 몫이다 (고치지 않았다).
  - **큰 자료의 깊이 3 에 남은 5초는 저장소가 아니라 제품이 쓰는 시간이다**: 자르기 전의 수를 세려고 관계 100만 행의 두 끝을 받아 정리한다. 색인으로는 더 줄지 않는다. 줄이려면 그 수의 뜻을 바꿔야 한다 (대표가 그대로 두기로 했다. AD-356).
  - 올리는 시간과 저장소의 크기는 색인으로 눈에 띄게 달라지지 않았다. 크기가 20 MB 만 는 것은 이 자료에서 도착 개체 하나에 관계가 100개씩 몰려 색인이 같은 값을 묶어 담기 때문이다. 도착 개체가 흩어진 자료에서는 더 크다.
  - 큰 자료에서 개체 하나의 관계 조회(가운데 층의 개체, 첫 쪽)가 18 ms 에서 134 ~ 150 ms 가 됐다. 저장소의 질의 시간은 아니다 (확인): 저장소의 통계에서 그 질의와 수를 세는 질의는 평균 3.5 ms 아래이고 0.05초를 넘긴 적이 없다. **까닭은 모른다.** 재는 차례에서 이 조회는 관계 지도 깊이 3 의 바로 다음인데, 색인이 없을 때도 차례는 같았고 그때의 가운데 값은 17.7 ms 였다 (가장 큰 값은 145 ms). 깊이 3 이 빨라지며 그 요청의 메모리 정리가 다음 요청과 겹치게 됐을 수 있으나 확인하지 못했다. 화면은 노드를 누르면 지도와 관계 목록을 함께 받으므로 실제 쓰임에서도 나올 수 있다. 관계 48만의 자료에서는 41 ms 에서 27 ms 로 줄었다.
  - 영향 범위 계산의 마지막 읽기(마지막 층의 개체 10,000개)에서 저장소가 가끔 관계 테이블을 식별자 순으로 통째로 훑는 계획을 골랐다 (나가는 관계를 100만 행 넘게 어림해서다. 실제로는 0행): 0.05초를 넘긴 71번 가운데 4번이고 한 번에 0.4초쯤이다. 나머지 67번은 0.05 ~ 0.09초였다. 이 계획은 걸리는 시간이 영향 대상의 수가 아니라 테이블의 크기에 비례한다. 읽는 차례를 식별자 순으로 정해 둔 것이 이 계획을 고르게 하는데, 그 차례는 방향을 모르는 유형을 알릴 때 어느 관계를 가리키는지를 정하므로 그대로 둔다. 계산의 0.47초 가운데 나머지가 어디서 쓰이는지는 나눠 재지 않았다. 목표 안이라 두었다.
  - 재는 실행이 실행 계획을 남기는 기준을 0.2초에서 0.05초로 낮추고, 시간을 많이 쓴 질의를 25개까지 적게 했다.
- 진행 (2026-11-23, 한도를 넘은 단계에서 멈춤): 찾은 노드가 한도를 넘은 단계에서 더 깊이 따라가지 않게 했다 (D2 AD-357). 담기는 노드와 간선은 그대로다. 응답에 따라간 깊이 `reachedDepth` 를 더했고 `totalNodes` 는 따라간 데까지 찾은 수가 됐다. 화면은 어느 깊이에서 멈췄는지를 알린다. 앞의 시험 가운데 수의 뜻에 기댄 곳(한도를 넘은 뒤 더 깊은 곳까지 센 값)을 새 뜻에 맞게 고쳤다. 앞의 기록에 남긴 "답의 크기는 막히지만 하는 일의 양은 막히지 않는다"는 이만큼 줄었다: 한도를 넘은 단계까지만 읽는다. 그 단계는 끝까지 읽으므로 (개체 200개 이하에 닿은 관계 모두), 관계가 아주 많이 몰린 개체가 그 안에 있으면 여전히 그만큼 읽는다.

#### D-14 관계 지도를 3D 로도 그린다

- 모듈: web
- 수용 기준: 관계 지도를 2D 와 3D 로 바꿔 볼 수 있다. 3D 에서도 같은 노드와 간선이 그려지고, 노드를 눌러 가운데를 옮기며, 시점 막대와 깊이를 바꾸면 다시 그려진다 (2026-11-23 에 정했다. D2 AD-361)
- 선행 작업: D-08
- 적어 둔 것 (2026-11-23, D2 AD-360): 보드에 없는 카드다. 범위(필수, 당김, 1월)는 대표가 보드에서 정한다. 전체 꾸러미 `react-force-graph` 를 들이기로 했다 (3D, AR, VR 용 라이브러리가 함께 온다: 25MB 쯤). 시작할 때 정할 것: 2D 꾸러미를 그대로 둘지, 처음에 무엇을 보일지, 딸려 오는 것의 라이선스와 화면의 묶음의 크기, 3D 그림을 화면 시험으로 어떻게 확인할지.
- 진행 (2026-11-23): 만들었다 (D2 AD-361). 3D 만 담은 꾸러미 `react-force-graph-3d` 를 2D 꾸러미 옆에 더했다 (전체 꾸러미는 들이지 않았다). 지도 위의 고르기로 2D 와 3D 를 바꾼다. 처음은 2D 이고, 3D 의 코드는 3D 를 고를 때만 내려받는다 (따로 떨어진 묶음 1,383 kB, 줄인 뒤 360 kB. 처음 내려받는 묶음은 507 kB 에서 511 kB). 3D 그림은 2D 와 같은 답을 그린다: 가운데 개체는 붉은 점, 이름표, 화살표, 같은 두 개체 사이의 여러 관계는 휘어서. 끌어서 돌리고 굴려서 확대한다. 수용 기준의 확인은 화면 시험 `web/tests/relation-map.spec.ts` 의 3D 묶음이다. 남은 것: 3D 그림도 캔버스라 화면 시험이 그 안을 읽지 못한다: 시험은 고르기, 같은 노드 목록, 그림이 비어 있지 않고 화면 안에 들어오는지를 보고, 그림은 찍은 화면으로 직접 봤다. 3D 그림의 점을 눌러 가운데를 옮기는 것과 돌리기·확대는 시험하지 않았다 (목록의 단추로 본다). 그래픽 가속이 없는 PC 에서의 속도를 재지 않았다. 노드 200개의 그림은 빽빽하다. 처음 만든 것은 카메라가 가운데에 바짝 붙어 이웃이 화면 밖으로 나갔다: 찍은 화면을 보고 고쳤고, 그 뒤로 시험이 가장자리를 본다.

  - 올린 직후의 답과 달라지는 것 (D7 에 적었다): 처리 상태와 조치의 수는 지금 저장된 값이다. 이름표와 참·거짓의 보일 글자는 지금 적재된 Pack 의 정의로 읽는다 (Pack 을 다시 적재해 정의를 바꿨으면 지난 판도 새 정의로 보인다). `processingNotStarted` 는 언제나 false 다. 읽는 도중에 다시 처리가 돌면 상태와 까닭과 조치의 수가 서로 다른 순간의 것일 수 있다.
  - 시험이 없는 것: 대기(PENDING)인 변동이 든 판, 바뀐 값을 남기기 전에 들어간 판 (`changedValues` 가 null), Pack 을 다시 적재한 뒤의 지난 판, 개체를 저장소에서 찾지 못하는 경우. api 의 시험은 시험용 Pack 의 사본으로만 했다 (link 의 시험은 지어낸 Pack 이다. 두 예시 Pack 은 리허설이 화면으로 본다).
  - 남은 것: 받은 때로 정렬하는 색인이 없다 (Pack 의 판을 모두 읽어 정렬한다. 판이 수천이 되기 전에는 문제가 없을 것으로 보지만 재지 않았다). 판 하나의 결과에서 조치의 수는 변동마다 한 번씩 묻는다 (변동이 수백인 판에서는 느릴 수 있다. 재지 않았다). 거부된 투입은 보이지 않는다. 입력 자료나 날짜로 거르는 것은 없다. 지난 판의 원본 파일을 내려받는 것은 없다.

#### E-07 컨테이너 이미지와 설치 스크립트 v0

- 모듈: common
- 수용 기준: 이미지 두 개로 다른 PC에서 뜬다
- 선행 작업: SK-08
- 진행 (2026-11-23): 보드의 카드를 그대로 옮기고 만들었다 (D2 AD-363). **수용 기준은 아직 확인되지 않았다: 다른 PC 에서 띄워 보지 않았다** (만든 PC 에서, 배포 폴더를 다른 자리에 복사해 띄워 본 것까지다).
  - 만든 것: `bash tools/package.sh [amd64] [arm64]` 가 배포 폴더 `dist/tabnit-base-<버전>-linux-<CPU>/` 를 만든다. 이미지 둘을 파일로 (`images/`), 설치 구성과 설치 스크립트 (`deploy/install/compose.yaml`, `install.sh`), 저장소의 Pack, 버전과 CPU 와 파일의 지문 (`VERSION`, `ARCH`, `SHA256SUMS`). 받는 쪽은 폴더를 통째로 복사해 그 폴더에서 `bash install.sh` 를 부른다: CPU 와 파일의 지문을 확인하고, 이미지를 읽어 들이고, 데이터베이스의 비밀번호를 처음 한 번 만들어 `.env` 에 두고, HTTPS 의 인증서를 마련하고 (폴더의 `tls/cert.pem`, `tls/key.pem` 또는 자체 서명), 컨테이너 둘을 띄운다. 사용자 만들기, 막힘 풀기, 비밀번호 바꾸기, 로그, 내리기도 같은 스크립트로 한다. 인터넷이 없어도 된다.
  - PostgreSQL 을 18 로 고정했다: 설치 구성, 개발 구성, 서버 시험, 검증 질문 실행. 고정한 뒤 `./gradlew build` 와 검증 질문 71/71 이 통과했다.
  - 앱의 이미지는 빌드 단계를 만드는 PC 의 CPU 로 돌린다: 다른 CPU 용을 만들 때 빌드를 흉내 내어 돌리지 않는다.
  - 돌려서 확인한 것 (애플 실리콘 맥 한 대, Docker 29.9): arm64 용과 amd64 용 배포 폴더가 만들어진다 (897 MB, 850 MB). arm64 용을 다른 자리에 복사해 설치했다. 자체 서명 인증서로: 이미지를 파일에서 읽어 들이고, 앱이 8443 에서 HTTPS 로 뜨고 (설치 스크립트가 HTTPS 로 상태를 물어 확인한다), 스키마 변경 18개가 적용되고, PostgreSQL 은 18.7 이고, 앱은 관리자 권한 없이 돈다. 받은 인증서(시험용으로 만든 PEM)로도 뜬다. 다시 불러도 그대로 뜬다. 설치 스크립트로 사용자를 만들면 데이터베이스와 감사 기록에 남는다. amd64 용을 만든 뒤 이 PC 의 `postgres:18` 이 이 PC 의 CPU 의 것으로 되돌아온다.
  - 확인하지 못한 것: **다른 PC 에서 띄우기. amd64 용 배포 폴더를 실제로 띄우기** (만들어지는 것까지만 봤다). HTTPS 로 로그인하고 Pack 을 적재하고 화면을 여는 것 (설치된 제품에 요청을 보내 보지 못했다). 리눅스 서버에서의 설치 (맥에서만 돌렸다). 막힘 풀기와 비밀번호 바꾸기, 로그 보기. 파일이 상했을 때와 CPU 가 다를 때의 거부. 받은 인증서의 개인 키에 암호가 걸린 경우 (받지 않는다).
  - 검토에서 찾아 고친 것 (2026-11-23): (가) 새 버전의 배포 폴더에서 처음 부르면 `.env` 가 없어 비밀번호를 새로 만들었고, 데이터는 옛 비밀번호만 알아 앱이 뜨지 않았다. 데이터가 있는데 `.env` 가 없으면 앞 폴더의 `.env` 를 복사하라고 알리며 멈춘다. (나) 처음 설치한 뒤 다른 포트를 주고 다시 부르면 띄우는 포트와 확인하는 포트가 어긋났다. 설치 구성의 값은 `.env` 의 것만 쓴다. (다) 파일의 지문이 `packs/` 까지 덮어, 받은 쪽이 Pack 을 고치면 설치 스크립트가 거부했다. 지문에서 `packs/` 를 뺐다. 셋 다 다시 돌려 확인했다. 받은 개인 키를 다른 사람이 읽을 수 있으면 알리고, 비밀번호를 명령 줄에 적으면 셸의 기록에 남는다는 것을 쓰는 법에 적었다.
  - 남은 것 (E-09 에서): 설치 스크립트의 자동 시험이 없다 (문법만 확인한다). 새 버전으로 올리는 절차는 앞 폴더의 `.env` 를 복사하는 것까지만 있다 (되돌리는 절차는 없다). 데이터를 지우는 명령이 없다 (볼륨을 손으로 지운다). 받은 인증서를 바꾸는 절차 (처음 설치할 때의 방식이 `.env` 에 남는다). 설치한 뒤 Pack 을 더하는 법은 폴더의 `packs/` 에 두는 것뿐이다. 포트와 시간대는 처음 설치할 때만 정한다. 컨테이너의 바탕 이미지의 작은 버전은 고정하지 않았다. 배포 폴더가 크다 (이미지를 줄이지 않았다).
