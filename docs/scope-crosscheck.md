# v1.0 범위의 기준 대조: 시연 앱의 기능 리스트 30개와 지금의 제품

상태: 초안 (2026-11-26. 같은 날 GS 사전상담 자료의 내용을 더했다). 설계 변경의 제안이다. **5절의 질문 가운데 열(1 ~ 7, 17 ~ 19)에 대표가 답했고 `docs/D2` 에 AD-401 ~ AD-410 으로 적었다. 나머지 스물하나(8 ~ 16, 20 ~ 31)는 미정이다.** 답은 5절의 질문 옆에 적었다. 본문의 다른 곳은 답하기 전에 쓴 그대로다. D1 3절은 카드 0-1 에서 고친다. 코드는 고치지 않았다.

> 이 문서는 결정이 아니다. D1 ~ D9 가 여전히 기준이다. 정해진 것은 `docs/D2` 의 줄(AD-401 ~ AD-410)이 기준이다.

## 0. 이 문서를 읽는 법

**무엇과 무엇을 견줬는가.**

- 기준 1: GS 사전상담 자료 (2026-10-26, 17쪽. 저장소에 두지 않는다). **인증의 대상은 v1.0, 기능 리스트는 30개 (1-1 ~ 5-4), 접수의 목표는 2027년 1분기다.** 11쪽에 기능마다의 시험 입력, 기대 출력, 합격 기준(안)이 있다. 자료 스스로 "합격 기준은 당사 제안(안)이며, 기능 리스트 확정 시 시험기관과 협의하여 조정"한다고 적는다. 자료의 기능 리스트 30개는 시연 앱의 것과 번호와 이름이 같다.
- 기준 2: 시연 앱의 소스 (`tabnit-demo-src`, v7, 2026-11-04). README 3절과 `src/10-data.js` 의 `D.FEATURES` (기능 30개, 확장 둘), `D.CQ` (골든셋 10개), `D.PERF` (성능 목표 5개), `src/60-guide.js` (시연 가이드 S0 ~ S10), `src/66-e2e-scenarios.js` (사용법 시나리오 E01 ~ E13). 코드는 가져오지 않는다. 명세로만 읽었다.
- 제품: 이 저장소의 `main` (`10b5058`, 2026-11-26). `docs/api/openapi.yaml` (operationId 17개), `server/` 의 공개 클래스, `web/src` (화면 넷), 시험 파일의 이름, `packs/` 의 검증 질문.

**어떻게 확인했는가.** GS 자료는 PDF 에서 글자를 뽑아 읽었다 (그림은 보지 못했다. 13쪽의 시연 화면, 15쪽의 개발 경과, 17쪽의 회사 소개는 훑기만 했다). 조사 둘로 나눠 소스를 읽었다 (시연 앱 쪽, 제품 쪽). 아무것도 실행하지 않았다: 시연 앱의 숫자는 소스에 적힌 값이고, 제품의 시험 이름은 파일에서 읽은 것이다 (통과 여부는 이 조사에서 다시 확인하지 않았다. 마지막으로 돌린 것은 같은 날의 PR #114 다).

**판정의 뜻.**

| 판정 | 뜻 |
|---|---|
| 충족 | 시연이 그 기능에 적은 합격 기준·핵심 동작을 제품이 자기 방식으로 해낸다. 근거(API, 시험)를 적었다 |
| 부분 | 핵심의 일부만 있다. 없는 것을 "차이"에 적었다 |
| 없음 | 그 기능의 코드·API·화면을 찾지 못했다. 가까운 것이 있으면 적었다 |

"충족"도 시연과 같은 모양이라는 뜻이 아니다. 차이가 있으면 적었다.

**확인하지 못한 것.**

- 시연 앱의 `47-rules.js`, `48-meta.js`, `49-kg-git.js` 는 화면 머리의 설명과 일부 함수만 읽었다 (확장 ⑥, ⑦과 6단계의 카드가 여기에 기댄다).
- 개발 보드(`tools/board/index.html`)의 카드 내용은 읽지 않았다. 당김 범위의 카드 번호는 D1 4절의 표에서 옮겼다.
- 모듈별 지침 파일, D3·D5·D8 의 본문은 이 대조를 위해 다시 읽지 않았다. 3절에 적은 "바뀌는 절"은 절의 제목으로 고른 것이라, 고칠 때 다시 확인해야 한다.

**먼저 알아 둘 것: 시연 앱을 그대로 따를 수 없는 곳.** 시연 앱은 요구 명세지만, 아래는 이 저장소의 규칙(`CLAUDE.md` 8절)과 부딪친다. 5절의 질문 1 ~ 3 이 이것이다.

| # | 시연 앱의 사실 | 이 저장소의 규칙 |
|---|---|---|
| 가 | 유효기간의 종료일이 **포함**이다 (`from <= d && d <= to`). 겹치는 관계는 "새 시작일 − 1일"로 닫는다 (`20-engine.js:87, 96`). **GS 자료는 둘을 섞어 적었다** (6쪽): 조회의 식은 종료일 제외(`valid_from ≤ date < valid_to`)인데 자동 종료는 "새 시작일 − 1일"이다. 적힌 대로면 그 하루가 빈다 | 시작일 포함, 종료일 **제외** (`CLAUDE.md` 8절, D3 4절). 겹치는 것은 새 시작일로 닫는다. GS 자료의 조회 식과 같다 |
| 나 | 규칙 평가(`E.evaluate`)가 규칙 팩 ID 마다의 분기와 예시 값으로 쓰였다. 변동의 종류마다 따라갈 관계와 깊이가 엔진 코드에 고정이다 (`20-engine.js:249 ~ 268`) | 엔진에 업무 용어와 예시 값을 넣지 않는다 (일반성). 따라서 시연의 **결과**는 옮기되 **방식**은 옮기지 않는다 |
| 다 | 조치 하나가 대상 **묶음**을 가진다 (조치 6건이 설비 12대, 인원 42명을 덮는다). 조치에 담당자, 부서, 상태 6종이 있다 | 조치는 변동 이벤트, 규칙, 대상마다 하나다 [AD-60]. 같은 변동에서 제조 안전 Pack 은 조치 64건을 만든다 (Q-12) |
| 라 | 서명은 열쇠가 없는 해시 비교다 (`ed25519:` 라는 접두어만 붙였다). Pack 설치의 서명 검사는 파일의 `signed` 표시를 그대로 믿는다 | 그대로 옮기면 서명이 아니다. 제품에서 무엇을 "서명"이라 할지 정해야 한다 |
| 마 | 식별자 매핑(1-3), 연결 테스트(1-1), 증분 건수(1-2), 성능의 다섯째 지표는 계산이 아니라 고정 자료의 재생이다 | 합격 기준은 옮길 수 있으나 구현의 본보기는 없다 |

## 1. 기능 30개의 대조

경로의 약칭: `S/` 는 `server/`, `W/` 는 `web/`. 시연 앱의 파일은 `src/` 를 생략하고 번호로 적었다 (20 = `20-engine.js`). 표의 마지막 칸은 GS 사전상담 자료 11쪽의 합격 기준(안)이다: 자료는 몇 기능을 한 줄로 묶어 적었고 (묶인 것을 괄호에 적었다), 3-1, 4-1, 4-7 은 줄이 없다. **판정은 시연 앱의 핵심 동작으로 내린 것이다. 합격 기준으로 보면 달라지는 것은 표 아래에 따로 적었다.**

**집계 (main `3435aea`, 2026-11-27. main `bae60eb` 에서도 같다): 충족 9, 부분 15, 없음 6.** 처음의 집계는 충족 9, 부분 12, 없음 9 였다 (대표의 초벌 판정 충족 9, 부분 13, 없음 8 과는 2-3 경로 추적을 "없음"으로 본 것 하나가 달랐다. AD-408). 바뀐 것은 아래 둘째 "다시 매김"에 있다.

**다시 매김 (2026-11-27, main `08037c1`).** 판정을 지금의 main 으로 다시 봤다. **앞의 판정(main `10b5058`)과의 차이: 없다. 충족 9, 부분 12, 없음 9 그대로다** (GS 합격 기준으로 센 것도 충족 9, 부분 9, 없음 12 그대로다). 그 사이에 main 에 병합된 것은 이 문서를 더한 PR 둘(#115, #116)뿐이고, `server/`, `web/`, `packs/`, `verify/`, `docs/api/` 는 바뀌지 않았다 (`git diff 10b5058 origin/main` 이 이 문서 하나만 낸다). 0단계와 1단계의 카드 18개(D9 의 E-20 ~ T-08)는 모두 시작하지 않았다: 근거로 적을 병합된 카드와 PR 이 없다. 충족으로 바꾼 기능이 없다. 2-3 의 "없음"은 대표가 확정했다 (AD-408). 시험은 이번에도 돌리지 않았다.

**다시 매김 (2026-11-27, main `3435aea`).** 0단계와 1단계의 카드 열둘이 병합된 뒤의 main 으로 다시 봤다. **앞의 판정(main `08037c1`)과의 차이: 없음이던 셋(2-2, 2-3, 2-6)이 부분이 됐다. 충족 9, 부분 12, 없음 9 → 충족 9, 부분 15, 없음 6.** GS 합격 기준으로 센 것은 충족 9, 부분 9, 없음 12 → **충족 11, 부분 10, 없음 9** 다 (2-6 과 5-2 가 충족으로, 2-2 와 2-3 이 부분으로).

| 구조화 문서 버전 비교: 건마다 1초 미만 | 문서 2종, 변경 5항목 | 목표 없음. 판 올리기 전체가 관계 1초에 1,800행쯤, 개체 1,100행쯤 (A-07) | 비교만 따로 재지 않았다. 예시 Pack 의 문서 판(12 ~ 14행)에서는 문제가 될 크기가 아니다 |
| 변동 이벤트 → 조치 생성 지연: 1분 미만 | 영향 대상 100건 | 목표 없음. 잰 값 (A-07): 영향 대상 110개에서 변동 하나의 처리 40 ms | 조건이 가깝고 값은 목표의 안이다. 목표로 적혀 있지는 않다 |
| 관계 지도 조회: 초기 표시 3초 미만 | 노드 1,000, 표준 PC 의 브라우저 | 노드 한도가 200 이다 [AD-357]. 서버의 조회는 큰 자료에서 깊이 1 이 25 ms. 화면이 그리는 시간은 재지 않았다 (D-14: "그래픽 가속이 없는 PC 에서의 속도를 재지 않았다") | 1,000 노드를 그리지 않는다. 화면의 시간을 잰 값이 없다 |
| 증분 수집 처리량: 1분에 1만 건 이상 | 모의 DB, 커넥터 하나 | 증분 수집이 없다. 판 올리기는 1초에 1,100 ~ 1,800행이라 1분이면 6만 ~ 10만 행쯤이다. 다만 관계 100만 행의 파일 하나에 10분쯤, 메모리 7GB 넘게 쓴다 (C-13 당김 [AD-358] [AD-362]) | 견줄 기능이 없다. 판 전체를 다시 넣는 속도로는 목표의 수를 넘는다 |

## 3. 설계가 막고 있는 곳

기능이 "없음"이나 "부분"인 까닭 가운데, 코드를 더하는 것으로는 안 되고 이미 내린 결정을 다시 열어야 하는 것들이다. "바뀌는 절"은 절의 제목으로 고른 것이다 (0절).

### 가. 자료가 판으로만 들어온다

| | |
|---|---|
| 지금 | 자료가 들어오는 길은 `submitEdition` 하나다. 판은 입력 자료의 **전체**다: 새 판에 없는 행의 관계와 값은 그 판의 적용일로 끝난다. 첫 판은 변동을 만들지 않는다 |
| 막히는 기능 | 1-2 (증분), 2-5 (등록 API), 3-3 (피드), 1-1 (DB 와 API 커넥터), 시나리오 S3, S4, S6 |
| 다시 여는 결정 | AD-42 (사라진 관계는 새 판의 적용일로 끝낸다), AD-45 (개체와 관계는 항상 입력 자료가 매핑을 거쳐), AD-121, AD-148 (첫 판은 변동이 없다), AD-164 (판 하나가 트랜잭션 하나) |
| 바뀌는 문서 | D3 6절 (판과 변동), D5 5절 (link 의 테이블), D6 7절 (매핑), D7 5절 (판 올리기) |
| 깨지는 것 | "없는 행은 끝낸다"에 기대는 link 의 시험 (`EditionIngestTest`, `EditionDiffTest`). 판의 차례에 기대는 전수 대조 전부 (X-C, X-I, X-A, X-R) |
| 권하는 길 | **전체 판을 그대로 두고, "일부만 담은 변경 묶음"을 판의 다른 종류로 더한다** (담긴 항목만 더하고 고치고, 지우는 것은 지운다고 적는다). 판 비교, 변동 이벤트, 뒤 단계는 그대로 쓴다. 등록 API, 피드, 증분 수집은 모두 이 묶음을 만드는 길이 된다 (4단계의 첫 카드) |
| 하지 않는 대안 | 개체와 관계를 직접 쓰는 API 를 core 에 여는 것. 판 비교를 거치지 않아 변동 이벤트와 근거의 판이 사라진다 |

### 나. 개체 하나를 고치는 길이 없다

| | |
|---|---|
| 지금 | 개체, 관계, 속성 값은 어느 입력 자료의 어느 판에서 왔는지를 갖고, 그 입력 자료의 다음 판이 덮어쓴다 |
| 막히는 기능 | 시나리오 S10 (노드와 관계의 생성, 수정, 폐기), 2-5 의 등록 |
| 다시 여는 결정 | AD-45. 그리고 "손으로 고친 것과 다음 판이 부딪히면 누가 이기는가"가 새 결정이다 (지금은 다른 입력 자료가 넣은 것과 겹치면 판을 거부한다 [AD-322]) |
| 바뀌는 문서 | D3 2절 ~ 4절, D5 3절, D7 (새 API) |
| 깨지는 것 | 출처를 입력 자료와 판으로만 보는 곳 (`BasisEdition`, 관계의 식별자). 식별자에 출처가 들어 있다 |
| 권하는 길 | 손으로 넣는 것을 **입력 자료 하나**("직접 등록")로 치고, 한 건을 고치는 것을 그 입력 자료의 변경 묶음 하나로 만든다 (가의 길 위에). 출처, 변동 이벤트, 감사가 그대로 따라온다 |
| 하지 않는 대안 | 개체에 "고친 사람"의 열을 더해 판과 무관하게 고치는 것. 다음 판이 조용히 덮어쓴다 |

### 다. 영향 방향이 관계 유형마다 하나다

| | |
|---|---|
| 지금 | Pack 이 관계 유형마다 영향 방향을 하나 적는다 (출발 → 도착, 도착 → 출발, 양쪽, 없음). 형식에는 "양쪽"이 있으나 두 예시 Pack 은 한쪽으로 정했다. 변동이 무엇이든 같은 방향으로 따라간다 |
| 시연 | 관계 유형마다의 "전파 선언"이 기본이고, **변동의 종류마다 따라갈 관계와 방향, 깊이를 따로** 준다 (문서 변경은 깊이 2, 요건과 설비는 3). 요건 적용은 양쪽이다 |
| 막히는 기능 | 시나리오 S3 (요건이 바뀌면 걸린 대상을 찾는다), S4 의 노출 변화, B-03 의 조사에서 "결정이 있어야 한다"로 남긴 법규 개정 |
| 다시 여는 결정 | AD-287 (제조 안전 Pack 의 요건 적용은 한쪽), AD-297 (퇴직연금 Pack 은 관계 유형마다 하나), AD-303 (한 관계를 양쪽으로 또는 위로 갔다가 내려오는 탐색은 1월 범위의 후보), AD-64 (영향 범위는 변동 이벤트마다 하나) |
| 바뀌는 문서 | D3 7절 (영향), D6 5절 (온톨로지의 영향 방향), D8 2절 (규칙 파일), D5 6절 (저장한 영향 범위) |
| 깨지는 것 | 영향 범위의 전수 대조 전부 (X-I: 제조 안전 33, 퇴직연금 25)와 그 위의 조치 (X-A). `ImpactQueryTest`. 두 Pack 의 정답을 만드는 스크립트의 방향 표 |
| 권하는 길 | 관계 유형의 방향은 기본값으로 두고, **Pack 이 변동의 갈래(어느 입력 자료의 변동인가)마다 따라갈 관계 유형과 방향을 덮어쓸 수 있게** 한다. 엔진에 변동의 종류를 넣지 않는다 (0절 나). 한 변동 이벤트의 영향 범위는 여전히 하나다 |
| 하지 않는 대안 | 요건 적용을 "양쪽"으로 바꾸는 것 (지금도 된다). 물질 하나가 바뀌면 같은 요건이 걸린 다른 물질과 그 공정까지 영향 범위에 든다 [AD-287 의 이유] |

### 라. 조치의 상태와 담당

| | |
|---|---|
| 지금 | 조치는 변동 이벤트, 규칙, 대상마다 하나다. 상태는 대기, 확정, 보류. 담당자의 자리가 없다 |
| 시연 | 조치 하나가 대상의 묶음을 덮는다. 상태 여섯과 전이의 표. 담당자는 역할과 사업장의 표에서 자동으로 고르고 손으로 바꾼다 |
| 막히는 기능 | 4-3, 4-4, 4-5, 시나리오 S1 의 "조치 6건" |
| 다시 여는 결정 | AD-47 (상태는 셋, 확정은 되돌릴 수 없다), AD-60 (조치의 식별), AD-309 (묶어 보기는 1월 범위의 후보), AD-270 (누가 확정하는가) |
| 바뀌는 문서 | D3 8절 (조치), D5 6절 (rules 의 테이블), D7 6절 ~ 7절, D8 5절 (조치) |
| 깨지는 것 | 상태를 더하는 것만으로는 깨지지 않는다 (더하는 변경). 조치를 묶음으로 바꾸면 조치의 전수 대조 전부 (X-A)와 `ActionGeneratorTest`, `actions.spec.ts`, `flow.spec.ts` 가 깨진다 |
| 권하는 길 | **조치는 대상마다 하나로 두고** (근거가 분명하다 [AD-60]), 상태(완료, 반려)와 담당자를 더한다. "조치 6건"은 같은 변동과 같은 규칙의 조치를 **묶어 보이는** 것으로 푼다 (보기의 일이다 [AD-309]). 담당자를 정하는 표는 Pack 의 정의다 (역할과 조직은 업무 지식이다) |
| 하지 않는 대안 | 조치를 규칙마다 하나로 바꾸는 것. 대상 하나만 끝낸 것을 적을 곳이 없어진다 |

### 마. 규칙이 Pack 의 한 파일이다

| | |
|---|---|
| 지금 | 규칙은 Pack 의 파일 하나이고, Pack 을 다시 적재하면 통째로 바뀐다. 규칙마다의 켜고 끔, 버전, 묶음이 없다 |
| 막히는 기능 | 4-1 (활성과 비활성, 버전, 되돌리기), 4-6 (꺼 둔 규칙을 미리 돌려 보기), 시나리오 S6, 확장 ⑥ |
| 다시 여는 결정 | AD-216 (적재된 Pack 의 규칙은 다시 적재로 바뀐다), AD-272 (Pack 은 서버에 둔 것을 고른다), D6 10절의 B-13 |
| 바뀌는 문서 | D6 8절 ~ 9절, D8 2절 (규칙 파일), 4절 (평가 순서), D5 4절 (pack 의 테이블) |
| 깨지는 것 | 규칙에 "켜짐"을 더하는 것은 더하는 변경이다 (없으면 켜짐). 규칙의 묶음과 버전은 `PackRule*Test` 와 조치에 적어 둔 규칙의 내용에 닿는다 |
| 권하는 길 | 두 걸음으로 나눈다. (1) 시뮬레이션은 규칙의 형식을 바꾸지 않고 만든다: "이 변동에 지금의 규칙을 쓰기 없이 돌린다". (2) 규칙의 묶음, 켜고 끔, 버전은 Pack 의 형식 변경으로 따로 한다. 시연의 합격 기준("미리보기 = 실제")은 (1)만으로 확인된다 |
| 하지 않는 대안 | 규칙을 데이터베이스에서 화면으로 고치게 하는 것 (6단계의 일이다. 업무 지식이 Pack 밖에 생긴다) |

### 바. 역할이 둘이다

| | |
|---|---|
| 지금 | 관리자와 담당자. 층으로 쌓인다 (관리자는 담당자의 일을 모두 한다). 권한은 API 마다 역할로 확인한다 |
| 시연 | 역할 다섯, 권한의 이름 일곱 (읽기, 쓰기, 건강 정보 읽기, 자료 관리, 규칙 관리, 시스템 관리, 감사 읽기), 계정마다의 추가 권한, 화면의 허용 목록, 필드의 가림 |
| 막히는 기능 | 5-1, 골든셋 CQ-08 과 CQ-09, 시나리오 S4 |
| 다시 여는 결정 | AD-270 (역할은 층으로 쌓인다), AD-262 (세션과 쿠키. 밖의 시스템이 쓸 토큰이 없다), 당김의 A-12 와 D-12 |
| 바뀌는 문서 | D7 2절 (공통 규칙)과 9절 (로그인과 세션), D5 7절 (common 의 테이블), D6 (가릴 속성을 Pack 이 적는다면 5절) |
| 깨지는 것 | `RolesApiTests` (역할 둘을 전제로 한다), `SecurityConfiguration`. 가림을 넣으면 속성 값을 돌려주는 모든 API 의 답 |
| 권하는 길 | 역할을 **권한의 묶음**으로 바꾼다 (지금의 두 역할은 그 묶음의 두 본보기로 남는다). 가릴 속성과 그것을 읽는 권한의 이름은 Pack 이 적는다 ("건강 정보"는 업무 용어다) |
| 하지 않는 대안 | 시연의 역할 다섯을 그대로 코드에 넣는 것. 역할의 이름이 업무 영역에 묶인다 |

### 사. 품질 게이트와 격리

| | |
|---|---|
| 지금 | 틀린 행은 건너뛰고 알린다. 제약을 어긴 자료는 그대로 들어가고, 물으면 보고한다 |
| 시연 | 점수가 기준에 못 미치는 레코드는 **들어가지 않고** 격리 큐에 남는다. 관리자의 판정이 규칙으로 저장돼 다음에 자동으로 처리된다 |
| 막히는 기능 | 1-4, 1-3 의 "실패 건은 격리", 골든셋 CQ-07, 시나리오 S5 |
| 다시 여는 결정 | AD-92 와 AD-390 (제약을 어긴 자료도 그대로 들어간다. 위반은 저장하지 않는다), AD-153 (알림), AD-164 (판 하나가 트랜잭션 하나: 일부만 보류하는 판이 없다) |
| 바뀌는 문서 | D3 6절, D5 5절, D6 6절 ~ 7절, D7 5절 |
| 깨지는 것 | 판이 "모두 들어가거나 하나도 안 들어간다"에 기대는 것. 격리된 행이 나중에 들어오면 그 판의 변동이 달라진다: 영향 범위와 조치를 판을 투입한 직후에 한 번 계산한다는 것 [AD-119] 과 맞춰야 한다 |
| 권하는 길 | 격리된 행을 **그 판에서 뺀 것**으로 치고 (지금의 "건너뛴 행"과 같다), 판정으로 풀린 행은 **변경 묶음 하나**로 들어오게 한다 (가의 길). 신뢰도의 산식과 기준은 Pack 의 정의다 |
| 하지 않는 대안 | 제약의 위반을 격리의 기준으로 바로 쓰는 것. 제약은 조회 시점의 전체 자료에 거는 것이라 [AD-390] 행 하나의 판정이 아니다 |

### 자. 정의를 제품 안에서 고친다

| | |
|---|---|
| 지금 | 업무 영역의 지식은 Pack 의 파일에 있고, 제품은 읽기만 한다. 고치려면 파일을 고쳐 다시 적재한다. 정의를 보는 화면도 없다 |
