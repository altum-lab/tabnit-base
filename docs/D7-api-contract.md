## 1. 계약을 다루는 법

- **계약이 먼저다.** OpenAPI 규격 파일을 먼저 고치고 그에 맞춰 구현한다. 구현을 먼저 하고 규격을 맞추지 않는다. 규격에 없는 API 를 구현하지 않는다. [AD-09] [api] [스킬 contract-first]
- 형식은 OpenAPI 3.1 이다. [AD-09]
- 규격을 바꾸는 일은 설계 변경 절차를 따른다. [C 7절]
- 화면의 호출 코드는 규격에서 만든다(`npm run gen:api`). 손으로 고치지 않는다. [web] [보드 API-01]
- **규격 파일은 `docs/api/openapi.yaml` 이다.** 서버의 구현과 화면의 호출 코드 생성이 모두 이 파일을 읽는다. [AD-77]
- 이 문서는 규칙과 까닭을 적고, 항목 하나하나의 형식은 규격 파일이 정한다. 둘이 다르면 규격 파일을 이 문서에 맞춘다. (제안)

## 2. 모든 API 에 공통인 규칙

### 조회 시점

- 관계를 읽는 모든 API 는 조회 시점을 받는다. 항목 이름은 `asOf` 다. [api] [스킬 contract-first] [AD-50]
- 조회 시점은 사용자가 고르는 값이고, 엔진에는 기준 날짜로 넘어간다. 값은 같다. [AD-50]
- 형식은 `2026-03-01` 모양의 날짜다. 시각은 없다. [D3 4절]
- 요청에 `asOf` 가 없으면 API 층이 한 번만 오늘로 정해 넘긴다. 오늘은 설치 설정의 시간대에서의 날짜이고, 설정에 적지 않으면 Asia/Seoul 이다. 엔진 안에는 기본값이 없다. [AD-23] [AD-40]
- **응답에는 어느 날짜로 답했는지를 `asOf` 로 반드시 담는다.** 요청에 있었든 없었든 담는다. [api] [AD-23]
- 형식이 틀린 `asOf` 는 거부한다. [보드 CORE-03] **받는 날짜는 0001-01-01 부터 9999-12-31 까지다**: 그 밖의 날짜(`+10000-01-01` 같은 것)도 형식이 틀린 것과 같이 400 `INVALID_AS_OF` 로 거부한다. [AD-370]

### 순서

- 목록의 정렬 기준은 규격에 적는다. [스킬 contract-first]
- api 는 모듈이 준 순서를 바꾸지 않는다. 화면도 서버가 준 순서를 바꾸지 않고, 수를 다시 세지 않는다. [api] [AD-21]

### 나눠 주기

큰 목록은 나눠 준다. 관계(4절), 조치와 영향 대상(6절)의 목록이 그렇다. [AD-310] [AD-347]

- 요청: `offset` (건너뛸 수. 없으면 0), `limit` (한 번에 받을 수. 없으면 50, 1 부터 200 까지).
- 응답: 답에 쓴 `offset` 과 `limit`, 그리고 **나누기 전의 전체 수 `total`** 을 함께 담는다. 화면은 수를 다시 세지 않는다.
- **나눠 받은 것을 이으면 한 번에 받은 것과 순서까지 같다.** 나누는 일은 정해진 순서(위 "순서") 위에서 한다: 순서를 정하는 모듈이 나눈다. api 가 받은 목록을 잘라 주지 않는다.
- `offset` 이 전체 수와 같거나 크면 빈 목록이다 (오류가 아니다). `total` 은 그대로 준다.
- 수가 아닌 값, 음수인 `offset`, 1 보다 작거나 200 보다 큰 `limit` 은 400 이다 (`INVALID_OFFSET`, `INVALID_LIMIT`). 조용히 고쳐 받지 않는다.
- 숫자는 영어 숫자(0 ~ 9)만으로 열 자까지 적는다. 더하기표, 빈칸, 소수점, 다른 글자의 숫자는 수가 아니다.
- **조회 시점을 받는 목록을 나눠 받을 때는 조회 시점을 적는다.** `asOf` 를 빼면 부를 때마다 서버가 오늘로 정하므로, 자정을 넘기면 쪽마다 날짜가 달라진다. 첫 답의 `asOf` 를 다음 요청에 그대로 보낸다 (화면이 그렇게 한다).
- 여러 번에 나눠 받는 사이에 목록이 바뀌면 (새 판이 들어와 조치가 생기거나 관계가 달라지면) 항목이 겹치거나 빠질 수 있다. 저장된 영향 범위는 바뀌지 않는다. 받을 때마다의 `total` 이 달라지면 처음부터 다시 받는다.
- 나누지 않는 목록: Pack 과 입력 자료(8절), 처리되지 않은 변동(5절), 조치 하나의 이력(7절), 판 올리기의 응답의 바뀐 항목과 알림(5절).

### 근거

- 결과에는 근거로 가는 연결을 담는다. 영향 대상에는 경로, 조치에는 근거 조항과 그 판. [api] [AD-04]

### 식별자

- 개체와 관계는 `id` 문자열 하나로 가리킨다. [AD-65]
- `id` 는 서버가 만든 것을 그대로 돌려보내는 값이다. 화면은 `id` 를 쪼개거나 만들지 않는다. (제안)
- `id` 에는 세로 막대(`|`)를 비롯해 어떤 글자든 들어갈 수 있다. [D5 1절] 그래서 `id` 는 주소의 일부가 아니라 질의 항목(`?entityId=`)으로 받는다. [AD-78]

### 개체

개체를 담는 응답은 식별자와 함께 사람이 읽을 것을 준다. [AD-326] [AD-349]

| 항목 | 뜻 |
|---|---|
| `entityId` | 개체의 `id`. 서버에 되돌려 보내는 값 |
| `entityType` | 개체 유형의 이름 (Pack 이 정한 것) |
| `entityTypeLabel` | 개체 유형의 이름표. 화면에 보일 이름 (Pack 의 `rdfs:label`) |
| `entityKey` | 입력의 키 |
| `displayName` | 표시 이름. 없으면 `null` |

- **표시 이름**은 Pack 이 그 유형의 표시 이름으로 정한 속성(`tabnit:displayNameProperty`, 상위 유형에서 받은 것 포함 [AD-88])의, 정해진 날짜에 유효한 값이다. Pack 이 정하지 않았거나 그 날짜에 값이 없으면 `null` 이고 화면은 키를 보여 준다 (D6 5절). 앞의 값을 끌어다 쓰지 않는다. [AD-55] [AD-70]
- **어느 날짜의 값인가**: 관계 조회는 조회 시점. 조치와 변동의 영향 범위는 그 변동이 나온 판의 적용일. 보는 날에 따라 달라지지 않는다. [AD-349]
- **표시 이름과 이름표는 저장하지 않는다. 응답을 만들 때 지금의 Pack 정의와 지금의 자료로 읽는다.** 같은 Pack 정의와 같은 자료에서는 언제나 같다. Pack 을 다시 적재해 이름표나 표시 이름 속성을 바꾸면 이미 만든 조치의 개체도 새 정의로 보인다 (조치의 내용, 근거 조항, 근거 경로는 그대로다). 지난 날짜의 값이 뒤늦게 들어오는 일은 없다 (둘째 판부터는 적용일 앞으로 넣지 않는다 [AD-200]). [AD-349]
- 개체가 저장소에 없으면 (생기지 않아야 한다: 개체는 지우지 않는다) 근거 없이 지어내지 않고 500 `INTERNAL` 로 답한다.
- 화면은 표시 이름, 유형의 이름표, 키를 함께 보여 준다. 화면이 `id` 를 쪼개 유형이나 키를 만들지 않는다.
- 지금 이렇게 주는 곳: 관계 조회(4절), 조치의 대상과 근거가 되는 주 개체(6절, 7절), 변동의 영향 범위의 영향 대상과 근거 경로(6절). 판 올리기의 응답과 처리되지 않은 변동(5절)의 개체는 아직 식별자뿐이다.

### 주소

- 모든 API 의 주소는 `/api/v1` 으로 시작한다. 계약을 깨는 변경이 필요하면 `/api/v2` 를 나란히 둔다. [AD-78]

### 로그인, 역할, 감사 기록

- 모든 요청은 로그인과 역할을 확인하고 감사 기록에 남긴다. 확인과 기록은 api 층이 common 을 불러서 한다. [api] [AD-05]
- **감사 기록** (D5 7절 audit_log):
  - 남기는 것: 로그인한 사람의 모든 API 요청(조회와 변경)과 그 결과, 로그인의 성공과 실패, 로그아웃, 권한이 없어 거부한 요청(403). 남기지 않는 것: 로그인하지 않은 채 부른 요청(401), 내 정보를 묻는 요청, 화면의 파일, 서버의 상태 확인. [AD-274]
  - **요청 하나는 두 줄이다.** 처리하기 전에 "누가 무엇을 하려 한다"를 먼저 남기고, 끝나면 결과를 한 줄 더 남긴다. [AD-273]
  - **하기 전의 줄을 남기지 못하면 변경을 하지 않고 조회도 답하지 않는다** (500 `INTERNAL`). 로그인과 로그아웃도 같다. [AD-05] [AD-275] 결과의 줄을 남기지 못한 것은 되돌릴 수 없다: 서버의 로그에 알리고, 하기 전의 줄이 남는다.
  - 무엇에 대해서인지는 요청의 항목 가운데 대상을 가리키는 것만 남긴다 (Pack, 입력 자료, 적용일, 개체, 조치, 변동 이벤트의 `id`, 거르는 상태). 조회에는 답에 쓴 기준 날짜를 남긴다. 비밀번호, 본문 전체, 올린 파일의 이름과 내용, 확정과 보류의 사유는 남기지 않는다.
  - 모든 API 는 남기는지 남기지 않는지를 코드에 밝혀 적는다. 밝히지 않은 API 는 요청을 받지 않는다.
- 역할은 둘이다. 관리자는 Pack 적재까지, 담당자는 조치 확정까지 할 수 있다. [common] **역할은 층으로 쌓인다: 관리자는 담당자의 일을 모두 한다.** [AD-270]
  - 담당자와 관리자: 보는 것 모두, 새 판 올리기, 조치의 확정과 보류.
  - 관리자만: Pack 적재 (10절).
  - 어느 API 를 어느 역할이 부를 수 있는지는 api 의 보안 설정 한 곳에 적는다. 할 수 없는 일을 부르면 403 `FORBIDDEN` 이고, 요청의 항목이 틀렸는지보다 권한을 먼저 본다. 관리자도 담당자도 아닌 역할의 사람은 로그아웃 말고 아무것도 부르지 못한다. (구현하면서 정한 것, "결정 필요" 15번)
  - 역할은 로그인할 때의 것이다. 세션이 이어지는 동안 바뀌지 않는다 (역할을 바꾸는 기능이 아직 없다).
- 권한이 없는 요청은 거부하고 그 사실도 감사 기록에 남긴다. [common]
- 감사 기록을 남기지 못하면 그 변경 요청도 실패로 처리한다. [AD-05]
- 로그인은 서버 세션과 쿠키로 한다 (9절). 로그인(`POST /api/v1/session`) 말고는 모두 로그인해야 부를 수 있다. [AD-262]
- **뼈대 단계의 임시 처리는 끝났다**: 로그인(E-02), 역할(E-06), 감사 기록(E-03, E-05)을 모두 구현했다. 로그인 없이 열고 기록을 남기지 않던 예외 [AD-80] 는 더 적용되지 않는다. 개발 환경 밖에 설치하기 전에 남은 것은 "결정 필요" 7번에 적었다.

### 오류

- 오류는 공통 오류 형식으로 낸다. 내부 예외 문구나 스택을 그대로 내보내지 않는다. [api]
- 사용자에게 보이는 문구는 한국어로, 무엇을 하면 되는지까지 적는다. [C 8절]
- 입력이 틀렸을 때는 어느 항목인지 알려 준다. [C 8절]
- 공통 오류 형식은 RFC 9457 (`application/problem+json`)에 `code` 와 `field` 를 더한 것이다. [AD-79]

| 항목 | 뜻 | 예 |
|---|---|---|
| `type` | 오류 종류의 주소. 따로 정하지 않은 오류는 `about:blank` | `about:blank` |
| `title` | 오류 종류의 짧은 이름 | "잘못된 요청" |
| `status` | HTTP 상태 | 400 |
| `detail` | 사용자에게 보이는 문구. 한국어로, 무엇을 하면 되는지까지 | "조회 시점의 형식이 틀렸습니다. 2026-03-01 과 같이 적어 다시 보내세요." |
| `code` | 오류의 종류. 화면이 이것으로 가른다. 바뀌지 않는 값이다 | `INVALID_AS_OF` |
| `field` | 틀린 항목의 이름. 입력 오류일 때만 | `asOf` |

`type`, `title` 에 넣을 값과 `code` 의 이름은 제안이다.

| 상황 | HTTP 상태 | `code` (제안) |
|---|---|---|
| 입력의 형식이 틀림 | 400 | `INVALID_AS_OF` 처럼 항목마다 |
| 로그인하지 않음 | 401 | `UNAUTHENTICATED` |
| 권한이 없음 | 403 | `FORBIDDEN` |
| 대상이 없음 | 404 | `ENTITY_NOT_FOUND` 처럼 대상마다 |
| 서버 쪽의 문제 | 500 | `INTERNAL` |

- 서버가 기본으로 내는 오류(없는 주소, 허용하지 않는 방식 등)도 이 형식으로 낸다. (제안. 아직 구현하지 않았다. 지금은 `code` 없이 나간다)
- 결과가 없는 것은 오류가 아니다. 빈 목록으로 답한다. 화면은 "영향 없음"처럼 없다는 사실을 말한다. [web]
- 없는 개체를 조회한 것은 결과가 없는 것과 다르다. 오류로 알린다. [보드 CORE-02]

### 값의 표기

- 날짜는 `2026-03-01`, 시각은 `2026-01-01T00:00:00Z` (협정 세계시) 모양으로 적는다. (제안)
- 항목 이름은 `validFrom` 처럼 낙타 표기로 적는다. (제안)
- 종료일이 없는 것은 `validTo` 를 `null` 로 적는다. 항목을 빼지 않는다. (제안)

## 3. API 목록

보드의 기능에서 필요한 API 를 뽑은 것이다. 4절에 자세히 적은 것은 첫째 줄 하나다. 나머지의 경로와 모양은 그 기능을 만드는 작업 전에 이 문서와 규격 파일에 먼저 적는다.

## 4. 시점 조회

개체 하나의 관계 가운데 조회 시점에 유효한 것을 돌려준다. core 의 `RelationQuery.relationsAsOf` 를 그대로 연다. [보드 CORE-03] [D3 5절]

### 요청

```
GET /api/v1/relations?entityId={개체의 id}&asOf={조회 시점}&offset={건너뛸 수}&limit={한 번에 받을 수}
```

[AD-78]

| 항목 | 반드시 | 뜻 | 근거 |
|---|---|---|---|
| `entityId` | 예 | 개체의 `id` | [AD-65] |
| `asOf` | 아니오 | 조회 시점. 없으면 오늘 | [AD-23] [AD-40] |
| `offset`, `limit` | 아니오 | 나눠 주기 (2절). 없으면 0 과 50 | [AD-347] |

### 응답 (200)

```json
{
  "asOf": "2026-03-01",
  "entityId": "p|T|ga",
  "total": 1,
  "offset": 0,
  "limit": 50,
  "relations": [
    {
      "id": "p|T|ga|T|na|R|src|1|2026-03-01",
      "relationType": "R",
      "sourceEntityId": "p|T|ga",
      "targetEntityId": "p|T|na",
      "validFrom": "2026-03-01",
      "validTo": "2026-06-01",
      "provenance": { "inputSourceId": "src", "editionNo": 1 },
      "recordedAt": "2026-01-01T00:00:00Z"
    }
  ]
}
```

항목의 이름과 묶음은 제안이다. 값은 지어낸 것이다.

- `asOf`: 답에 쓴 날짜. 반드시 있다. [AD-23]
- `relations`: 조회 시점에 유효한 관계. 개체가 출발 쪽이든 도착 쪽이든 들어 있다. 유효한 것이 없으면 빈 목록이다. [AD-29] [D3 5절]
- `total`: 조회 시점에 유효한 관계의 전체 수. `relations` 는 그 가운데 `offset` 부터 `limit` 개까지다 (2절 "나눠 주기"). [AD-347]
- **순서**: 관계 유형, 상대 개체의 `id`, 관계의 `id` 차례이고 모두 글자 코드 순이다. [AD-38]
- 관계마다 유효기간, 출처(입력 자료와 판), 기록한 때가 들어 있다. [AD-30] [AD-31]
- 유효기간은 시작일 포함, 종료일 제외다. `validTo` 가 조회 시점과 같은 관계는 들어 있지 않다. [D3 4절]
- 출처가 달라 겹쳐 저장된 관계는 둘 다 들어 있다. [D3 3절] 하나로 합쳐 보여 줄지는 "결정 필요" 4번.
- **개체는 유형, 키, 표시 이름과 함께 준다** (2절 "개체"). 관계마다 `source` 와 `target` 이 있다. 표시 이름은 조회 시점의 값이다. `sourceEntityId` 와 `targetEntityId` 는 그대로 있다. [AD-326] [AD-349]

### 오류

| 상황 | HTTP 상태 | `code` (제안) | 근거 |
|---|---|---|---|
| `entityId` 가 없음 | 400 | `MISSING_ENTITY_ID` | [C 8절] |
| `asOf` 의 형식이 틀림, 받는 범위(0001 ~ 9999년) 밖 | 400 | `INVALID_AS_OF` | [보드 CORE-03] [AD-370] |
| `entityId` 에 쓸 수 없는 글자가 있음 (NUL, 깨진 글자) | 400 | `INVALID_ENTITY_ID` | [AD-370] |
| `offset`, `limit` 의 값이 틀림 (2절 "나눠 주기") | 400 | `INVALID_OFFSET`, `INVALID_LIMIT` | [AD-347] |
| 그런 개체가 없음 | 404 | `ENTITY_NOT_FOUND` | [보드 CORE-02] |
| 로그인하지 않음, 권한이 없음 | 401, 403 | 2절. 뼈대 단계에는 확인하지 않는다 | [api] [AD-80] |

### 규격

`docs/api/openapi.yaml` 의 `getRelationsAsOf` 가 이 API 의 규격이다. 항목의 형식은 그 파일을 본다.

### 관계 지도

개체 하나를 가운데 두고, 조회 시점에 유효한 관계로 이어진 이웃을 노드와 간선으로 돌려준다. 관계 지도 화면이 쓴다. core 의 `RelationMapQuery.relationMap` 을 연다. [보드 CORE-05] [D3 5절] [AD-352]

```
GET /api/v1/relation-map?entityId={가운데 개체의 id}&asOf={조회 시점}&depth={깊이}
```

| 항목 | 반드시 | 뜻 | 근거 |
|---|---|---|---|
| `entityId` | 예 | 가운데 개체의 `id` | [AD-65] [AD-352] |
| `asOf` | 아니오 | 조회 시점. 없으면 오늘 | [AD-23] [AD-40] |
| `depth` | 아니오 | 가운데 개체에서 따라갈 관계의 수. 없으면 1, 많아야 3 | [AD-352] |

```json
{
  "asOf": "2026-03-01",
  "centerEntityId": "p|T|ga",
  "depth": 1,
  "reachedDepth": 1,
  "maxNodes": 200,
  "totalNodes": 2,
  "truncated": false,
  "nodes": [
    { "entityId": "p|T|ga", "entity": { "entityId": "p|T|ga", "entityType": "T", "entityTypeLabel": "유형", "entityKey": "ga", "displayName": "가" }, "depth": 0 },
    { "entityId": "p|T|na", "entity": { "entityId": "p|T|na", "entityType": "T", "entityTypeLabel": "유형", "entityKey": "na", "displayName": null }, "depth": 1 }
  ],
  "edges": [
    {
      "id": "p|T|ga|T|na|R|src|1|2026-03-01",
      "relationType": "R",
      "sourceEntityId": "p|T|ga",
      "targetEntityId": "p|T|na",
      "validFrom": "2026-03-01",
      "validTo": null,
      "provenance": { "inputSourceId": "src", "editionNo": 1 },
      "recordedAt": "2026-01-01T00:00:00Z"
    }
  ]
}
```

값은 지어낸 것이다.

- **지도 하나는 개체 하나의 둘레다.** Pack 전체를 한 번에 주지 않는다. 화면은 노드를 누르면 그 개체를 가운데로 다시 받는다. [AD-352]
- **방향과 무관하게 따라간다.** 들어오는 관계와 나가는 관계를 모두 따라간다. Pack 이 정한 영향 방향을 보지 않는다: 영향이 퍼지는 쪽만 보는 것은 영향 범위(6절)다. 간선에는 관계에 적힌 방향(`sourceEntityId` 에서 `targetEntityId` 로)이 그대로 있다. [AD-352]
- **깊이**: 노드의 `depth` 는 가운데 개체에서 건넌 관계의 수 가운데 가장 작은 것이다. 가운데 개체는 0 이다. `depth` 를 적지 않으면 1 까지, 많아야 3 까지 따라간다. [AD-352]
- **한도**: 노드는 가운데 개체를 넣어 200개까지 담는다 (`maxNodes`). 넘으면 가까운 것부터(아래의 순서) 200개만 담고 `truncated` 가 `true` 다. 같은 깊이 안에서는 유형의 이름 순으로 남는다: 순서를 정하려는 것이고 뜻이 있는 순서가 아니다. 화면은 잘렸다고 알린다. 나머지를 이어 받는 길은 없다: 보려는 쪽의 노드를 가운데로 다시 받는다. 한도는 설치 설정이 아니라 이 계약의 값이다. [AD-352]
- **한도를 넘은 단계에서 멈춘다** [AD-357]: 가까운 단계부터 따라가다가 찾은 노드가 200개를 넘으면 더 깊이 따라가지 않는다. `reachedDepth` 가 따라간 깊이다 (멈추지 않았으면 `depth` 와 같다). 가까운 것부터 담으므로 담기는 노드와 간선은 끝까지 따라갔을 때와 같다. `totalNodes` 는 `reachedDepth` 까지 찾은 수다: `reachedDepth` 가 `depth` 보다 작으면 청한 깊이 안의 전체가 아니라 멈춘 데까지의 수다. 멈춘 깊이 너머에 이어진 것이 더 있는지는 서버도 모른다 (읽지 않았다): 마침 거기가 끝이어도 `reachedDepth` 는 멈춘 깊이다. 화면은 어느 깊이에서 멈췄는지를 함께 알린다. 서버는 한도를 넘은 단계까지만 읽는다 (그 단계는 끝까지 읽는다: 개체 200개 이하에 닿은 관계 모두). 관계 200만의 자료에서 깊이 3 이 5초쯤에서 0.35초가 됐다 (D9 의 A-06).
- **노드의 순서**: 깊이, 개체 유형, 개체의 `id` 차례이고 글자 코드 순이다. 가운데 개체가 맨 앞이다. [AD-352]
- **간선**: 조회 시점에 유효한 관계 가운데 두 끝이 모두 `nodes` 에 있는 것이다. 같은 깊이의 노드 사이의 관계도 들어 있다. 잘린 노드에 닿는 관계는 없다. 순서는 관계 유형, 출발 개체의 `id`, 도착 개체의 `id`, 관계의 `id` 차례이고 글자 코드 순이다. 출처가 달라 겹쳐 저장된 관계는 간선 둘이다 [AD-308]. 간선의 수에는 한도가 없다. [AD-370]
- 유효기간은 시작일 포함, 종료일 제외다. 조회 시점에 유효하지 않은 관계는 따라가지도 않고 간선으로 주지도 않는다. [D3 4절]
- **개체는 유형, 키, 표시 이름과 함께 준다** (2절 "개체"). 노드마다 `entity` 가 있다. 표시 이름은 조회 시점의 값이다. 간선에는 두 끝의 `id` 만 있다: 개체는 노드에서 찾는다. [AD-349]
- 나눠 주지 않는다 (`offset`, `limit` 이 없다). 한도가 답의 크기를 막는다.

| 상황 | HTTP 상태 | `code` | 근거 |
|---|---|---|---|
| `entityId` 가 없음 | 400 | `MISSING_ENTITY_ID` | 시점 조회와 같다 |
| `asOf` 의 형식이 틀림, 받는 범위 밖 | 400 | `INVALID_AS_OF` | 시점 조회와 같다 |
| `entityId` 에 쓸 수 없는 글자가 있음 | 400 | `INVALID_ENTITY_ID` | 시점 조회와 같다 [AD-370] |
| `depth` 가 1 부터 3 까지의 정수가 아님 | 400 | `INVALID_DEPTH` | [AD-352] |
| 그런 개체가 없음 | 404 | `ENTITY_NOT_FOUND` | 시점 조회와 같다 |
| 로그인하지 않음, 권한이 없음 | 401, 403 | 2절 | |

화면: 관계 지도 화면(`/relations`, D-08)이 이 API 로 지도를 그리고 시점 조회 API 로 그 아래의 관계 목록을 보여 준다. 지도를 먼저 받고 서버가 답한 `asOf` 로 목록을 받는다: 조회 시점을 비워도 둘이 같은 날짜를 본다. 시점 막대는 그 `asOf` 의 앞뒤 1년을 하루 단위로 민다 [AD-353]. 지도는 2D 와 3D 로 바꿔 볼 수 있다: 같은 답을 그린다 [AD-361].

규격은 `docs/api/openapi.yaml` 의 `getRelationMap` 이다. 감사 기록에는 `getRelationMap` 으로, 가운데 개체의 `id` 와 조회 시점과 함께 남는다 (2절).

## 5. 판 올리기

파일 하나를 입력 자료의 새 판으로 올린다. 받아들인 판은 앞 판과 비교해 바뀐 항목(변동)을 찾고, 이어서 변동마다 영향 범위를 계산해 조치를 만들어 저장한다. 응답이 오면 그 판의 조치가 만들어져 있다. [AD-234] api 의 서비스(`EditionProcessing`)를 그대로 연다. [AD-233] [AD-237]

- 한 Pack 에서는 한 번에 하나만 처리한다. 뒤에 온 요청은 앞의 것이 끝날 때까지 기다린다. [AD-235] 그 Pack 의 재적재도 같은 차례를 쓴다 (10절). [AD-331]
- 담당자와 관리자가 부를 수 있다. [AD-240]
- 지난 판의 변동을 다시 보는 조회 API 는 아직 없다. 바뀐 항목은 올린 응답에 담아 준다. [AD-237]

### 요청

```
POST /api/v1/editions
Content-Type: multipart/form-data
```

[AD-238]

| 항목 | 반드시 | 뜻 | 근거 |
|---|---|---|---|
| `packId` | 예 | Pack 의 식별자 | [AD-74] |
| `inputSourceId` | 예 | 입력 자료의 식별자. 그 Pack 의 매핑 가운데 하나 | [AD-41] |
| `effectiveDate` | 예 | 판의 적용일. `2026-03-01` 모양 | [AD-42] |
| `file` | 예 | 올리는 파일. 파일의 이름은 기록에 남긴다 (폴더 부분은 뗀다) | [AD-84] |

- 식별자는 주소에 넣지 않고 폼의 항목으로 받는다. [AD-78]
- 파일 크기의 한도는 설치 설정 `spring.servlet.multipart.max-file-size` 하나로 정한다. 기본은 20MB 다. 요청 전체의 한도(`max-request-size`)는 그보다 조금 크게 둔다. 한도를 넘는 파일은 서버가 본문을 다 읽기 전에 거부한다 (413). 이 경우는 투입 기록에 남지 않는다. (구현하면서 정한 것, "결정 필요" 8번)

```json
  "packId": "p",
  "inputSourceId": "src",

  "changes": [
    {
      "changeEventId": "p|src|2|ga",
      "itemKey": "ga",
      "kind": "CHANGED",
      "primaryEntityId": "p|T|ga",
      "targetEntityIds": ["p|T|ga"],
      "changedValues": [
        { "entityId": "p|T|ga", "attributeName": "limit", "attributeLabel": "한도", "before": "0.8", "after": "0.7" }
      ],
      "processing": { "status": "PROCESSED", "failedStage": null, "failureCode": null, "failures": [], "actionCount": 2 }
    }
  ],
  "notices": [],
  "retriedChanges": [],
  "processingNotStarted": false
}
```

항목의 이름과 묶음은 제안이다. 값은 지어낸 것이다.

- `outcome`: `ACCEPTED` 는 새 판을 만들었다. `UNCHANGED` 는 내용이 바로 앞 판과 같아 판을 만들지 않았다 [AD-155]: 이때 `editionId`, `editionNo`, `effectiveDate` 는 그 앞 판의 것이고 `changes` 와 `notices` 는 비어 있다.
- `changes`: 앞 판과 비교해 바뀐 항목. **순서**는 항목의 키의 글자 코드 순이다. 첫 판이면 비어 있다. [AD-148] [AD-122]
- `changes[].changedValues`: 그 행에서 바뀐 속성 값. 속성마다 이전 값(`before`)과 새 값(`after`)이다. 값은 저장한 글자 그대로다 (2절 "값의 표기"). 변경된 행은 두 판에서 그 행이 만든 것이 다른 속성 값이고 (값은 같고 유효기간만 달라진 것도 들어간다: 두 값이 같다), 추가된 행은 넣은 것 전부이며 `before` 가 null, 삭제된 행은 넣었던 것 전부이며 `after` 가 null 이다. `attributeLabel` 은 Pack 이 정한 속성의 이름표다: 없으면 속성의 이름이다. **순서**는 개체의 `id`, 속성의 이름의 글자 코드 순이다. **이전 값을 알 수 없으면 목록 전체가 null 이다** (바뀐 값을 남기기 전에 들어간 판과 견준 변동): 빈 목록은 바뀐 속성 값이 없다는 뜻이고 null 은 모른다는 뜻이다. 바뀐 관계는 여기에 없다. [AD-367] [AD-291]
- `changes[].processing`: 그 변동을 조치까지 처리한 결과. `PROCESSED` 는 영향 범위와 조치를 저장했다. `FAILED` 는 실패했고 (단계와 이유의 코드, 평가에 실패한 규칙의 목록 `failures` 가 붙는다) 다음에 받아들여진 판을 올릴 때, 또는 관리자가 다시 처리할 때 다시 시도된다 (아래 "처리되지 않은 변동과 다시 처리"). `PENDING` 은 아직 처리하지 못했다. 변동 하나가 실패해도 나머지는 처리된다. [AD-236]
- `notices`: 투입의 알림 (건너뛴 행 등). 종류와 이유의 코드와 값, 그리고 그것을 풀어 쓴 한국어 문구 `message` 가 있다. **순서**는 행 번호, 종류, 코드, 내용 순이다. [AD-153]
- **알림의 문구** (`notices[].message`): 몇 번째 행의 어느 열(또는 어느 개체의 어느 속성)이 왜 걸렸는지와 무엇을 하면 되는지를 적는다. 문구는 거부의 문구와 같이 api 가 코드마다 가진다. 문구를 따로 두지 않은 코드는 코드와 값을 그대로 넣은 문구로 낸다. 화면이 가르는 데는 `kind` 와 `code` 를 쓴다: 문구는 바뀔 수 있다. 문구는 저장하지 않고 응답을 만들 때 만든다. [AD-326] [AD-348]
- `retriedChanges`: 이 요청이 함께 다시 처리한, 앞선 판의 변동. 전에 실패해 남아 있던 것이다. **순서**는 처리한 차례다. [AD-207] [AD-234]
- `processingNotStarted`: 판은 받아들였지만 변동의 처리를 시작하지 못했다. 드문 일이다 (저장소 오류).
- 조치의 내용과 영향 범위는 이 응답에 없다. 조치를 보는 API 에서 준다 (뒤에).

### 처리되지 않은 변동과 다시 처리

변동의 처리(영향 범위 계산, 규칙 실행)가 실패하면 그 변동은 실패로 남는다. 무엇이 왜 실패했는지를 보고, 고친 뒤에 관리자가 다시 처리한다. [AD-321] [AD-345]

```
GET /api/v1/unprocessed-changes?packId=p
```

```json
{
  "packId": "p",
  "changes": [
    {
      "changeEventId": "p|guideline|2|G-1", "editionId": "p|guideline|2", "inputSourceId": "guideline",
      "editionNo": 2, "effectiveDate": "2026-03-01", "itemKey": "G-1", "kind": "CHANGED",
      "primaryEntityId": "p|Guideline|G-1",
      "processing": {
        "status": "FAILED", "failedStage": "RULES", "failureCode": "RULE_FAILED", "actionCount": 0,
        "failures": [ { "ruleNo": "0001", "code": "DUE_DATE_OUT_OF_RANGE", "entityId": null, "attributeName": null, "value": "2147483647" } ]
      }
    }
  ]
}
```

- 그 Pack 의 처리되지 않은 변동(실패 `FAILED`, 대기 `PENDING`)만 나온다. 처리된 변동은 나오지 않는다. **순서**는 처리하는 차례다: 판을 받은 차례, 그 안에서는 항목의 키의 글자 코드 순. [AD-207] 쪽 나누기는 없다 (2절의 규칙과 같다).
- **실패의 까닭**: `failedStage` (어느 단계), `failureCode` (이유의 코드), `failures` (평가에 실패한 규칙마다 한 줄: 규칙 번호, 코드, 걸린 개체와 속성과 값). `failures` 는 규칙이 평가에 실패했을 때(`RULE_FAILED`)만 있고 규칙 번호 순이다. 그 밖의 실패(저장소 오류, 정의와 자료가 어긋난 것 등)는 단계와 코드뿐이다: **문구는 저장하지도 내보내지도 않는다.** 화면이 코드마다 정해 둔 안내문을 보여 주고, 내부의 오류 문구는 서버의 기록에만 남는다. [AD-345]
- 판 올리기의 응답의 `processing` 에도 같은 `failures` 가 붙는다.
- `packId` 가 빠졌거나 빈칸뿐이면 400 `MISSING_PACK_ID`, 그런 Pack 이 없으면 404 `PACK_NOT_FOUND` 다. 다시 처리도 같다.
- 변동 이벤트와 그 까닭은 한 시점의 것으로 함께 읽는다. 다시 처리가 도는 중에 읽어도 상태와 까닭이 서로 어긋나지 않는다. 읽기는 처리를 기다리지 않는다.

```
POST /api/v1/change-reprocessings
Content-Type: application/json
X-XSRF-TOKEN: (XSRF-TOKEN 쿠키의 값)

{ "packId": "p" }
```

```json
{ "packId": "p", "processedCount": 1, "failedCount": 0, "changes": [ { "changeEventId": "p|guideline|2|G-1", "editionId": "p|guideline|2", "itemKey": "G-1",
    "processing": { "status": "PROCESSED", "failedStage": null, "failureCode": null, "failures": [], "actionCount": 2 } } ] }
```

- **관리자만 부를 수 있다.** 담당자가 부르면 403 `FORBIDDEN` 이다. [AD-321]
- 그 Pack 의 처리되지 않은 변동을 모두, 처리하는 차례로, 지금의 자료와 지금의 규칙으로 처음부터 다시 계산한다. [AD-154] 변동을 골라서 다시 처리하지는 않는다: 차례가 결과에 닿는다. 변동 하나가 다시 실패해도 나머지는 처리한다. [AD-236]
- `changes` 는 이 요청이 다시 처리한 것과 그 결과다. `processedCount` 와 `failedCount` 는 그 가운데 처리된 것과 다시 실패한 것의 수다 (화면이 세지 않게 서버가 준다). 처리할 것이 없었으면 빈 목록이고 200 이다. 결과를 표시하지 못한 변동(드문 일: 저장소 오류)은 넣지 않는다: 상태가 바뀌지 않았다.
- 같은 Pack 의 판 올리기와 다시 처리는 한 번에 하나만 한다. 뒤에 온 것이 기다린다. [AD-235]
- 감사 기록에 남는다 (`reprocessChanges`, 대상 `packId`, 다시 처리한 수와 처리된 수).
- 규격은 `listUnprocessedChanges`, `reprocessChanges` 다.

## 6. 조치와 그 근거 보기

저장된 조치와, 그 조치를 낳은 변동의 영향 범위를 읽는다. rules 의 `ActionRecords` 를 연다. 화면(web)은 아직 잇지 않았다. [AD-241]

- 조치와 영향 범위는 판을 올린 직후에 그때의 자료로 한 번 계산해 저장한 것이다. 뒤에 자료나 규칙이 바뀌어도 달라지지 않는다. [AD-119] [AD-226]
- 담당자와 관리자가 부를 수 있다.
- 개체(조치의 대상, 근거가 되는 주 개체)는 `id`, 유형, 유형의 이름표, 키, 표시 이름으로 준다 (2절 "개체"). 표시 이름은 **그 변동이 나온 판의 적용일**의 값이다: 보는 날에 따라 달라지지 않는다. [AD-244] [AD-326] [AD-349]

### 조치 목록

```
GET /api/v1/actions?packId={Pack 의 식별자}&status={상태}&changeEventId={변동 이벤트의 id}
```

| 항목 | 반드시 | 뜻 | 근거 |
|---|---|---|---|
| `packId` | 예 | Pack 의 식별자 | [AD-74] |
| `status` | 아니오 | `PENDING`, `CONFIRMED`, `ON_HOLD` 가운데 하나. 없으면 가리지 않는다 | [AD-242] [AD-47] |
| `changeEventId` | 아니오 | 이 변동 이벤트에서 나온 조치만. 없으면 가리지 않는다 | [AD-60] |

```json
{
  "packId": "p",
  "status": "PENDING",
  "changeEventId": null,
  "total": 1,
  "actions": [
    {
      "id": "p\\|src\\|2\\|ga|0001|p\\|T\\|na",
      "changeEventId": "p|src|2|ga",
      "ruleNo": "0001",
      "ruleLabel": "규칙의 이름",
      "actionText": "해야 할 일",
      "priority": 1,
      "dueDate": "2026-03-15",
      "status": "PENDING",
      "appliesTo": "IMPACT_TARGET",
      "target": { "entityId": "p|T|na", "entityType": "T" },
      "basis": {
        "entity": { "entityId": "p|T|ga", "entityType": "T" },
        "inputSourceId": "src",
        "editionNo": 2,
        "effectiveDate": "2026-03-01"
      },
      "createdAt": "2026-03-01T00:00:00Z"
    }
  ]
}
```

항목의 이름과 묶음은 제안이다. 값은 지어낸 것이다.

- **거른 조치를 나눠 준다** (2절 "나눠 주기"). `total` 은 거른 조치의 전체 수다. [AD-310] [AD-347]
- **순서**: 기한이 이른 것부터. 같으면 우선순위(수가 작은 것부터), 규칙 번호, 대상 개체의 `id`, 조치의 `id` 차례이고 글자는 모두 글자 코드 순이다. 변동 하나로 걸러도 같은 기준이다. [AD-243]
- `basis`: 근거 조항(변동이 생긴 행의 주 개체)과, 그 변동이 나온 입력 자료의 판. 반드시 있다. [AD-04] [AD-229] [AD-98]
- `ruleLabel`, `actionText`, `priority`, `dueDate` 는 조치를 만들 때의 값이다. 뒤에 규칙을 고쳐도 바뀌지 않는다. [AD-226]
- `appliesTo` 가 `IMPACT_TARGET` 인 조치는 그 변동의 영향 범위(아래)에 대상의 근거 경로가 있다. `CHANGE_TARGET` 인 조치는 대상이 바뀐 개체 자신이라 근거 경로가 없다. [AD-102] [AD-211]
- 서로 다른 변동이 같은 대상에 같은 규칙을 걸면 조치가 각각 나온다. 묶어 보여 주는 일은 화면의 몫이다. [AD-60] (D8 "결정 필요" 3번)
- 해당하는 것이 없으면 빈 목록이다. 그 Pack 의 것이 아닌 변동 이벤트로 거른 것도 빈 목록이다 (다른 Pack 의 조치를 주지 않는다).

| 상황 | HTTP 상태 | `code` (제안) |
|---|---|---|
| `packId` 가 없음 | 400 | `MISSING_PACK_ID` |
| `status` 가 셋 가운데 하나가 아님 | 400 | `INVALID_STATUS` |
| `changeEventId` 항목이 있는데 값이 비었거나 쓸 수 없는 글자가 있음 | 400 | `INVALID_CHANGE_EVENT_ID` |
| `offset`, `limit` 의 값이 틀림 (2절 "나눠 주기") | 400 | `INVALID_OFFSET`, `INVALID_LIMIT` |
| 그런 Pack 이 없음 | 404 | `PACK_NOT_FOUND` |

### 변동의 영향 범위

```
GET /api/v1/impact-scopes?changeEventId={변동 이벤트의 id}&entityId={영향 대상의 id}&offset={건너뛸 수}&limit={한 번에 받을 수}
```

```json
{
  "changeEventId": "p|src|2|ga",
  "packId": "p",
  "asOfPrevious": "2026-02-28",
  "asOfEffective": "2026-03-01",
  "maxDepth": 3,
  "truncated": false,
  "storedAt": "2026-03-01T00:00:00Z",
  "total": 1,
  "offset": 0,
  "limit": 50,
  "countsByType": [ { "entityType": "T", "count": 1 } ],
  "countsByDepth": [ { "depth": 1, "count": 1 } ],
  "targets": [
    {
      "entityId": "p|T|na",
      "entityType": "T",
      "depth": 1,
      "path": {
        "startEntityId": "p|T|ga",
        "asOf": "2026-03-01",
        "steps": [
          { "stepNo": 1, "relationId": "p|T|ga|T|na|R|src|1|2026-01-01", "relationType": "R", "sourceEntityId": "p|T|ga", "targetEntityId": "p|T|na" }
        ]
      }
    }
  ]
}
```

- **두 날짜로 본 것이다.** 판의 적용일 전날(`asOfPrevious`)과 적용일(`asOfEffective`)의 관계로 각각 따라가 합쳤다. 경로마다 어느 날짜의 관계로 닿았는지가 `path.asOf` 에 있다: 전날이면 그 판에서 없어진 관계로 닿은 것이다. [AD-100] [AD-116] 조회 시점 하나로 보는 영향 범위(아직 없다)와는 다른 API 다. (D8 "결정 필요" 6번의 한 부분)
- **순서**: 영향 대상은 깊이, 개체 유형, 개체의 `id` 차례. `countsByType` 은 개체 유형의 글자 코드 순, `countsByDepth` 는 깊이 순. 경로의 단계는 변동 대상 쪽부터. [AD-61] [AD-36]
- `total` 과 두 수의 합계는 영향 대상의 수와 같다. 변동 대상 자신은 세지 않는다. 수는 서버가 센다 (rules). [AD-63] [AD-34] [AD-21]
- **영향 대상을 나눠 준다** (2절 "나눠 주기"). `targets` 는 `offset` 부터 `limit` 개까지다. `total`, `countsByType`, `countsByDepth` 는 나누기 전의 영향 범위 전체의 값이다. [AD-347]
- **대상 하나만 묻기**: `entityId` 를 주면 그 개체인 영향 대상만 준다 (많아야 하나). 조치의 근거 경로를 찾을 때 쓴다. 그 개체가 영향 대상이 아니면 `targets` 는 빈 목록이고 200 이다. `total` 과 두 수는 거르지 않은 값 그대로다. `entityId` 가 비어 있으면 400 `MISSING_ENTITY_ID`, 쓸 수 없는 글자가 있으면 400 `INVALID_ENTITY_ID` 다. [AD-347]
- 영향 대상마다 근거 경로가 반드시 있다. 단계의 수는 깊이와 같다. [AD-04]
- 영향 대상(`entity`), 경로가 시작한 변동 대상(`path.start`), 단계의 출발과 도착(`source`, `target`)을 유형, 키, 표시 이름과 함께 준다 (2절 "개체"). 표시 이름은 판의 적용일(`asOfEffective`)의 값이다: 전날의 관계로 닿은 경로의 개체도 적용일의 값으로 보인다 (그 판에서 없어진 개체는 값이 없어 키로 보일 수 있다). 식별자 항목은 그대로 있다. [AD-349]
- 단계의 출발과 도착은 그 관계에 적힌 방향이다. 따라간 방향이 아니다. 관계의 내용은 계산할 때의 값이다. [AD-212]
- `truncated`: 최대 깊이에서 멈췄고 그 너머에 아직 찾지 못한 대상이 있다. [AD-62] [AD-117]
- 화면: 영향 범위 화면(`/impact?changeEventId=…`, D-03)이 이 API 의 값을 그대로 보여 준다. 변동 감지 화면과 조치 화면에서 이어 온다 [AD-365].
- 영향 범위는 변동 이벤트의 `id` 만으로 읽는다. Pack 으로 거르지 않는다 (응답에 `packId` 가 있다). 로그인을 붙일 때 Pack 단위의 접근 범위와 함께 다시 본다.

| 상황 | HTTP 상태 | `code` (제안) |
|---|---|---|
| `changeEventId` 가 없음 | 400 | `MISSING_CHANGE_EVENT_ID` |
| `changeEventId` 에 쓸 수 없는 글자가 있음 | 400 | `INVALID_CHANGE_EVENT_ID` |
| `entityId` 항목이 있는데 값이 비었음, 쓸 수 없는 글자가 있음 | 400 | `MISSING_ENTITY_ID`, `INVALID_ENTITY_ID` |
| `offset`, `limit` 의 값이 틀림 (2절 "나눠 주기") | 400 | `INVALID_OFFSET`, `INVALID_LIMIT` |
| 그 변동 이벤트의 저장된 영향 범위가 없음 (없는 변동, 아직 처리되지 않았거나 처리에 실패한 변동) | 404 | `IMPACT_SCOPE_NOT_FOUND` |

### 규격

`docs/api/openapi.yaml` 의 `listActions` 와 `getChangeImpactScope` 가 이 API 들의 규격이다.

## 7. 확정과 보류

조치를 확정하거나 보류하고, 조치 하나를 그 이력과 함께 읽는다. rules 의 `ActionDecisions` 와 `ActionRecords` 를 연다. 화면(web)은 아직 잇지 않았다. [AD-250]

- 상태는 대기에서 확정이나 보류로, 보류에서 확정으로만 바뀐다. 확정은 되돌릴 수 없다. [AD-47]
- **누가 했는지와 언제 했는지는 요청에서 받지 않는다.** 서버가 채운다: 누가는 로그인한 사람, 언제는 서버의 시각이다. [AD-251]
- 누가 했는지는 로그인한 사람의 아이디다 (9절). 로그인이 붙기 전에 쓰던 임시 아이디의 설정(`tabnit.interim-actor`)은 없앴다 (E-02). 그 전에 개발 환경에서 남긴 이력에는 임시 아이디(`dev`)가 적혀 있을 수 있다. [AD-251] [AD-269] [AD-80]
- 확정과 보류, 조치와 이력을 읽는 것은 담당자와 관리자가 한다. [AD-270]

### 조치 하나와 이력

```
GET /api/v1/action?actionId={조치의 id}
```

```json
{
  "action": { "id": "…", "status": "CONFIRMED", "…": "조치 목록의 조치와 같은 모양 (6절)" },
  "history": [
    { "seq": 1, "fromStatus": "PENDING", "toStatus": "ON_HOLD", "decidedBy": "officer-1", "decidedAt": "2026-03-02T01:00:00Z", "note": "담당 부서의 답을 기다린다" },
    { "seq": 2, "fromStatus": "ON_HOLD", "toStatus": "CONFIRMED", "decidedBy": "officer-2", "decidedAt": "2026-03-03T01:00:00Z", "note": null }
  ]
}
```

- `action`: 조치 목록(6절)의 조치와 같은 모양이다.
- `history`: 그 조치의 이력. **순서**는 상태를 바꾼 차례(`seq`)다. 시각의 순이 아니다. 아직 아무도 바꾸지 않았으면 빈 목록이다. 조치 목록에는 이력을 담지 않는다. [AD-254]
- `note` 가 없으면 `null` 로 적는다. 항목을 빼지 않는다.

| 상황 | HTTP 상태 | `code` (제안) |
|---|---|---|
| `actionId` 가 없음 | 400 | `MISSING_ACTION_ID` |
| `actionId` 에 쓸 수 없는 글자가 있음 | 400 | `INVALID_ACTION_ID` |
| 그런 조치가 없음 | 404 | `ACTION_NOT_FOUND` |

### 확정과 보류

```
POST /api/v1/action-decisions
Content-Type: application/json

{ "actionId": "…", "decision": "HOLD", "note": "담당 부서의 답을 기다린다" }
```

[AD-252]

| 항목 | 반드시 | 뜻 | 근거 |
|---|---|---|---|
| `actionId` | 예 | 조치의 `id` | [AD-60] |
| `decision` | 예 | `CONFIRM` 확정, `HOLD` 보류 | [AD-47] |
| `note` | 보류에는 예 | 사유. 1,000자까지. 눈에 보이는 글자가 없으면 없는 것으로 본다 | [AD-247] |

- 응답(200)은 "조치 하나와 이력"과 같은 모양이다: 바뀐 조치와 그 이력. 이력의 마지막 줄이 방금 한 것이다.
- 요청에 다른 항목(누가, 언제 등)이 있어도 쓰지 않는다.
- 한 요청이 조치 하나의 상태를 한 번 바꾼다. 이력 한 줄이 는다. 상태와 이력은 함께 바뀐다. [AD-248] 같은 사람이 같은 동작을 다시 보낸 것만 예외다: 아무것도 바뀌지 않고 이력도 늘지 않는다 (아래). [AD-325]

| 상황 | HTTP 상태 | `code` (제안) |
|---|---|---|
| 본문이 JSON 이 아니거나 읽을 수 없음 | 400 | `INVALID_BODY` |
| `actionId` 가 없음, 쓸 수 없는 글자가 있음 | 400 | `MISSING_ACTION_ID`, `INVALID_ACTION_ID` |
| `decision` 이 없음, 둘 가운데 하나가 아님 | 400 | `MISSING_DECISION`, `INVALID_DECISION` |
| 사유가 틀림 (보류인데 없음, 너무 김, 쓸 수 없는 글자) | 400 | `INVALID_NOTE` |
| 그런 조치가 없음 | 404 | `ACTION_NOT_FOUND` |
| **지금의 상태에서는 그렇게 바꿀 수 없음** | 409 | `ACTION_DECISION_CONFLICT` |

- **거부(409)** 는 공통 오류 형식에 `currentStatus` (조치의 지금 상태)와 `lastDecision` (마지막 이력: 누가 언제 지금의 상태로 바꿨는가)을 더해 담는다. 아무것도 바뀌지 않았다. [AD-253] [AD-248]
- **같은 사람이 같은 동작을 다시 보내면 성공(200)으로 답한다.** 조치의 지금 상태가 그 동작의 것이고(확정이면 확정됨, 보류이면 보류됨) 그 상태로 바꾼 마지막 이력이 요청한 사람의 것이면, 아무것도 바꾸지 않고 지금의 조치와 이력을 돌려준다. 새 이력은 남지 않고, 다시 보낸 요청의 사유는 버려진다: 처음 것이 남는다. 응답을 받지 못해 다시 누른 담당자에게 성공한 일이 실패로 보이지 않게 한다. 다시 보낸 요청도 입력은 그대로 확인한다: 사유 없는 보류나 너무 긴 사유는 400 이다. 다시 보낸 것으로 보는 데 시간의 한도는 없다: 며칠 뒤에 사유를 고치려고 같은 보류를 보내도 처음 사유가 남는다 (사유를 고치는 기능은 없다). 감사 기록에는 두 요청이 모두 성공으로 남는다: 감사 기록만으로는 다시 보낸 것인지 가릴 수 없고, 조치의 이력(한 줄)과 맞춰 보면 안다. [AD-325]
- 다른 사람이 먼저 바꿨을 때는 409 다. 화면은 `lastDecision` 으로 누가 했는지를 보여 주고 목록을 고친다. [AD-253]

### 규격

`docs/api/openapi.yaml` 의 `getAction` 과 `decideAction` 이 이 API 들의 규격이다.

## 8. Pack 과 입력 자료의 목록

판을 올릴 때 Pack 과 입력 자료를 고르도록, 적재된 Pack 과 그 입력 자료를 준다. pack 의 `PackDefinitions` 와 link 의 `EditionRecords` 를 연다. [AD-258]

```
GET /api/v1/packs
```

```json
{
  "packs": [
    {
      "packId": "p",
      "label": "Pack 의 이름",
      "inputSources": [
        { "inputSourceId": "src", "fileFormat": "CSV", "latestEdition": { "editionId": "p|src|2", "editionNo": 2, "effectiveDate": "2026-03-01" } },
        { "inputSourceId": "src-2", "fileFormat": "CSV", "latestEdition": null }
      ]
    }
  ]
}
```

- **순서**: Pack 은 Pack 의 `id` 의 글자 코드 순, 입력 자료는 입력 자료의 `id` 의 글자 코드 순이다. [AD-38]
- `inputSources`: 그 Pack 의 매핑이 받는 입력 자료다. [AD-41] 입력 자료에는 이름이 따로 없어 `id` 를 보여 준다.
- `latestEdition`: 그 입력 자료의 가장 새 판 (판 번호가 가장 큰 판). 아직 판이 없으면 `null` 이다. **다음에 올리는 판의 적용일은 이 판의 적용일보다 늦어야 한다.** 화면이 이것을 보여 줘 틀린 적용일을 미리 피하게 한다.
- 적재된 Pack 이 없으면 빈 목록이다. 요청에 받는 항목이 없어 400 과 404 가 없다.
- 담당자와 관리자가 부를 수 있다.

`docs/api/openapi.yaml` 의 `listPacks` 가 이 API 의 규격이다.

## 9. 로그인과 세션

아이디와 비밀번호로 로그인하고, 서버 세션과 쿠키로 로그인한 상태를 유지한다. common 의 `UserAccounts` 가 계정과 로그인을 판단하고, api 가 세션과 HTTP 를 맡는다. [AD-262] [AD-263]

- **로그인하지 않으면 API 를 쓸 수 없다.** 로그인(`POST /api/v1/session`)과 서버의 상태 확인(`/actuator/health`) 말고는 모두 로그인해야 한다. 로그인하지 않은 요청은 401 `UNAUTHENTICATED` 다. 화면의 파일은 로그인 없이 내준다 (화면이 떠야 로그인할 수 있다).
- **화면의 파일은 서버가 함께 내준다** (설치 설정 `tabnit.web-dir` 을 정했을 때. 컨테이너 이미지가 정한다). [AD-277] `/api` 와 `/actuator` 가 아닌 주소 가운데 파일의 이름으로 보이지 않는 것(마지막 마디에 점이 없다)은 화면의 주소로 보고 화면의 첫 파일(`index.html`)로 답한다: 화면의 주소를 새로 고쳐도 화면이 뜬다. [AD-257] 없는 파일과 없는 API 는 404 다.
- **세션**: 서버의 메모리에 둔다. 30분 동안 요청이 없으면 끝난다 (설치 설정 `server.servlet.session.timeout`). 앱을 다시 띄우면 모두 로그아웃된다. [AD-266] 세션 쿠키는 스크립트가 읽지 못하고 (`HttpOnly`), 같은 사이트에서만 보내며 (`SameSite=Strict`), HTTPS 로만 보낸다 (`Secure`). 로그인하면 세션의 식별자를 새로 바꾼다.
- **위조 요청 방어 (CSRF)**: 바꾸는 요청(POST, DELETE 등)에는 서버가 `XSRF-TOKEN` 쿠키로 준 값을 `X-XSRF-TOKEN` 헤더에 실어 보낸다. 없거나 틀리면 403 `FORBIDDEN` 이다. 로그인 요청도 같다. 세션 쿠키의 제한과 두 겹이다. [AD-267]
- **비밀번호**: bcrypt 해시로만 저장하고, 저장된 값의 앞에 방식의 이름을 함께 적는다. 12자 이상, 72바이트 이하. 서버는 비밀번호를 기록에 남기지 않는다. [AD-264]
- **여러 번 틀리면 잠시 막는다**: 같은 아이디로 잇달아 5번 틀리면 15분 동안 그 아이디의 로그인을 막는다 (설치 설정 `tabnit.login.max-failures`, `tabnit.login.lock-duration`). 막힌 동안에는 맞는 비밀번호도 받지 않는다. 시간이 지나면 풀린다. 성공하면 틀린 횟수를 0 으로 되돌린다. [AD-265]
- **역할**: 사용자마다 관리자(`ADMIN`)나 담당자(`OFFICER`)를 적어 둔다. 역할마다 할 수 있는 일은 2절에 있다 (E-06).
- **확정과 보류의 "누가"** 는 로그인한 사람의 아이디다. 임시 아이디의 설정(`tabnit.interim-actor`)은 없앴다. [AD-251]

### 내 정보

```
GET /api/v1/session
```

```json
{ "loginId": "officer-1", "role": "OFFICER", "timeZone": "Asia/Seoul" }
```

로그인하지 않았으면 401 `UNAUTHENTICATED` 다. 화면이 처음 열릴 때 부른다. 이 응답(401 이어도)과 함께 `XSRF-TOKEN` 쿠키가 온다.

- `timeZone`: 설치 설정의 시간대 (`tabnit.time-zone`, 기본 Asia/Seoul). **API 의 시각은 모두 협정 세계시 그대로이고, 화면이 이 시간대로 바꿔 보여 준다.** 서버가 조회 시점의 "오늘"을 정하는 시간대와 같다 (2절). 보는 사람의 브라우저의 시간대를 따르지 않는다: 같은 시각이 누구에게나 같게 보인다. 로그인의 응답에도 같은 항목이 있다. [AD-326] [AD-348]

### 로그인

```
POST /api/v1/session
Content-Type: application/json
X-XSRF-TOKEN: (XSRF-TOKEN 쿠키의 값)

{ "loginId": "officer-1", "password": "…" }
```

성공하면 200 과 내 정보, 그리고 세션 쿠키가 온다.

| 상황 | HTTP 상태 | `code` (제안) |
|---|---|---|
| `loginId` 나 `password` 가 없음 | 400 | `MISSING_LOGIN_ID`, `MISSING_PASSWORD` |
| 본문을 읽을 수 없음 | 400 | `INVALID_BODY` |
| **아이디가 없음, 비밀번호가 틀림, 여러 번 틀려 막힘** | 401 | `LOGIN_FAILED` |
| `X-XSRF-TOKEN` 헤더가 없거나 틀림 | 403 | `FORBIDDEN` |

- **세 경우를 응답으로 가리지 않는다.** 상태, `code`, 문구가 모두 같다. 아이디가 있는지와 막혀 있는지를 알려 주지 않는다. 문구는 세 가능성을 모두 말한다. (구현하면서 정한 것, "결정 필요" 14번)

### 로그아웃

```
DELETE /api/v1/session
X-XSRF-TOKEN: (XSRF-TOKEN 쿠키의 값)
```

세션을 끝내고 204 로 답한다. 로그인하지 않은 채로 불러도 204 다.

### 처음 사용자와 그 뒤의 사용자

사용자를 만드는 화면은 아직 없다 (D-12, 당김 범위). 설치할 때 명령으로 만든다. [AD-268]

```
TABNIT_NEW_USER_PASSWORD='…' java -jar tabnit-api.jar --tabnit.create-user.login-id=admin --tabnit.create-user.role=ADMIN
```

- 아이디와 역할은 실행 인자로, **비밀번호는 환경 변수 `TABNIT_NEW_USER_PASSWORD` 로만** 받는다. 설정 파일이나 실행 인자로는 받지 않는다 (기록에 남는다). 이렇게 띄우면 서버는 HTTP 를 열지 않고 계정 하나를 만든 뒤 바로 끝난다 (떠 있는 서버와 함께 돌려도 된다). 비밀번호를 로그에 적지 않는다. 실패하면 이유를 알리고 0 이 아닌 값으로 끝난다.
- 아이디는 영어 소문자나 숫자로 시작하고 영어 소문자, 숫자, 점, 밑줄, 붙임표만 써서 3자에서 50자다.
- 사용자가 하나도 없으면 아무도 로그인할 수 없다.
- 사용자를 지우는 기능은 아직 없다.

### 로그인 막힘 풀기와 비밀번호 바꾸기

관리자가 서버에서 명령으로 한다. 화면은 없다. 사용자를 만드는 명령과 같은 방식이다: 서버는 HTTP 를 열지 않고 일 하나를 한 뒤 바로 끝난다 (떠 있는 서버와 함께 돌려도 된다). 실패하면 이유를 알리고 0 이 아닌 값으로 끝난다. [AD-320] [AD-346]

```
java -jar tabnit-api.jar --tabnit.unlock-user.login-id=officer1
TABNIT_NEW_USER_PASSWORD='…' java -jar tabnit-api.jar --tabnit.change-password.login-id=officer1
```

- **막힘 풀기**: 그 계정의 막힘을 풀고 틀린 횟수를 처음으로 돌린다. 막혀 있지 않은 계정을 풀어도 된다. 비밀번호와 역할은 바꾸지 않는다.
- **비밀번호 바꾸기**: 새 비밀번호는 환경 변수 `TABNIT_NEW_USER_PASSWORD` 로만 받는다 (만들 때와 같은 변수, 같은 규칙). **막힘도 함께 푼다**: 바꾼 뒤 바로 로그인할 수 있다. 역할은 바꾸지 않는다.
- **이미 로그인된 세션은 끝내지 않는다.** 세션은 떠 있는 서버에 있다. 끝날 때까지(쓰지 않은 채 30분) 유효하다. 비밀번호가 새어 나가 바로 끝내야 하면 서버를 다시 띄운다 (모든 세션이 끝난다).
- 그런 아이디의 계정이 없으면 실패한다.
- 명령으로 띄웠는데 아이디를 읽지 못해 아무 일도 하지 않았으면 (아이디가 비었거나 `false` 다: 설정이 그 명령을 끈 것으로 읽는다) 그 사실을 알리고 0 이 아닌 값으로 끝난다. 사용자를 만드는 명령도 같다. 아이디 `false` 인 계정은 이 명령들로 다룰 수 없다.

### 명령의 감사 기록

세 명령(사용자 만들기, 막힘 풀기, 비밀번호 바꾸기)은 감사 기록에 남는다. [AD-329] [AD-346]

- 요청과 같이 두 줄이다: 하기 전의 줄(`STARTED`)과 결과의 줄(`SUCCESS`, `FAILED`). 하기 전의 줄을 남기지 못하면 하지 않는다.
- `action` 은 `createUser`, `unlockUser`, `changeUserPassword` 다. `target` 은 `loginId=아이디`, `detail` 은 `via=command` (사용자 만들기는 `; role=역할` 이 붙는다). `http_status` 는 없다.
- **누가(`actor`)는 비어 있다.** 명령은 로그인 없이 서버에서 실행한다. 누가 서버에 들어와 실행했는지는 운영체제의 기록이 맡는다.
- 비밀번호는 남지 않는다.

### 규격

`docs/api/openapi.yaml` 의 `getSession`, `login`, `logout` 이 이 API 들의 규격이다.

## 10. Pack 적재

관리자가 서버의 Pack 폴더에 있는 Pack 하나를 적재한다. pack 의 `PackLoader` 를 연다. [AD-271] [AD-272]

```
POST /api/v1/pack-loads
Content-Type: application/json
X-XSRF-TOKEN: (XSRF-TOKEN 쿠키의 값)

{ "packId": "p" }
```

```json
{ "packId": "p", "outcome": "LOADED", "warnings": [] }
```

- **관리자만 부를 수 있다.** 담당자가 부르면 403 `FORBIDDEN` 이다. [AD-270]
- **Pack 은 올리지 않는다. 서버에 있는 것을 고른다.** 설치할 때 Pack 폴더들을 서버의 한 곳에 두고 그 자리를 설치 설정 `tabnit.packs-dir` 에 적는다. 요청의 `packId` 는 그 폴더 바로 아래에 있는 폴더의 이름이고, 폴더의 이름이 Pack 의 `id` 다 (D6). Pack 을 고치려면 서버의 폴더를 고친 뒤 다시 적재한다.
- `packId` 는 영어 소문자, 숫자, 붙임표만 쓴 100자 이하의 글자다. 그 밖의 글자(`/`, `.`, 빈칸 등)는 400 이다: Pack 폴더 밖을 가리킬 수 없다. Pack 폴더 밖을 가리키는 바로가기(심볼릭 링크)인 폴더는 없는 것으로 본다.
- `outcome`: `LOADED` 처음 적재했다, `UPDATED` 이미 있던 정의를 고친 것으로 바꿨다, `UNCHANGED` 이미 있는 것과 같아 바꾸지 않았다. 무엇을 받고 무엇을 거부하는지는 pack 이 정한다 (D6 9절).
- **`warnings` 는 경고의 목록이다.** 적재를 막지 않는다: 응답은 200 이고 Pack 은 적재됐다. Pack 은 형식에 맞지만 뜻대로 동작하지 않을 수 있는 곳을 Pack 을 만드는 사람에게 알린다. 경고마다 자리(`file`), 대상(`item`), 문구(`message`)가 있고, pack 이 준 순서와 문구 그대로다. 없으면 빈 목록이다. 바뀐 것이 없는 적재(`UNCHANGED`)에도 같은 경고가 나온다. 지금 있는 경고는 하나다: 개체를 여럿 만드는 입력 자료에 걸리는 규칙이 변동 대상의 유형을 정하지 않고 그 속성을 볼 때 (D8 2절). [AD-323] 경고는 저장하지 않는다: 다시 보려면 다시 적재한다. 감사 기록에는 경고가 있을 때 그 수만 남는다 (`warnings=1`).
- 적재하는 것은 정의뿐이다. 개체와 관계는 넣지 않는다. [AD-45] 적재는 전부 되거나 전부 안 된다.
- 적재한 때는 서버의 시계에서 읽어 넘긴다.
- 적재는 한 번에 하나씩 한다 (서버 안에서 차례로).
- **같은 Pack 의 판 처리와 재적재는 한 번에 하나만 한다.** 그 Pack 의 판을 올려 처리하는 중이거나 처리되지 않은 변동을 다시 처리하는 중이면 적재가 그것이 끝날 때까지 기다리고, 적재하는 동안에는 그 Pack 의 판 올리기와 다시 처리가 기다린다. 한 판이 어느 정의와 규칙으로 처리됐는지가 분명해진다. 다른 Pack 의 판 처리는 기다리지 않는다. 기다리는 데에 시간의 한도는 없다: 요청은 처리가 끝나면 이어진다. [AD-331] [AD-235]

| 상황 | HTTP 상태 | `code` (제안) |
|---|---|---|
| `packId` 가 없음 | 400 | `MISSING_PACK_ID` |
| `packId` 에 쓸 수 없는 글자가 있거나 너무 김, 글자가 아님 | 400 | `INVALID_PACK_ID` |
| 본문을 읽을 수 없음 | 400 | `INVALID_BODY` |
| 관리자가 아님 | 403 | `FORBIDDEN` |
| 그 이름의 폴더가 없음, Pack 폴더를 정하지 않은 설치 | 404 | `PACK_FOLDER_NOT_FOUND` |
| 이미 적재된 Pack 을 받을 수 없는 방식으로 고침 | 409 | `PACK_CHANGE_REJECTED` |
| Pack 이 형식에 맞지 않거나 정의가 서로 맞지 않음 | 422 | `PACK_INVALID` |

- 422 에는 찾은 문제 전부가 `problems` 에 담긴다 (`file`, `item`, `message`). 409 에는 맞지 않는 곳이 `reasons` 에 담긴다. 둘 다 pack 이 준 순서와 문구 그대로다.
- 응답에 서버의 폴더 경로를 담지 않는다.

`docs/api/openapi.yaml` 의 `loadPack` 이 이 API 의 규격이다.

## 11. 결정 필요

2026-11-20 의 결정으로 SK-07 을 막던 질문은 닫혔다 (AD-77 ~ AD-81). 남은 것은 그 API 를 만드는 작업 전에 정하면 된다.

1. (닫힘) 로그인은 서버 세션과 쿠키로 한다. [AD-262] 주소와 응답은 9절.
2. (닫힘) **역할과 API.** 새 판을 올리는 것은 담당자와 관리자가 모두 한다 [AD-240]. 관리자는 담당자의 일을 모두 한다: 조치도 확정한다 [AD-270].
3. (닫힘) **Pack 적재의 길.** 서버의 Pack 폴더에 둔 Pack 을 관리자가 API 로 이름을 골라 적재한다 [AD-272]. 10절. 화면은 없다 (설정 화면은 당김 범위).
4. (닫힘, AD-308) **겹쳐 저장된 관계의 표시.** 출처가 달라 같은 두 개체, 같은 유형의 관계가 둘 저장된 경우, API 가 둘 다 주고 화면이 출처와 함께 두 줄로 보여 주는가, API 가 하나로 합쳐 주는가? 합치면 유효기간과 출처를 어떻게 합치는지 규칙이 필요하다. (D3 "결정 필요" 3번)
5. (닫힘, AD-326: 유형, 키, 표시 이름을 함께 준다. 12월) **상대 개체의 정보.** 관계 목록에 상대 개체의 `id` 만 주는가, 개체 유형과 키와 표시 이름도 함께 주는가? 함께 주지 않으면 화면이 `id` 를 그대로 보여 주거나 개체마다 다시 물어야 한다.
6. (닫힘, AD-310: 나눠 주기와 전체 수를 12월에 넣는다) **큰 목록.** 관계가 수천 개인 개체의 목록을 한 번에 다 주는가, 나눠 주는가(쪽 나누기)? 나눠 주면 화면이 수를 다시 세지 않도록 전체 수를 함께 줘야 한다.
7. (닫힘) **뼈대 단계의 임시 처리를 끝내는 때.** 로그인(E-02), 역할(E-06), 감사 기록(E-03, E-05)이 모두 붙어 [AD-80] 의 예외는 끝났다. 개발 환경 밖에 설치하기 전에 따로 볼 것: Pack 이나 입력 자료 단위의 접근 범위 (8, 9번의 참고 사항), 설치 구성과 HTTPS 앞단 (SK-08), 보안 점검 대응 (E-16, 1월 범위).
8. (닫힘, AD-335. 알림과 거부의 문구와 위치: AD-326) **판 올리기에서 구현하면서 정한 것 (D-05 의 서버 쪽).** 맞는지 확인이 필요하다.
   - 응답의 항목 이름과 묶음 (5절). 오류의 `code` 이름.
   - 파일 크기의 한도는 `spring.servlet.multipart.max-file-size` 하나로 정하고 link 의 투입에도 같은 값을 넘긴다. 서버가 먼저 막으므로 한도를 넘는 파일은 보통 투입 기록에 남지 않는다. link 가 크기로 거부한 것(서버를 거치지 않고 부른 경우)도 413 으로 답한다.
   - 거부한 이유의 문구는 api 가 코드마다 가진다. link 는 코드와 값만 돌려준다. 문구를 둔 것은 link 가 파일 전체를 거부할 때 내는 코드 열다섯이다 (`NOT_UTF8`, `NO_HEADER`, `INVALID_HEADER`, `BLANK_COLUMN_NAME`, `INVALID_COLUMN_NAME`, `DUPLICATE_COLUMN_NAME`, `UNCLOSED_QUOTE`, `MISSING_COLUMN`, `EFFECTIVE_DATE_NOT_AFTER_PREVIOUS`, `CANNOT_END`, `RECEIVED_BEFORE_PREVIOUS`, 엑셀의 `NOT_XLSX`, `NOT_CSV`, `SHEET_NOT_FOUND`, `XLSX_TOO_LARGE` [AD-376]). 건너뛴 행의 알림에는 엑셀의 `FORMULA_WITHOUT_RESULT`, `CELL_ERROR` 가 더해졌다 [AD-375]. 그 밖의 코드가 오면 코드와 값을 그대로 넣은 문구로 나간다. link 에 거부의 코드가 늘면 여기도 함께 늘려야 한다.
   - **몇 번째 행인지, 어느 열인지를 문구에 넣지 못하는 거부가 있다.** link 는 `UNCLOSED_QUOTE`, `BLANK_COLUMN_NAME`, `DUPLICATE_COLUMN_NAME`, `INVALID_HEADER`, `INVALID_COLUMN_NAME` 의 위치를 예외의 문구에만 담고 이유의 값으로는 돌려주지 않는다. 투입 기록에도 남지 않는다. link 가 이유의 값을 채워야 한다 (link 의 변경).
   - 투입의 알림(`notices`)은 문구 없이 코드와 값으로 준다. 화면이 풀어 보여 줘야 한다.
   - 파일의 이름은 폴더 부분을 떼고 남긴다. 이름이 없으면 남기지 않는다.
   - 요청이 multipart 가 아니거나 주소·방식이 틀린 오류는 프레임워크가 내는 형식 그대로다 (`code` 없음, 2절).
   - 한 요청이 오래 걸릴 수 있다 (변동이 많은 판, 같은 Pack 의 앞 요청을 기다림). 시간 제한은 두지 않았다.
   - `spring.servlet.multipart.max-file-size` 를 0 이하(한도 없음)로 두면 서버가 뜨지 않는다. 판의 원본을 저장소에 담으므로 한도가 반드시 있어야 한다.
   - **로그인을 붙일 때 이 API 에서 챙길 것** (보안 검토의 참고 사항, 2026-11-21): Pack 이나 입력 자료 단위의 접근 범위 (지금은 `packId` 만 알면 올리고 그 Pack 의 변동을 받는다), 권한 확인을 Pack 조회보다 먼저 두기 (404 의 구분으로 Pack 과 입력 자료가 있는지 드러난다), 쿠키로 로그인하면 CSRF 방어 (multipart 요청은 다른 사이트의 폼으로도 보낼 수 있다), 투입 기록에 올린 사람 남기기, 저장된 파일 이름을 화면이나 내려받기에 쓸 때의 처리.
9. (닫힘, AD-335. 접근 범위: AD-319) **조치와 영향 범위 보기에서 구현하면서 정한 것 (D-06 의 서버 쪽).** 맞는지 확인이 필요하다.
   - 응답의 항목 이름과 묶음 (6절). 오류의 `code` 이름. 주소 (`/api/v1/actions`, `/api/v1/impact-scopes`).
   - 조치를 변동 하나로 걸러도 순서는 Pack 의 목록과 같은 기준(기한이 먼저)이다. 엔진이 한 변동의 조치를 돌려주는 순서 [AD-222] 와는 첫 기준이 다르다.
   - **근거 조항의 개체 유형은 조치에 저장되어 있지 않아 core 의 개체 조회로 읽어 담는다.** 대상의 유형은 조치를 만들 때의 값(저장)이고 근거의 유형은 읽을 때의 값이다. 개체는 지워지지 않고 유형은 식별자의 일부라 값이 달라질 길은 없지만, 그 개체가 저장소에 없으면 그 Pack 의 목록 전체가 서버 쪽의 문제(500)가 된다. 조치에 근거의 유형을 저장하려면 새 스키마 변경 파일이 필요하다 (D5 의 변경).
   - Pack 이 있는지 보려고 Pack 의 정의 전체를 읽는다. 시간은 재지 않았다.
   - 저장된 영향 대상의 경로가 깊이와 맞지 않으면 (저장소가 어긋난 경우) 근거 없이 내보내지 않고 서버 쪽의 문제(500)로 답한다.
   - (닫힘, AD-347: 영향 대상을 나눠 준다) 영향 범위는 영향 대상과 경로를 한 번에 모두 줬다. 이제 영향 대상을 나눠 준다. 경로가 아주 깊은 대상 하나의 응답이 큰 것은 그대로다.
   - Pack 의 조치 목록 조회에는 색인을 더하지 않았다 (측정값이 없다). 조치가 아주 많아지면 느려질 수 있다.
