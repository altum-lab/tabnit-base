## 1. 시험은 두 겹이다

| core | 빈 저장소, 관계가 없는 개체, 돌아오는 관계, 한 대상에 이르는 경로 여럿, 깊이 한계, 유효기간 경계(시작일 당일, 종료일 전날, 종료일 당일), 과거·현재·미래 시점 | [core] [보드 T-01] |
| pack | 빈 Pack, 유형 하나뿐인 Pack, 참조가 끊긴 Pack, 같은 Pack 다시 넣기 | [보드 T-04] |
| link | 빈 파일, 첫 판, 바뀐 것 없는 판, 전부 바뀐 판, 행 순서만 바뀐 판, 잘못된 행이 섞인 파일, 같은 파일 두 번 | [link] [보드 T-02] |

- 같은 데이터로 두 번 돌린 결과를 견주는 시험을 하나 둔다. 목록은 순서까지 같아야 한다. [스킬 tdd-ac] [C 6절]

- 데이터베이스가 필요한 시험은 Testcontainers 의 실제 PostgreSQL 로 돌린다. 메모리 데이터베이스로 바꾸지 않는다. [AD-10] [스킬 tdd-ac]
- 시험을 통과시키려고 시험을 지우거나 약하게 고치지 않는다. [C 8절]

## 3. 검증 질문

### 어디에, 어떤 형식으로

- 검증 질문과 정답은 Pack 의 `questions/` 폴더에 둔다. [AD-85] [D6 2절]
- 형식은 YAML 이다. 질문과 정답은 정의가 아니라 시험 자료다. [AD-107]
- 파일은 UTF-8 이다. 파일 하나에 시나리오 하나와 그 시나리오의 질문들을 적는다. (제안)
- **실행기와 엔진 코드에는 정답이 들어가지 않는다.** 질문과 정답은 Pack 안에만 있다. 실행기는 Pack 을 가리지 않는다. [verify]

### 시나리오

질문을 돌리기 전의 자료는 Pack 이 시나리오로 적는다: 어느 예시 입력 파일을, 어떤 적용일로, 어떤 차례로 투입하는가. [AD-110]

```yaml
scenario:
  id: S-01
  title: 시나리오의 이름
  steps:
    - step: 1
      inputSource: source-a          # 입력 자료의 식별자 (매핑 정의에 있는 것)
      file: data/source-a-v1.csv     # Pack 폴더 기준 경로
      effectiveDate: 2026-01-01      # 판의 적용일
    - step: 2
      inputSource: source-a
      file: data/source-a-v2.csv
      effectiveDate: 2026-03-01
    - step: 3
      inputSource: source-a
      file: data/source-a-v3.csv
      effectiveDate: 2026-06-01
```

항목의 이름은 제안이다.

- 실행기는 빈 저장소에 Pack 을 적재하고, 시나리오의 차례대로 판을 투입한 뒤 질문을 돌린다. 언제 돌려도 같은 상태에서 시작한다. [AD-110]
- 입력 파일은 Pack 의 `data/` 에 있는 예시 입력 파일이다. 가상 데이터만 쓴다. [AD-45] [packs]
- 시나리오에는 판이 셋 이상 있어야 한다. 그래야 현재와 과거 두 시점을 물을 수 있다. [AD-112]
- 기록한 때처럼 밖에서 넘기는 시각은 실행기가 고정한 값을 넘긴다. 실행한 날에 따라 결과가 달라지지 않는다. [AD-26] (제안)

### 질문의 종류

흐름의 네 단계를 모두 묻는다. [AD-108]

| 종류 | 묻는 것 | 정답에 적는 것 (제안) |
|---|---|---|
| 시점 조회 | 어떤 날짜에 어떤 개체의 유효한 관계 | 관계의 목록 (관계 유형, 출발 개체, 도착 개체, 시작일, 종료일) |
| 변동 | 시나리오의 어느 단계에서 나온 변동 | 바뀐 항목의 목록 (항목의 키, 추가·변경·삭제) |
| 영향 범위 | 어느 변동의 영향 범위 | 영향 대상의 목록 (개체, 깊이, 근거 경로), 개체 유형별 수, 깊이별 수, 한계에서 멈췄는지 |
| 조치 | 어느 변동에서 만들어진 조치 | 조치의 목록 (근거 규칙, 대상, 근거 조항과 그 판, 근거 경로, 기한, 우선순위) |

```yaml
questions:
  - id: Q-001
    kind: relations-as-of
    title: 질문을 한 줄로
    asOf: 2026-02-01
    entity: { type: TypeA, key: key-1 }
    expect:
      relations:
        - { type: relatesTo, source: { type: TypeA, key: key-1 }, target: { type: TypeB, key: key-9 }, validFrom: 2026-01-01, validTo: null }

  - id: Q-002
    kind: impact
    title: 질문을 한 줄로
    change: { step: 2, itemKey: key-1 }      # 시나리오의 2단계에서 이 항목에 생긴 변동
    expect:
      targets:
        - entity: { type: TypeB, key: key-9 }
          depth: 1
          path:                                  # 근거 경로: 시작한 변동 대상과 거친 관계
            from: { type: TypeA, key: key-1 }
            relations:
              - { type: relatesTo, source: { type: TypeA, key: key-1 }, target: { type: TypeB, key: key-9 } }
      countsByType: { TypeB: 1 }
      countsByDepth: { 1: 1 }
      truncated: false
```

항목의 이름과 모양은 제안이다. 값은 자리만 잡은 것이다.

- 개체는 유형의 이름과 입력의 키로 가리킨다. Pack 식별자는 그 Pack 이므로 적지 않는다. [D6 5절] (제안)
- **모든 질문은 날짜를 적는다.** 시점 조회는 `asOf` 를, 변동·영향 범위·조치는 시나리오의 단계를 적는다(그 단계의 적용일이 날짜다). "오늘"에 기대는 질문은 없다. [AD-23] (제안)
- 질문에는 겹치지 않는 번호가 있다. 보고는 번호로 한다. [스킬 verify-questions]
- 질문마다 정답의 근거(어느 행, 어느 관계, 어느 날짜 때문인지)를 주석으로 적는다. 정답이 틀렸는지 따질 때 본다. (제안)

### 서로 다른 시점

- Pack 마다 **현재와 과거 두 시점**, 셋 이상의 시점을 묻는다. 시나리오에 판이 셋 이상 있고, 마지막 판 뒤의 날짜(현재)와 그 앞의 판들 사이의 날짜들(과거)을 묻는다. [verify] [AD-112]
- "현재"는 실행한 날이 아니라 시나리오가 정한 날짜다. [AD-112]
- 같은 개체를 판이 바뀌기 전과 뒤의 날짜로 각각 묻는다. 한 번 바뀐 것이 또 바뀌는 경우를 포함한다. (제안)
- 유효기간의 경계 날짜(시작일 당일, 종료일 전날, 종료일 당일)를 묻는 질문을 포함한다. [core] (검증 질문에도 넣는 것은 제안)

### 질문의 수

- Pack 마다 질문은 10개 이상이다. 네 종류(시점 조회, 변동, 영향 범위, 조치)마다 2개 이상이다. 예시 Pack 둘과 시험용 Pack 모두 같다. [AD-113]
- 실행기는 이 최소 수를 확인해, 모자라면 알린다. [AD-113]

## 4. 정답과 견주기

- **목록은 항목도 순서도 같아야 통과다.** 수와 날짜도 정확히 같아야 한다. [AD-109]
- 정답에 적지 않은 항목은 견주지 않는다 (예: 기록한 때). [AD-109]
- **근거까지 견준다.** 영향 범위의 정답에는 영향 대상마다 근거 경로(시작한 변동 대상과 거친 관계)를, 조치의 정답에는 근거 조항과 그 판을 적고 견준다. 대상은 맞는데 경로가 틀린 것도 실패다. [AD-114] [AD-04]
- 영향 범위와 조치의 질문에서 근거를 빼고 적은 정답은 형식이 틀린 것으로 본다. (제안)
- 견주는 순서는 엔진이 정한 순서다: 시점 조회는 관계 유형·상대 개체·관계 식별자 [AD-38], 영향 대상은 깊이·개체 유형·개체 식별자 [AD-61], 조치는 우선순위·규칙 번호·대상 식별자 [D8 4절]. 정답을 적는 사람이 이 순서로 적는다.
- **정답을 고쳐 통과시키지 않는다.** 정답은 대표가 정한다. 결과가 정답과 다르면 코드를 의심한다. 정답이 틀렸다고 판단되면 근거(조문, 경로, 날짜)를 적어 묻는다. [verify] [packs] [스킬 verify-questions]

## 5. 실행기

검증 질문을 돌리는 것은 verify 모듈이다. [verify] [보드 VER-01]

### 하는 일

1. 저장소의 Pack 을 모두 찾는다. Pack 을 가리지 않는다. [verify]
2. Pack 마다, 시나리오마다: 빈 저장소에 Pack 을 적재하고 시나리오대로 판을 투입한다. [AD-110]
3. 질문을 번호 순으로 돌려 정답과 견준다. [AD-109]
4. 같은 일을 한 번 더 해서 두 번의 결과가 같은지 본다. 다르면 어느 질문이 달랐는지 남긴다. 이것은 결함이다. [verify] [보드 VER-01.1]
5. 질문별 통과·실패 목록을 낸다. 통과 수만 내지 않는다. [verify]

### 지킬 것

- 질문을 건너뛰거나 끄지 않는다. 질문 하나가 오류를 내도 나머지는 계속 돌린다. [verify]
- **아직 만들지 않은 종류의 질문은 실패로 보고한다.** 건너뛰지 않는다. [AD-108]
- 실패한 질문에는 번호, 기대한 값, 실제 값, 날짜를 적는다. [스킬 verify-questions]
- Pack 별 통과 수와 전체 수를 낸다. 직전 main 의 통과 수와의 차이를 본다. [스킬 verify-questions]
- 실행기는 모듈의 내부나 테이블을 직접 보지 않는다. [C 4절]
- **묻는 길**: 각 모듈의 공개 API 로 시작한다. 그 종류의 HTTP API 가 D7 에 생기면 그 질문은 HTTP 로 묻도록 옮긴다. Pack 적재와 판 투입도 같다. 출시 때는 모든 질문을 HTTP 로 묻는다. [AD-111]
- HTTP 로 옮기기 전까지 그 종류의 질문은 api 층의 잘못을 보지 못한다. 그 사이에는 api 의 일반 시험과 화면 흐름 시험이 본다. 어느 종류가 아직 모듈을 직접 부르는지 보고에 적는다. (제안)
- 명령은 `bash verify/run.sh` 다. [C 3절] CI 의 밤 통합이 이 명령을 돌린다. [.github/workflows/nightly.yml]

1. **질문과 정답.** 제조 안전 Pack, 퇴직연금 Pack, 시험용 Pack 의 시나리오, 질문, 정답. Pack 의 내용(D6 "결정 필요" 6번)이 먼저 있어야 한다. 시험용 Pack 은 지어낸 업무 영역이라 이 대화에서 함께 만들 수 있다. SK-06 의 수용 기준("검증 질문이 자동으로 돌고 통과와 실패가 목록으로 나온다")을 확인하려면 적어도 Pack 하나의 질문이 있어야 한다.

### 뒤에 정해도 되는 것

2. **두 날짜의 근거 경로.** 변동 이벤트의 영향 범위는 적용일 전날과 적용일 두 날짜로 보고, 대상마다 더 짧은 경로(같으면 적용일 쪽)를 남긴다 (AD-100, AD-116). 정답의 근거 경로에 어느 날짜의 관계인지를 `asOf` 로 적는 것으로 제안한다. 시험용 Pack 의 질문을 적으면서 형식에 더한다.
3. **넓게 잡히는 영향 범위.** 참조로만 등장한 개체도 변동 대상으로 하기로 했다 (AD-59). 그 규칙으로 계산한 영향 범위가 기대와 맞는지는 예시 Pack 의 질문과 정답을 정할 때 확인한다 (D3 "결정 필요" 2번).
4. **화면 흐름 시험과의 관계.** 화면 전체 흐름 시험(E-08, 새 판 투입부터 확정까지)이 같은 시나리오를 쓰는가? 쓰면 자료와 정답을 한 곳에서 관리할 수 있다.
5. **큰 자료.** 성능 점검용 큰 자료(T-07)는 지어낸 자료를 만들어 내는 것이라 검증 질문과 따로다. 큰 자료에도 정답을 견주는 질문을 두는가?
6. **HTTP 로 옮기는 때.** 종류마다 HTTP API 가 생기는 변경에서 그 질문을 함께 옮기는가, 따로 작업을 두는가? 출시 전에 모든 질문이 HTTP 로 묻는지를 무엇으로 확인하는가?
