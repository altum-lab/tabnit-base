## 1. 공통 규칙

### 저장소와 변경 관리

- 저장소는 PostgreSQL 하나다. [AD-07] 버전은 정해지지 않았다 (D2 "결정 필요" 2번).
- 스키마 변경은 `server/api/src/main/resources/db/migration/` 에 `V번호__설명.sql` 파일을 새로 추가해서만 한다. 올라간 파일은 고치지 않는다. [AD-12] [AD-46]
- 변경 파일에 행을 지우는 문장(`DELETE`, `TRUNCATE`)을 쓰지 않는다. [규칙 migration]
- 테이블마다 주인 모듈이 있다(2절). 다른 모듈은 주인 모듈의 공개 API 로만 읽고 쓴다. 남의 테이블을 직접 건드리지 않는다. [AD-18] [AD-46]

### 식별자

- 식별자는 입력의 키에서 정해진다. 데이터베이스가 매기는 일련번호를 식별자로 쓰지 않는다. [AD-37]
- 식별자를 이루는 값은 각각 열로 두고, 그 값들을 이어 붙인 문자열을 `id` 열로 함께 둔다. 테이블 사이의 참조, API, 화면, 근거 경로는 `id` 하나만 들고 다닌다. [AD-65]
- `id` 는 값을 정해진 차례로 `|` 로 이어 붙여 만든다. 값 안에 `|` 나 `\` 가 있으면 그 앞에 `\` 를 붙인다. [AD-65]
- "식별자 순"은 `id` 의 글자 코드 순이다. [AD-65] [AD-38]

| 대상 | `id` 를 이루는 값 (이 차례로) | 근거 |
|---|---|---|
| 개체 | `pack_id`, `entity_type`, `entity_key` | [AD-37] |
| 속성 값 | 개체의 세 값, `attribute_name`, `valid_from` | [AD-53]. 제안 |
| 관계 | `pack_id`, 출발 개체의 `entity_type` 과 `entity_key`, 도착 개체의 `entity_type` 과 `entity_key`, `relation_type`, `input_source_id`, `edition_no`, `valid_from` | [AD-37] |

- 날짜는 `2026-03-01` 모양으로, 판 번호는 십진수로 적는다. (제안)
- `id` 는 저장할 때 core 가 값에서 만든다. 밖에서 받은 `id` 를 그대로 믿지 않는다. (제안)
- 감사 기록과 이력처럼 입력의 키가 없는 것의 식별자는 "결정 필요" 7번.

### Pack 의 경계

- Pack 은 서로 독립이다. 개체, 관계, 입력 자료, 변동, 조치는 모두 한 Pack 에 속한다. [AD-74]
- 관계의 출발 개체와 도착 개체는 같은 Pack 의 개체여야 한다. 조회와 영향 범위는 한 Pack 안에서만 계산한다. [AD-74]
- 그래서 자료를 담는 테이블에는 모두 `pack_id` 가 있다.

### 순서

- 목록의 마지막 정렬 기준은 식별자다. [AD-25]
- 식별자와 유형 이름은 글자 코드 순으로 비교한다. [AD-38] 그러려면 이 열들의 정렬 규칙(collation)을 `"C"` 로 둔다. 설치한 곳의 언어 설정에 따라 순서가 달라지지 않는다. (제안)

### 유효기간

관계와 속성 값에 같은 열 둘을 둔다. [AD-22] [AD-39]

| 열 | 형식 | 뜻 | 근거 |
|---|---|---|---|
| `valid_from` | `date`, 반드시 있음 | 시작일. 포함한다 | [AD-22] |
| `valid_to` | `date`, 없을 수 있음 | 종료일. 제외한다. 없으면 계속 유효하다 | [AD-22] |

- 종료일이 있으면 시작일보다 뒤여야 한다: `valid_to is null or valid_to > valid_from`. [D3 4절]
- 끝없는 날짜(`infinity`, `-infinity`)는 받지 않는다. 종료일이 없다는 것은 `valid_to` 가 비어 있는 것 하나로만 나타낸다. [AD-75]
- 기준 날짜 d 에 유효한 행: `valid_from <= d and (valid_to is null or d < valid_to)`. [D3 4절]
- 행을 지우지 않는다. 끝낼 때는 `valid_to` 를 넣는다. [AD-24]

### 출처와 기록한 때

관계와 속성 값에 같은 열을 둔다. [AD-30] [AD-31] [AD-54]

| 열 | 형식 | 뜻 | 근거 |
|---|---|---|---|
| `input_source_id` | 입력 자료의 식별자, 반드시 있음 | 어느 입력 자료에서 왔는가 | [AD-30] |
| `edition_no` | 판의 번호, 반드시 있음. 1 부터 | 그 자료의 어느 판에서 처음 나타났는가 | [AD-30] [AD-75] |
| `recorded_at` | `timestamptz`, 반드시 있음 | 기록한 때. 밖에서 받아 넘긴 시각이다. 데이터베이스의 현재 시각(`now()`)을 기본값으로 두지 않는다 | [AD-31] [AD-26] |

- 출처 열은 비어 있을 수 없다. 비어 있으면 유일 제약과 겹침 거부가 그 행을 비교하지 않아 겹침이 뚫린다. 같은 까닭으로 식별자를 이루는 열(`pack_id`, 유형과 속성의 이름, 키)도 모두 반드시 있어야 한다.
- 식별자(`id`)와 식별자를 이루는 글자 열, 출처의 `input_source_id` 는 빈 글자일 수 없다. 속성 값의 `value` 는 이 규칙에 들지 않는다. 빈 글자인 값을 받을지는 속성의 형식(D6)이 정한다. [AD-75]

### 색인

- 이 초안에는 유일 제약과 겹침 거부처럼 **결과가 맞기 위해 필요한 것만** 적는다.
- 빠르게 하려는 색인은 측정값이 있을 때만 넣는다. 측정 없이 색인이나 캐시를 넣지 않는다. 측정은 큰 시험 자료(T-07)로 하고 (`bash verify/large.sh ... measure`), 그 결과로 정한 색인을 이 문서의 그 테이블에 적는다. 지금까지 더한 것: `relation` 의 도착 개체 색인 [AD-356]. [core] [보드 A-07]
- **성능 목표** [AD-355]: 영향 범위 계산 하나(core 의 계산만. 저장과 규칙 실행은 들지 않는다. 되풀이해 잰 가운데 값)가 영향 대상 1,000개쯤에서 0.1초 이내, 10,000개쯤에서 1초 이내다. 그 사이와 너머는 비례로 본다 (영향 대상 하나에 0.1 ms. 0.1초보다 작게 잡지는 않는다) [AD-359]. 개발용 PC 의 값으로 정했다 (정할 때의 값: 36 ms, 0.47초. D9 의 A-07). `bash verify/large.sh ... measure` 가 재고, 넘으면 넘었다고 알린다. 빌드와 CI 는 재지 않는다: 영향 범위 계산이나 관계의 저장을 고칠 때 돌려 본다. 설치할 서버에서는 설치 구성(E-07) 때 한 번 더 잰다. 다른 것(판 올리기, 나눠 주는 조회, 관계 지도)에는 목표가 없다.

## 3. core 의 테이블

### entity — 개체

| 열 | 형식 | 뜻 | 근거 |
|---|---|---|---|
| `id` | text | 식별자. 아래 세 값을 이어 붙인 것 | [AD-65] |
| `pack_id` | text | 어느 Pack 의 개체인가 | [AD-37] |
| `entity_type` | text | 개체 유형. 온톨로지가 정한 이름. 가장 구체적인 유형 하나다 | [AD-37] [AD-88] |
| `entity_key` | text | 입력의 키 | [AD-37] |
| `recorded_at` | timestamptz | 처음 기록한 때 | 제안 |

- 기본 키: `id`. 유일: (`pack_id`, `entity_type`, `entity_key`). [AD-65]
- 유일: (`pack_id`, `id`). 관계와 속성 값이 같은 Pack 의 개체만 가리키게 하는 참조의 대상이다. [AD-74]
- 같은 개체를 다시 넣어도 행이 늘지 않는다. [link]
- 개체에는 유효기간이 없다. 유효기간은 관계와 속성 값에 있다. [AD-22] [AD-39]
- 표시 이름 열은 두지 않는다. 표시 이름은 온톨로지가 개체 유형마다 지정한 속성의 값이다. 기준 날짜에 그 값이 없으면 `entity_key` 를 보여 준다. 지정하는 형식은 D6 이 정한다. [AD-70]

- 다른 모듈은 개체를 core 의 공개 조회로 읽는다: 식별자로 개체(Pack, 유형, 키)를 읽고, 없으면 없다고 답한다. 여럿을 한 번에 물으면 있는 것만 식별자 순으로 돌려준다. 식별자를 다른 모듈이 거꾸로 풀어 읽지 않는다. [AD-218]

### attribute_value — 속성 값

| 열 | 형식 | 뜻 | 근거 |
|---|---|---|---|
| `id` | text | 식별자 | [AD-65] |
| `pack_id` | text | 어느 Pack 의 값인가 | [AD-74] |
| `entity_id` | text. (`pack_id`, `entity_id`) 가 `entity` 의 (`pack_id`, `id`) 를 가리킴 | 어느 개체의 값인가 | [AD-39] [AD-74] |
| `attribute_name` | text | 속성. 온톨로지가 정한 이름 | [AD-39] |
| `value` | text, 반드시 있음 | 값. 속성의 형식에 맞는 정해진 표기의 글자 | [AD-71] |
| `valid_from`, `valid_to` | 1절 | 유효기간 | [AD-39] |
| `input_source_id`, `edition_no`, `recorded_at` | 1절 | 출처와 기록한 때 | [AD-54] |

- 기본 키: `id`. 유일: (`entity_id`, `attribute_name`, `valid_from`). [AD-65]
- 개체는 반드시 `entity` 에 있어야 하고, 속성 값과 같은 Pack 이어야 한다. [AD-74]
- **겹침 거부**: `entity_id` 와 `attribute_name` 이 같은 행끼리 유효기간이 겹치면 저장을 거부한다. 출처는 보지 않는다. [AD-53]
- 기준 날짜에 유효한 행이 없으면 값이 없는 것이다. 앞의 행을 끌어다 쓰지 않는다. "값 없음"을 행으로 저장하지 않는다. [AD-55]
- 값이 바뀌면 앞 행의 `valid_to` 에 새 행의 `valid_from` 을 넣는다. [AD-56] 이것은 부르는 쪽(link)이 "끝내기"로 한다. core 의 저장은 다른 행을 고치지 않고, 겹치면 어느 값과 겹치는지 알리며 거부한다. [AD-163]
- **끝내기**: 종료일이 없는 행에만 종료일을 넣을 수 있다. 종료일은 시작일보다 뒤여야 한다. 이미 같은 날짜로 끝나 있으면 그대로 두고, 다른 날짜로 끝나 있으면 거부한다. 한 번 넣은 종료일은 바꾸지 않는다. 관계도 같다. [AD-162]
- 식별자는 (개체의 식별자를 이루는 값들, 속성의 이름, 시작일)을 이은 글자다. [AD-65]
- 같은 값(식별자, 값, 종료일, 출처가 모두 같은 것)을 다시 저장하면 그대로 둔다. 값은 빈 글자일 수 없다. [AD-55]
- 같은 개체, 같은 속성, 같은 시작일의 값이 이미 다른 내용(값, 종료일, 출처)으로 있으면 거부하고 무엇이 다른지 알린다. 한 번 저장한 값은 바꾸지 않는다.
- **받는 날짜의 범위는 0001-01-01 부터 9999-12-31 까지다.** 유효기간의 시작일과 종료일, 끝내기의 종료일, 속성 값 조회의 기준 날짜, 기록한 때에 적용한다. 범위 밖의 값은 저장소까지 보내지 않고 거부한다. 저장소의 오류가 되면 부르는 쪽의 트랜잭션이 깨지기 때문이다. 관계의 저장도 같다. (제안. "결정 필요" 10번)
- 거부는 저장소의 오류를 내지 않는다. 부르는 쪽의 트랜잭션 안에서 거부된 뒤에도 이어서 읽고 쓸 수 있다.
- 개체 하나의 기준 날짜에 유효한 속성 값은 속성 이름의 글자 코드 순으로 돌려준다. 속성마다 많아야 하나다. [AD-53]
- 개체 하나의 속성 값 여럿은 `attribute_name`, `valid_from` 순으로 돌려준다. (제안)
- **개체 여럿의 기준 날짜에 유효한 값을 한 번에 읽는 조회** (`valuesAsOf(개체들, 기준 날짜)`): 개체 하나를 읽는 조회와 같은 시점 조회다 (시작일 포함, 종료일 제외. 기준 날짜는 반드시 받는다). 개체의 식별자, 속성의 이름, 값의 식별자 순이다. 넘긴 차례와 겹침은 결과에 닿지 않는다. 값이 없는 개체는 줄이 없다. **없는 개체는 오류로 알린다** (D3 2절. 여럿이면 식별자 순으로 첫째). api 가 응답의 개체에 표시 이름을 붙이는 데 쓴다. 실행 계획은 재지 않았다. [AD-349]
- **어느 날부터 유효한 값을 읽는 조회** (`valuesInEffectFrom`): 개체 여럿과 날짜 하나를 받아, 그 개체들의 값 가운데 종료일이 없거나 그 날짜보다 뒤인 것을 모두 돌려준다. 시작일은 보지 않는다 (그 날짜 뒤에 시작하는 것도 든다). 출처를 가리지 않는다. 값의 식별자 순이다. 아직 없는 개체는 오류가 아니라 값이 없는 것으로 답한다 (새 판이 만들 개체를 미리 물을 수 있어야 한다). 날짜는 반드시 받는다. 한 날짜에 유효한 값을 주는 시점 조회가 아니므로 한 속성에 값이 여럿 나올 수 있다: 넣기 전에 기간이 겹치는지 가리는 데만 쓰고 (link), 화면, API, 규칙의 조건은 쓰지 않는다. [AD-344]

#### 값의 형식

- 온톨로지가 속성마다 형식을 정한다: 글자, 정수, 소수, 날짜, 참·거짓. 형식마다 저장하는 표기는 D6 5절에 있다. [AD-71]
- 저장은 글자 열 하나로 한다. 형식마다 열을 나누지 않는다. [AD-71]
- 적재할 때 값이 형식에 맞는지 확인한다. 틀리면 그 행을 건너뛰고 행 번호와 이유를 남긴다. 확인은 형식을 아는 쪽(link)이 한다. core 는 받은 글자를 그대로 저장한다. [AD-71] [link]
- 수나 날짜의 비교는 규칙 실행기가 형식에 맞춰 한다. [AD-71]

### relation — 관계

| 열 | 형식 | 뜻 | 근거 |
|---|---|---|---|
| `id` | text | 식별자 | [AD-65] |
| `pack_id` | text | 어느 Pack 의 관계인가 | [AD-74] |
| `source_entity_id` | text. (`pack_id`, `source_entity_id`) 가 `entity` 의 (`pack_id`, `id`) 를 가리킴 | 출발 개체 | [AD-29] [AD-74] |
| `target_entity_id` | text. (`pack_id`, `target_entity_id`) 가 `entity` 의 (`pack_id`, `id`) 를 가리킴 | 도착 개체 | [AD-29] [AD-74] |
| `relation_type` | text | 관계 유형. 온톨로지가 정한 이름 | [D3 3절] |
| `valid_from`, `valid_to` | 1절 | 유효기간 | [AD-22] |
| `input_source_id`, `edition_no`, `recorded_at` | 1절 | 출처와 기록한 때 | [AD-30] [AD-31] |

- 기본 키: `id`. 유일: (`source_entity_id`, `target_entity_id`, `relation_type`, `input_source_id`, `edition_no`, `valid_from`). [AD-37] [AD-65]
- 출발 개체와 도착 개체는 반드시 `entity` 에 있어야 하고, 관계와 같은 Pack 이어야 한다. 없는 개체를 가리키는 관계는 거부한다. [보드 CORE-01] [AD-74]
- **출발 개체와 도착 개체가 같은 관계는 거부한다.** `source_entity_id <> target_entity_id`. [AD-68]
- **겹침 거부**: `source_entity_id`, `target_entity_id`, `relation_type`, `input_source_id`, `edition_no` 가 모두 같은 행끼리 유효기간이 겹치면 저장을 거부한다. 맞닿는 것은 겹침이 아니다. [AD-30]
- 출처가 다르면 두 개체와 유형이 같아도 겹치는 기간에 둘 다 저장된다. [D3 3절]
- 관계나 속성 값이 가리키는 개체는 지울 수 없다. [AD-24]
- 새 판에서도 그대로인 관계는 행을 새로 만들지 않는다. [AD-30]
- **색인 `relation_target_entity_idx`**: `target_entity_id` 로 찾는다. 빠르게 하려는 색인이다 (결과에는 닿지 않는다). 관계 지도가 이웃을 찾을 때 쓴다 (큰 자료의 실행 계획으로 확인). 이것이 없을 때는 겹침 거부의 색인(출발 개체로 시작한다)을 빌려 썼다. 영향 범위 계산은 잰 자료에서 여전히 겹침 거부의 색인으로 읽었고, 시점 조회가 이 색인을 쓰는지는 확인하지 못했다. 측정으로 더했다 (D9 의 A-06). [AD-356]

### 겹침 거부를 거는 방법

데이터베이스의 배제 제약으로 건다. [AD-67]

- 유효기간을 날짜 범위(`daterange`, 시작 포함 끝 제외)로 보고, 같은 관계(또는 같은 개체의 같은 속성)끼리 범위가 겹치면(`&&`) 저장이 실패하게 한다. `valid_to` 가 없으면 끝이 없는 범위다.
- 이 제약에는 PostgreSQL 에 함께 들어 있는 `btree_gist` 확장이 필요하다. 스키마 v0 의 변경 파일에서 켠다. [AD-67]
- 어느 경로로 쓰든, 동시에 들어와도 막힌다.
- core 는 제약 위반을 받아 "어느 관계의 어느 기간과 겹치는지"를 담은 오류로 바꿔 알린다. 데이터베이스의 오류 문구를 그대로 내보내지 않는다. [C 8절] [api]
- 정렬 규칙을 `"C"` 로 둔 글자 열에도 이 제약이 걸린다. SK-03 의 시험(`CoreSchemaV0Tests`)에서 확인했다.

### 영향 방향은 테이블에 두지 않는다

영향 범위 계산은 관계 유형마다의 영향 방향을 알아야 한다. [AD-33] core 는 pack 에 의존할 수 없으므로 [AD-16], 부르는 쪽(api)이 pack 의 공개 API 로 방향을 읽어 기준 날짜, 최대 깊이와 함께 인자로 넘긴다. core 는 Pack 의 정의를 저장하지 않는다. [AD-66]

방향의 값은 넷이다: 출발에서 도착으로, 도착에서 출발로, 양쪽, 퍼지지 않음. [AD-33] 따라가다가 인자에 없는 관계 유형의 관계를 만나면 어느 유형인지 알리며 계산을 멈춘다. [AD-123]

### 관계 지도의 조회

관계 지도(D3 5절, D7 4절)는 `relation` 과 `entity` 를 읽기만 한다. 새 테이블은 없다. [AD-352] 도착 쪽을 읽는 색인은 뒤에 측정으로 더했다. [AD-356]

- 이웃을 찾을 때는 단계마다, 그 단계의 개체에 닿은 관계 가운데 기준 날짜에 유효한 것의 두 끝만 읽는다 (출발 쪽이든 도착 쪽이든). 영향 범위 계산과 달리 방향으로 거르지 않는다 (영향 범위 계산은 영향이 퍼져 나가는 쪽의 관계만 읽는다 [AD-354]). 잰 자료에서는 출발 쪽은 유일 제약의 색인을, 도착 쪽은 도착 개체 색인을 썼다 [AD-356]. 간선을 읽을 때는 겹침 거부의 색인으로 읽었다.
- 찾은 개체의 유형을 `entity` 에서 한 번에 읽는다 (자르는 순서에 유형이 든다).
- 간선은 두 끝이 모두 담긴 노드인 관계를 한 번에 읽는다.
- 찾은 노드가 한도를 넘은 단계에서 더 읽지 않는다 [AD-357]. 그 단계는 끝까지 읽는다 (개체 200개 이하에 닿은 관계 모두): 관계가 아주 많이 몰린 개체가 그 안에 있으면 그만큼 읽는다. 걸리는 시간은 D9 의 A-06 과 A-07 에 있다.

## 4. pack 의 테이블

Pack 적재는 정의(온톨로지, 제약, 매핑, 규칙, 검증 질문)만 저장한다. [AD-45]

정의는 항목별 테이블로 나눠 담는다. [AD-69] Pack 자신, 개체 유형, 상위 유형, 관계 유형, 속성의 다섯 테이블은 D6 4절 ~ 5절의 항목을 그대로 열로 옮긴 것이다. [AD-125] 변경 파일: `V3__pack_definition.sql` (SK-04). 매핑, 규칙, 검증 질문, 제약의 테이블은 그 작업에서 더한다.

- 주인 모듈은 pack 이다. 다른 모듈은 pack 의 공개 API 로만 읽는다. [AD-18]
- 이름 열의 정렬 규칙은 `"C"` 다 (1절 순서). 모든 참조는 같은 Pack 안에서만 걸린다. [AD-74]
- 이름과 이름표는 빈 글자일 수 없다. [AD-75]
- 같은 Pack 을 다시 넣어도 중복되지 않는다. 적재는 전부 되거나 전부 안 된다. [pack]
- 한 Pack 안에서 개체 유형, 관계 유형, 속성의 이름이 서로 겹치지 않는 것 [D6 5절] 은 테이블이 아니라 pack 의 검증이 지킨다. 세 종류가 한 주소 공간을 쓰므로 정의 파일에서 겹칠 수 없다.

### pack_definition

| 열 | 형식 | 뜻 | 근거 |
|---|---|---|---|
| `pack_id` | text | Pack 의 식별자 | [D6 4절] |
| `label` | text | 사람이 읽는 이름 | [D6 4절] |
| `default_max_depth` | integer | 영향 범위의 최대 깊이 기본값. 1 이상 | [AD-35] |
| `loaded_at` | timestamptz | 적재한 때. 밖에서 받아 넘긴 시각. 기본값을 두지 않는다 | [AD-125] |

- 기본 키: `pack_id`.

### 매핑의 테이블

매핑 정의(D6 7절)를 담는다. [AD-141] 변경 파일: `V5__pack_mapping.sql`. Turtle 에서 차례가 없는 부분(행이 만드는 개체, 관계)은 내용을 키로 삼는다.

**pack_mapping** — 매핑 하나. 입력 자료 하나에 하나다.

| 열 | 형식 | 뜻 | 근거 |
|---|---|---|---|
| `pack_id`, `input_source_id` | text | 기본 키. 입력 자료의 식별자는 출처의 `input_source_id` 가 된다 | [AD-41] |
| `file_format` | text | `CSV` 또는 `XLSX` | [AD-84] |
| `sheet_name` | text, 없을 수 있다 | 엑셀일 때 읽을 시트. CSV 이면 없다 | [AD-93] |
| `default_date_pattern` | text, 없을 수 있다 | 날짜의 기본 모양. 변경 파일 `V6__pack_mapping_default_date_pattern.sql` 에서 더했다 | [AD-143] |
| `primary_entity_type`, `primary_key_column` | text | 행의 주 개체. 유형과 키 열 | [AD-120] |

**pack_mapping_column** — 차례가 있는 열 목록.

| 열 | 형식 | 뜻 | 근거 |
|---|---|---|---|
| `pack_id`, `input_source_id`, `kind`, `position` | | 기본 키. `kind` 는 `REQUIRED` (반드시 있어야 하는 열) 또는 `ITEM_KEY` (항목의 키 열). `position` 은 1 부터 | [AD-57] [AD-122] |
| `column_name` | text | 열 이름 | |

**pack_mapping_entity** — 행이 만드는 개체.

| 열 | 형식 | 뜻 | 근거 |
|---|---|---|---|
| `pack_id`, `input_source_id`, `entity_type`, `key_column` | text | 기본 키. 개체 유형과, 입력의 키가 되는 열 | [AD-37] |

**pack_mapping_attribute** — 개체의 속성 값.

| 열 | 형식 | 뜻 | 근거 |
|---|---|---|---|
| (위 개체의 키), `attribute_name` | text | 기본 키 | [AD-39] |
| `column_name` | text | 값을 읽을 열 | |
| `valid_from_column`, `valid_to_column` | text, 없을 수 있다 | 유효기간을 읽을 열 | [AD-42] |

**pack_mapping_relation** — 행이 만드는 관계.

| 열 | 형식 | 뜻 | 근거 |
|---|---|---|---|
| `pack_id`, `input_source_id`, `relation_type`, `source_entity_type`, `source_key_column`, `target_entity_type`, `target_key_column` | text | 기본 키 | [AD-29] |

- 참조: 매핑이 가리키는 개체 유형은 `pack_entity_type`, 속성은 `pack_attribute`, 관계 유형은 `pack_relation_type`.
- "속성 하나는 매핑 하나만 넣는다"[AD-137] 는 테이블이 아니라 pack 의 검증이 지킨다.

### pack_localized_label

언어별 이름표다. 기본 이름표는 각 테이블의 `label` 열에 있다. [AD-131] 변경 파일: `V4__pack_localized_label.sql`.

| 열 | 형식 | 뜻 | 근거 |
|---|---|---|---|
| `pack_id` | text | 어느 Pack 의 정의인가 | |

- 개체 유형, 관계 유형, 속성의 이름은 한 Pack 안에서 겹치지 않으므로 종류를 따로 적지 않는다. `name` 이 정의된 이름인지는 pack 의 검증이 지킨다.

### pack_attribute

| 열 | 형식 | 뜻 | 근거 |
|---|---|---|---|
| `pack_id` | text | | |

| `entity_type` | text | 이 속성을 갖는 개체 유형. 그 하위 유형도 갖는다 | [AD-88] |
| `value_format` | text | `STRING`, `INTEGER`, `DECIMAL`, `DATE`, `BOOLEAN` 가운데 하나 | [AD-71] |

- 기본 키: `(pack_id, name)`. 참조: `entity_type` 은 `pack_entity_type`.

### 규칙 정의의 테이블

변경 파일: `V9__pack_rule.sql` (B-04). 규칙의 형식은 D8 2절 ~ 3절이 정한다. 규칙을 실행하는 것은 rules 다. 여기에는 읽어서 검증한 정의만 담는다. [AD-213]

**pack_rule** — 규칙.

**pack_rule_condition** — 규칙의 조건. 유형을 보는 조건이거나 속성 값을 보는 조건이다.

규칙의 형식을 넓힌 것 (B-03, 변경 파일 `V14__rule_scope_and_changed_items.sql`). 이미 올라간 V9 는 고치지 않고 더했다. [AD-289]

## 5. link 의 테이블

2026-11-20 의 결정(AD-148 ~ AD-155)으로 다시 썼다. 판, 항목, 항목이 만든 것, 투입 기록, 알림의 다섯 테이블은 변경 파일 `V7__link_edition.sql` 에 있다 (C-04, [AD-183]). 판 비교에 쓰는 열과 변동 이벤트, 변동 대상의 테이블은 `V8__link_change_event.sql` 에 있다 (C-05, [AD-194]). V8 은 판이 하나도 없는 데이터베이스를 전제로 한다. [AD-197]

- 주인 모듈은 link 다. 다른 모듈은 link 의 공개 API 로만 읽고 쓴다. [AD-18]
- link 는 다른 모듈의 테이블을 가리킬 수 없다. 개체, 관계, 속성 값의 식별자(core)와 입력 자료의 식별자(pack 의 매핑)는 값으로 담고 참조 제약을 걸지 않는다. 있는지는 그 모듈의 공개 API 로 확인한다. [AD-18]
- **입력 자료의 테이블은 따로 두지 않는다.** 입력 자료는 pack 의 매핑이 정한다 (`pack_mapping`). link 는 (Pack, 입력 자료의 식별자)를 값으로 쓰고, 그런 입력 자료가 있는지는 투입할 때 pack 의 공개 API 로 확인한다. [AD-160]
- link 는 "이 Pack 에서 판이 있는 입력 자료의 목록"을 공개 API 로 답한다. api 가 Pack 을 적재할 때 그것을 물어 pack 에 넘긴다. [AD-159]
- 식별자와 정렬은 1절을 따른다. 글자 열의 정렬 규칙은 `"C"` 다.

### edition — 판

받아들여진 투입 하나가 판 하나다. [AD-41] [AD-152]

| 열 | 형식 | 뜻 | 근거 |
|---|---|---|---|
| `id` | text | 판의 식별자. (Pack, 입력 자료, 판 번호)를 이은 글자 | [AD-65] |
| `pack_id`, `input_source_id` | text | 어느 입력 자료의 판인가 | [AD-41] |
| `edition_no` | integer | 그 입력 자료 안에서의 판 번호. 1 부터, 빈틈 없이 | [AD-75] [AD-152] |
| `effective_date` | date | 적용일 | [AD-42] |
| `content_hash` | text | 받은 파일의 바이트의 SHA-256 해시 | [AD-155] [AD-158] |
| `content` | bytea | 받은 원본 파일의 내용. 크기 한도는 설치 설정이고 기본값은 20MB 다 | [AD-150] [AD-158] |
| `file_name` | text, 없을 수 있다 | 받은 파일의 이름. 사람이 보기 위한 것이고 처리에 쓰지 않는다 | [AD-193] |
| `received_at` | timestamptz | 받은 때. 밖에서 받아 넘긴 시각 | [AD-31] 과 같은 방식 |

- 유일: (`pack_id`, `input_source_id`, `edition_no`).
- **적용일은 같은 입력 자료의 바로 앞 판보다 하루 이상 뒤여야 한다.** 같거나 앞서면 판을 만들지 않는다. [AD-149]
- **받은 때는 같은 입력 자료의 바로 앞 판보다 이를 수 없다.** 이르면 판을 만들지 않는다. 같은 때는 받는다. [AD-208]
- **내용이 바로 앞 판과 같으면 판을 만들지 않는다.** 적용일이 달라도 그렇다. [AD-155]
- 판과 원본은 한 트랜잭션으로 저장한다. 원본 없이 판만 있는 상태가 없다. [AD-150]
- **판 하나의 투입은 트랜잭션 하나다.** 판, 항목, 개체·관계·속성 값, 알림, 변동 이벤트가 모두 들어가거나 하나도 안 들어간다. 한 번 받아들인 판은 다시 처리하지 않는다. [AD-164]
- 판에는 상태가 없다. 거부된 투입은 판이 아니다. [AD-152]
- 둘째 판부터는 바로 앞 판과 비교한다. 아래 "판 비교"를 본다. [AD-194]
- 내용의 해시는 소문자 16진수 64자다. 열 이름만 있고 행이 없는 파일도 판이 된다 (항목이 없는 판). [AD-189]
- 투입을 확인하는 차례: 크기 한도, 앞 판과 같은 내용인가, 적용일, 받은 때, 파일 읽기와 매핑 실행. 거부의 이유는 처음 걸린 하나다. [AD-191] [AD-208]
- 같은 입력 자료의 투입이 동시에 들어오면 하나씩 차례로 처리한다. [AD-192]

### edition_item — 판의 항목

판 비교는 새 판과 바로 앞 판을 항목의 키로 맞춰 비교한다. [AD-57]

| 열 | 형식 | 뜻 | 근거 |
|---|---|---|---|
| `edition_id` | text | 어느 판의 항목인가 | [AD-57] |
| `item_key` | text | 항목의 키. 매핑이 정한 키 열의 값을 식별자와 같은 규칙으로 이은 글자. 200자까지 | [AD-57] [AD-122] [AD-187] |
| `row_no` | integer | 원본 파일에서의 행 번호 | [link] |
| `content_hash` | text | 매핑이 쓰는 열의 값들의 해시. 값은 읽은 뒤의 표기로 넣는다. 만드는 법은 아래 | [AD-57] [AD-156] [AD-188] |
| `primary_entity_id` | text | 그 행의 주 개체의 `id`. 다음 판에서 그 행이 없어지면 삭제 변동의 주 개체가 된다 | [AD-120] [AD-195] |

- 유일: (`edition_id`, `item_key`).
- **한 판 안에서 항목의 키가 겹치는 행은 모두 건너뛰고 알림으로 남긴다.** 앞 판에 그 키의 항목이 있었다면 앞 판의 것을 그대로 이어 둔다: 이 판의 항목으로 앞 판의 내용 해시와 만든 것을 그대로 옮겨 적고, 끝내지 않고 변동도 만들지 않는다. [AD-157]
- 매핑이 쓰지 않는 열만 바뀐 행은 바뀌지 않은 것이다. [AD-156]
- 건너뛴 행은 항목이 되지 않는다. 알림으로만 남는다.
- **항목의 내용 해시를 만드는 법.** [AD-188] 그 행이 적은 것을 한 줄씩 만든다: 개체는 (`E`, 유형, 키), 속성 값은 (`A`, 유형, 키, 속성 이름, 읽은 값, 유효기간의 칸에 적힌 시작일`~`종료일), 관계는 (`R`, 출발의 유형과 키, 도착의 유형과 키, 관계 유형, 적힌 시작일`~`종료일). 한 줄 안의 값은 식별자와 같은 규칙으로 잇는다. 줄을 글자 코드 순으로 늘어놓고 겹치는 줄은 하나로 하여 줄바꿈(LF)으로 이은 UTF-8 바이트의 SHA-256 이다.
  - 유효기간의 칸이 비어 있으면 빈 글자로 둔다. 판의 적용일로 채우지 않는다. 그래야 같은 행이 다음 판에서 바뀐 것으로 잡히지 않는다.
  - Pack 의 식별자와 행 번호는 넣지 않는다. 다른 행과 부딪혀 넣지 못한 값도 그 행이 적은 것이므로 든다.
  - 값 안의 줄바꿈은 역빗금과 n 으로 바꿔 적는다. 값 하나가 여러 줄로 읽히지 않게 한다.

### edition_item_output — 항목이 만든 것

| 열 | 형식 | 뜻 | 근거 |
|---|---|---|---|
| `edition_id`, `item_key` | text | 어느 항목인가 | [AD-151] |
| `kind` | text | `ENTITY`, `RELATION`, `ATTRIBUTE_VALUE` 가운데 하나 | [AD-151] |
| `object_id` | text | 그 개체, 관계, 속성 값의 식별자 (core 의 `id`) | [AD-65] |
| `object_hash` | text | `object_id` 의 UTF-8 바이트의 SHA-256. 식별자가 길 수 있어 유일을 이것으로 지킨다 | [AD-187] |
| `subject` | text | 무엇에 대한 것인가. 개체는 (`E`, 유형, 키), 속성 값은 (`A`, 유형, 키, 속성 이름), 관계는 (`R`, 출발의 유형과 키, 도착의 유형과 키, 관계 유형)를 식별자와 같은 규칙으로 이은 글자 | [AD-195] |
| `fact_hash` | text | 행이 적은 것 한 줄(항목의 내용 해시를 만드는 줄)의 SHA-256. 다음 판의 행이 같은 줄을 적으면 이 기록의 것을 잇는다 | [AD-195] |
| `valid_from`, `valid_to` | date, 없을 수 있다 | 저장된 유효기간. 개체에는 없다. `valid_to` 는 만들 때의 종료일이다 | [AD-195] |
| `value` | text, 없을 수 있다 | 속성 값이면 그 값 (저장한 글자 그대로). 다음 판에서 그 행의 값이 바뀌면 이것이 이전 값이 된다. 개체와 관계에는 없다. `V19` 보다 앞서 들어간 판의 것은 비어 있다: 그 값이 무엇이었는지 link 는 모른다 | [AD-367] |

- 유일: (`edition_id`, `item_key`, `kind`, `object_hash`). 뜻은 "같은 항목이 같은 것을 두 번 적지 않는다"이다. [AD-187]
- **그 행이 이 판에서 만든 것과, 앞 판에서 만들어져 이 판에서도 이어지는 것을 모두 적는다.** 바뀌지 않은 행의 관계는 처음 만든 판의 것이 이어지므로, 그 관계의 식별자가 뒤의 판의 항목에도 적힌다. [AD-151]
- 다음 판에서 그 행이 없어지면 여기 적힌 관계와 속성 값을 새 판의 적용일로 끝낸다 [AD-42] [AD-121]. 같은 것을 다른 행이 여전히 적고 있으면 끝내지 않는다.
- 삭제된 행의 변동 대상은 앞 판의 그 행에 적힌 개체 전부다. 변경된 행은 앞 판과 새 판에 적힌 개체를 합친 것이다. [AD-58]

### 판 비교

둘째 판부터 한다. 새 판의 행이 적은 것과, 바로 앞 판의 항목들이 만든 것(`edition_item_output`)을 대상마다 견준다. 대상은 한 개체의 한 속성, 또는 한 관계(출발, 도착, 관계 유형)다. [AD-195]

- **잇는다.** 행이 적은 줄이 앞 판의 기록과 같으면(`fact_hash`) 그 기록의 것을 그대로 잇는다. 같은지는 적힌 글자로 견준다: 유효기간의 칸을 비워 둔 것과 같은 날짜를 직접 적은 것은 다른 줄이다 [AD-204]. core 에 아무것도 쓰지 않는다. 새 판의 항목에도 같은 식별자가 적힌다. [AD-151]
- **끝낸다.** 앞 판이 넣어 둔 것 가운데 새 판의 어느 행도 적지 않은 것은 새 판의 적용일로 끝낸다 [AD-42] [AD-121]. 다른 행이 여전히 적고 있으면 끝내지 않는다. 종료일이 이미 있는 것(적힌 종료일이 적용일과 같거나 앞)은 그대로 남는다.
- **넣는다.** 앞 판의 기록에 없는 줄은 새로 넣는다. 시작일은 적힌 날짜이고, 없으면 새 판의 적용일이다. 출처는 새 판이다. **둘째 판부터는 시작일이 그 판의 적용일보다 앞설 수 없다.** 더 앞이면 적용일부터 넣고 알린다 (`STARTS_AT_EFFECTIVE_DATE`). 적힌 종료일이 적용일과 같거나 앞이면 넣지 않고 알린다 (`ALREADY_PAST`). 그런 행이 파일에 남아 있는 동안은 판마다 같은 알림이 나온다. [AD-199] [AD-200]
- **끝낼 수 없으면 판을 거부한다** (`CANNOT_END`). 시작일이 적용일과 같거나 뒤인 것 [AD-198], 그리고 적힌 종료일이 적용일보다 뒤인 것 (한 번 넣은 종료일은 바꾸지 않는다 [AD-162]) [AD-202].
- **저장소에 이미 있는 값과 겹치면 그 값만 넣지 않는다.** 새로 넣을 속성 값의 기간이, 저장소에 이미 있는 같은 개체의 같은 속성의 값 가운데 이 입력 자료의 바로 앞 판이 넣은 것이 아닌 것(다른 입력 자료가 넣었거나 앞앞 판에서 끝난 것)과 겹치면 넣지 않고 그 행마다 알린다 (`ATTRIBUTE_CONFLICT`, `OVERLAPS_STORED_VALUE`). 알림의 `detail` 에 넣으려던 값과 기간, 겹치는 값과 그 기간, 그것을 넣은 입력 자료와 판을 적는다. 겹침은 출처를 보지 않는다 [AD-53]. 맞닿는 것은 겹침이 아니다. 값, 기간, 출처가 모두 같은 것(같은 판을 다시 넣은 것)도 겹침이 아니다. 판의 나머지는 받는다. 넣지 못한 값은 그 행이 만든 것으로 적지 않으므로 다음 판이 다시 가린다. 한 판 안에서 서로 부딪힌 값(아래)은 저장소의 값과도 겹치더라도 부딪힘으로만 알린다. link 는 이를 위해 행이 적은 개체들의 값을 core 의 조회(어느 날부터 유효한 값)로 한 번 읽는다. [AD-322] [AD-344]
- **부딪히면 앞 판의 것을 그대로 둔다.** 한 대상에 대해 유효한 것들(이은 것, 새로 넣을 것, 이어 둔 항목이 쥔 것) 가운데 기간이 겹치는 서로 다른 것이 있으면, 새것은 넣지 않고 앞 판의 것은 끝내지 않는다. 그 대상을 적은 행마다 알린다. 앞 판의 것은 앞 판에서 그것을 적었던 행의 항목에 이어 적고, 그런 행이 그 대상을 적은 행 가운데 없으면 적은 행 모두의 항목에 적는다 (다음 판이 다시 가릴 수 있게 누군가의 항목에는 적혀 있어야 한다). [AD-136] [AD-146] [AD-179] [AD-180] [AD-203]
- **건너뛴 행의 항목은 이어 둔다.** 키를 읽을 수 있었던 행이 건너뛰어졌고 앞 판에 그 키의 항목이 있었으면, 앞 판의 내용 해시와 주 개체와 만든 것을 그대로 옮겨 적는다. 행 번호는 새 파일에서 그 키가 처음 나온 행이다. [AD-157] [AD-196]
- 적용하는 차례: 끝낼 관계, 끝낼 속성 값, 개체, 속성 값, 관계. 각각 식별자 순이다. 앞 값을 먼저 끝내야 새 값이 겹치지 않는다. [AD-163]
- **바뀐 항목.** 키가 새 판에만 있으면 추가, 앞 판에만 있으면 삭제다. 두 판에 다 있으면, 그 항목이 만든 것(이어 받은 것 포함)의 모음이 앞 판과 다를 때 변경이다 [AD-201]. 항목의 내용 해시는 판정에 쓰지 않는다. 변동 대상은 추가는 새 판의, 삭제는 앞 판의 그 항목의 개체이고 변경은 둘을 합친 것이다. [AD-58]

- 유일: (`change_event_id`, `seq`). 차례는 개체의 식별자, 속성의 이름의 글자 코드 순이다. 두 값이 모두 비어 있는 행은 없다.
- **기준은 `change_event_changed_item` 의 속성과 같다**: 변경된 행은 앞 판과 새 판에서 그 행이 만든 것(`edition_item_output`)이 다른 속성 값이다. 추가된 행은 넣은 것 전부이고 이전 값이 없다. 삭제된 행은 넣었던 것 전부이고 새 값이 없다. [AD-291] [AD-367]
- 값은 같고 유효기간만 달라진 속성도 들어간다: 이전 값과 새 값이 같다. [AD-291]
- 값이 부딪혀 넣지 않은 속성(AD-146)은 행이 적은 값이 아니라 저장된 값을 기준으로 남는다: 부딪힌 행은 그대로 남은 앞 판의 값을 이어 적으므로 (위 "판 비교"), 그 행이 앞 판에서 그 속성을 적지 않았다면 이전 값이 비어 있고 새 값이 그 남은 값이다. 부딪혔다는 것과 행이 적은 값은 판의 알림에 있다.
- 한 행이 같은 개체의 같은 속성 값을 한쪽에서 둘 이상 만들었으면 (유효기간을 달리 적은 열이 여럿인 매핑), 시작일과 식별자의 차례로 하나씩 짝지어 여러 행으로 남긴다. 짝이 없는 쪽은 비어 있다.
- `change_event.changed_values_recorded` (boolean, 기본 거짓): 바뀐 값을 남긴 변동 이벤트인가. **거짓이면 바뀐 값이 없는 것이 아니라 모르는 것이다**: link 의 공개 API 는 빈 목록이 아니라 없음(null)으로 준다. `V19` 보다 앞서 만들어진 이벤트와, `V19` 보다 앞서 들어간 판과 견줘 이전 값을 알 수 없는 이벤트가 그렇다 (하나라도 모르면 그 이벤트 전체를 모른다고 한다).
- 값은 자료의 값이다. 판 올리기의 응답으로 담당자와 관리자에게 보인다 (D7 5절).

## 6. rules 의 테이블

변경 파일: `V10__rules_impact_and_action.sql` (B-06). 영향 범위의 테이블 셋과 조치의 테이블이다. [AD-225] 조치의 이력(`action_history`)은 아직 변경 파일이 없다 (B-07).

- rules 는 다른 모듈의 테이블을 가리킬 수 없다. 변동 이벤트의 식별자(link)와 개체·관계의 식별자(core)는 값으로 담고 참조 제약을 걸지 않는다. [AD-18]
- **영향 범위와 조치는 트랜잭션 하나로 저장한다.** api 가 core 에서 계산한 영향 범위를 넘기면 rules 가 둘을 함께 저장한다. 함께 저장되거나 함께 안 된다. [AD-154] [AD-209]
- 한 번 저장한 영향 범위는 고치지 않는다. 처리됨이 된 변동 이벤트에는 영향 범위가 하나 있고, 실패한 변동 이벤트에는 없다. 실패한 것을 다시 실행하면 처음부터 다시 계산해 새로 저장한다. [AD-119] [AD-154] [AD-206]
- **평가에 실패한 규칙이 하나라도 있으면 아무것도 저장하지 않는다.** [AD-227] **이미 저장된 변동으로 다시 불리면 아무것도 바꾸지 않는다.** [AD-228]
- **긴 식별자는 해시 열로 키를 삼는다.** 변동 이벤트의 식별자와 개체의 식별자는 길 수 있어 유일 제약에 그대로 넣지 않는다. 그 UTF-8 바이트의 SHA-256 (소문자 16진수 64자)을 `_hash` 열로 두고 키와 참조에 쓴다. 식별자 자신도 열로 함께 둔다. link 의 방법 [AD-187] 과 같다. (구현하면서 정한 것, "결정 필요" 14번)
- `pack_id` 는 `impact_scope` 와 `action` 에 둔다. 영향 대상과 경로의 단계는 영향 범위를 거쳐 Pack 에 속한다. (구현하면서 정한 것)

| `locked_until` | timestamptz, 없을 수 있음 | 이때까지 막는다 | [보드 COM-01] [AD-265] |
| `created_at` | timestamptz | 만든 때. 밖에서 받아 넘긴 시각 | 제안 |

- 기본 키: `login_id`. 아이디의 모양, 해시의 앞머리, 역할의 값, 틀린 횟수가 0 이상인 것을 데이터베이스가 확인한다.
- 다른 테이블은 이 테이블을 가리키지 않는다. 누가 했는지는 아이디를 값으로 담는다 (조치의 이력). [AD-246]
- 틀린 횟수와 막힘은 그 계정의 행을 잠그고 고친다: 함께 온 시도가 횟수를 빠뜨리지 않는다.
- 세션은 데이터베이스에 두지 않는다. 서버의 메모리에 둔다. [AD-266]
- 사용자는 설치할 때 명령으로 만든다 (D7 9절). [AD-268] 사용자 관리 화면은 당김 범위다 (D-12). 비밀번호를 바꾸거나 사용자를 지우거나 막힌 것을 푸는 기능은 아직 없다.
- 구현하면서 정한 것 (맞는지 확인이 필요하다): `created_at` 열, 아이디의 규칙, 막히는 순간 틀린 횟수를 0 으로 되돌리는 것, common 이 core 처럼 JDBC(spring-jdbc)로 직접 접근하는 것 (AD-76 과 같은 방식), common 의 시험이 api 에 있는 스키마 변경 파일을 읽어 실제 PostgreSQL 에서 도는 것.

### audit_log — 감사 기록

누가, 언제, 무엇을 조회하거나 바꿨는지와 그 결과를 남긴다. [common] 스키마 변경 파일 `V13__common_audit_log.sql`. common 의 `AuditLog` 가 쓰고 읽는다. 무엇을 남길지는 api 가 정한다 (D7 2절).

| 열 | 형식 | 뜻 | 근거 |
|---|---|---|---|
| `id` | bigint, 일련번호 | 한 줄의 식별자. 남긴 차례대로 커진다 | [AD-276] |
| `occurred_at` | timestamptz | 언제. 밖에서 받아 넘긴 시각 | [common] |
| `actor` | text, 없을 수 있음 | 누가. 사용자의 아이디. 로그인 전이면 비어 있음. 200자까지 | [common] |
| `action` | text | 무엇을 했는가. 기능의 이름 (API 규격의 `operationId`, 그리고 `logout`, `accessDenied`, 계정 관리 명령의 `createUser`, `unlockUser`, `changeUserPassword`). 100자까지 | [common] [AD-346] |
| `target` | text, 없을 수 있음 | 무엇에 대해. 대상을 가리키는 요청의 항목을 `이름=값; 이름=값` 으로 적는다. 1000자까지 | [common] |
| `as_of` | date, 없을 수 있음 | 조회가 답에 쓴 기준 날짜 | [AD-23] |
| `outcome` | text | `STARTED` 하기 전에 남긴 줄, `SUCCESS` 성공, `DENIED` 거부 (권한 없음, 로그인 실패), `FAILED` 실패 | [common] [AD-273] |
| `http_status` | integer, 없을 수 있음 | 응답의 HTTP 상태. 하기 전의 줄에는 없다 | 제안 |
| `detail` | text, 없을 수 있음 | 그 밖의 내용 (무엇을 했는지, 결과가 무엇인지). 4000자까지 | 제안 |
| `started_id` | bigint, 없을 수 있음 | 결과의 줄이 가리키는 하기 전의 줄 | [AD-273] |

- 조회와 변경이 모두 남는다. [AD-05] 무엇을 남기고 무엇을 남기지 않는지는 [AD-274].
- **요청 하나는 두 줄이다.** 하기 전에 `STARTED` 인 줄을 먼저 남기고, 끝나면 결과의 줄을 남긴다. 결과의 줄은 `started_id` 로 앞의 줄을 가리킨다. 감사 기록은 변경과 같은 트랜잭션에 쓰지 않는다: 남기는 즉시 저장된다. [AD-273]
- 하기 전의 줄을 남기지 못하면 변경을 하지 않고 조회도 답하지 않는다. [AD-05] [AD-275] 결과의 줄을 남기지 못하면 하기 전의 줄만 남는다: 결과의 줄이 없는 `STARTED` 는 "결과를 모르는 시도"다.
- 권한이 없어 거부한 요청과 로그아웃은 한 줄이다 (`started_id` 없음).
- 비밀번호를 남기지 않는다. 개인 식별 값을 필요 이상 넣지 않는다. [common] 요청의 본문 전체, 올린 파일의 이름과 내용, 확정과 보류의 사유를 남기지 않는다.
- 감사 기록은 고치거나 지우지 않는다. 더하기만 한다. 한 줄의 식별자는 일련번호이고 순서는 그 순이다. 보관 기간은 정하지 않았다. [AD-276]
- **데이터베이스가 지킨다.** 변경 파일 `V17__audit_log_append_only.sql` (E-18): 행을 고치거나 지우는 문장과 테이블을 통째로 비우는 문장(`truncate`)을 방아쇠(트리거)가 오류로 막는다. 더하는 것은 된다. 막지 못하는 것: 테이블의 주인이나 데이터베이스의 관리자가 방아쇠를 끄거나 지우는 것. 그것은 데이터베이스의 권한 관리와 설치 구성이 맡는다. [AD-329] [AD-346]
- **계정 관리 명령도 남는다** (사용자 만들기, 막힘 풀기, 비밀번호 바꾸기). 누가는 비어 있고 `detail` 에 `via=command` 를 적는다. `http_status` 는 없다 (D7 9절). [AD-346]
- 사용자 테이블을 가리키지 않는다: 누가는 값으로 담는다.
- 요청에서 온 값이 들어오므로 common 이 저장할 수 있는 글자로 다듬는다: 제어 글자(널 글자, 줄바꿈 등)는 빈칸으로, 짝 없는 대리 문자는 대체 글자로 바꾸고, 한도를 넘으면 자르고 끝에 `…` 를 둔다.
- 구현하면서 정한 것 (맞는지 확인이 필요하다): 열 `http_status`, `detail`, `started_id` 와 길이의 한도, 결과의 값 넷, `started_id` 의 부분 색인. 데이터베이스가 더하기만 하는 것을 강제하지 않던 것은 `V17` 에서 고쳤다 (위). 감사 기록을 보는 API 와 화면은 없다 (`AuditLog` 의 읽는 길은 식별자 뒤의 줄을 차례로 읽는 것 하나다).

## 8. 결정 필요

2026-11-20 의 결정으로 스키마 v0 (SK-03)을 막던 질문 8건은 닫혔다 (AD-65 ~ AD-74). 남은 것은 스키마 v0 밖의 테이블에 대한 것이고, 그 테이블을 만드는 작업 전에 정하면 된다.

1. (닫힘) 방향을 모르는 관계 유형은 오류로 알린다. [AD-123]
2. (닫힘) link 의 테이블에 대한 질문은 정해졌다 (AD-148 ~ AD-160). 남은 것: 알림과 실패의 이유의 코드 목록 (link 의 작업에서 D7 과 함께 정한다). 받은 파일의 이름을 남기는 것과 투입 기록의 목록의 차례는 제안이다.
3. (닫힘) 2번에 합쳤다.
4. (닫힘) 2번에 합쳤다. 규칙 하나가 실패한 변동은 아무것도 저장하지 않고 실패로 돌려준다 [AD-227]. 부르는 쪽이 변동 이벤트를 실패(규칙 실행 단계)로 표시한다. 이유의 코드를 무엇으로 적는지는 api 의 작업에서 D7 과 함께 정한다.
5. (닫힘) 영향 범위는 rules 가 조치와 함께 저장한다 [AD-209]. 테이블은 셋이다 [AD-210]. 조치는 저장된 영향 대상을 가리킨다 [AD-211]. 경로의 단계에는 관계의 내용을 함께 적는다 [AD-212]. 6절에 적었다. 테이블은 V10 으로 만들었다 [AD-225]. 열에서 구현하면서 정한 것은 14번. 영향 범위를 읽는 API 의 모양은 D7 과 함께 정한다.
6. (닫힘) 보류에는 사유를 반드시 적고 확정에는 선택이다. 1,000자까지. [AD-247]
7. (닫힘) **감사 기록과 이력의 식별자.** 조치의 이력 한 줄은 (조치, 차례)로 가리킨다 (6절 action_history). 감사 기록 한 줄은 일련번호로 가리키고, 지우지 않으며, 보관 기간은 설치 대상의 규정을 확인한 뒤 정한다 [AD-276]. 7절 audit_log.
8. (닫힘) **로그인.** 비밀번호 해시 방식 [AD-264], 틀려도 되는 횟수와 막는 시간 [AD-265], 세션을 두는 곳 [AD-266], 처음 관리자를 만드는 방법 [AD-268]. 7절에 적었다.

10. (닫힘, AD-335) **core 의 저장 API 에서 구현하면서 정한 것과 남은 것 (A-13).**
    - **받는 날짜의 범위** (0001-01-01 ~ 9999-12-31). 저장소가 담을 수 있는 범위는 더 넓지만 범위 밖은 저장소의 오류가 된다. 이 범위가 맞는가? 관계의 시점 조회와 영향 범위 계산의 기준 날짜에는 아직 이 확인이 없다 (끝없는 날짜로 물으면 열려 있는 것을 돌려준다).
    - (닫힘) 끝낸 것을 처음 모양으로 다시 저장하는 것은 지금처럼 거부한다. link 는 받아들인 판을 다시 처리하지 않으므로 이 경로를 타지 않는다. [AD-164]
    - **식별자를 이루는 값의 길이.** 속성의 이름이나 개체의 키가 아주 길면(무작위 글자 수천 자) 색인의 한계에 걸려 저장소의 오류가 된다. 길이의 상한을 정해 입력에서 막아야 한다. Pack 의 이름(D6)과 입력의 키에 함께 닿는다.
    - **기록한 때의 정밀도.** 저장소는 마이크로초까지 담는다. 그보다 세밀한 시각을 넣으면 읽을 때 잘려 있다.
    - **끝낸 때는 남지 않는다.** 행에는 처음 기록한 때 하나만 있다. 종료일을 언제 넣었는지는 link 의 판과 항목 기록으로 따라간다.
    - 속성이 아주 많은 개체(수천 개)의 저장과 조회의 시간은 재지 않았다. 측정은 A-07 에서 한다.
11. (닫힘, AD-335) **link 의 투입에서 남은 것 (C-04).** 구현하면서 정한 것은 확정했다 (AD-188 ~ AD-193).
    - 거부한 이유의 코드와 값 (5절 ingest_record). D7 을 쓸 때 확정한다.
    - 내용이 같은지는 파일의 바이트로만 본다. Pack 의 매핑을 고친 뒤 같은 파일을 다시 넣어도 `UNCHANGED` 다 [AD-155]. 판이 있는 입력 자료의 매핑은 바꿀 수 없으므로 [AD-142] 지금은 생기지 않는다. 매핑을 바꿀 수 있게 하는 날에 다시 본다.
    - 입력 자료의 가장 새 판을 읽는 조회를 뒀다 (판 번호가 가장 큰 판. Pack 목록의 API 가 쓴다 [AD-258]).
    - 투입과 조회를 감사 기록에 남기는 일은 api 에서 한다 (아직 없다). 크기 한도는 api 가 설치 설정에서 읽어 넘긴다 (D7 5절).
    - 판 번호를 식별자에 넣는 모양은 9번 그대로 열려 있다. 받은 때는 마이크로초까지 남는다.
    - 재지 않은 것: 원본을 데이터베이스에 담았을 때의 시간과 크기 (20MB 파일로 넣어 보지 않았다), 큰 파일의 투입이 같은 입력 자료의 다음 투입을 얼마나 기다리게 하는가, 새 조회의 실행 계획.
12. (닫힘, AD-322: 겹침은 12월에 고친다. 취소와 종료일 당기기는 1월. 나머지는 AD-335) **판 비교에서 남은 것 (C-05).** 구현하면서 정한 것은 확정했다 (AD-201 ~ AD-204).
    - **알려진 문제 (고치지 않았다).**
      - 지난 기간의 값을 고친 행은 넣지 않고 알리는데 (`ALREADY_PAST`), 그 항목이 만든 것에서 앞 판의 것이 빠지므로 변경으로 잡힌다. 저장된 것은 바뀌지 않는다. 영향 범위가 한 번 더 계산될 뿐이다. [AD-201] 의 "변동이 있으면 저장된 것이 바뀐 것"에서 벗어나는 한 가지 경우다.
      - 한 행이 같은 것을 두 줄로 적는 매핑 (한 행의 두 개체 정의나 두 관계 정의가 같은 대상을 가리키고 적는 법만 다른 경우)은 그 행의 기록에 줄 하나만 남아, 다음 판에서 "앞 판의 것과 부딪힘"으로 잘못 처리될 수 있다. 값은 바뀌지 않고 알림이 나온다.
      - (닫힘, AD-344) 다른 입력 자료가 넣은 같은 속성의 값과 기간이 겹치면 저장 실패(`STORAGE_FAILURE`)로 끝나던 것을 고쳤다: 그 값만 넣지 않고 알린다 (아래 "저장소에 이미 있는 값과 겹치면"). 관계는 출처가 다르면 겹쳐 저장되므로 (3절) 해당하지 않는다.
      - 저장소에 이미 있는 값과 겹쳐 넣지 못한 값에서 남은 것 (C-08, 확인이 필요하다): (가) 변동은 그 행이 실제로 만든 것이 앞 판과 다를 때 생긴다. 넣지 못한 값은 만든 것이 아니므로, 그 행이 새 행이면 추가로 잡히되 "바뀐 것"에 그 속성이 들지 않고, 앞 판에도 있던 행이면 변동이 아니다. 겹치던 값이 끝난 뒤의 판에서 값이 들어가면 그 판에서 그 행이 변경으로 잡히고 "바뀐 것"에 그 속성이 든다. (나) 같은 사실을 두 입력 자료가 적으면 (값과 기간이 같고 출처만 다르다) 뒤에 들어온 쪽은 판마다 같은 알림을 받는다. (다) 내용이 앞 판과 같은 파일은 판이 되지 않으므로 (C-04), 다시 가리려면 내용이 달라진 판이 들어와야 한다. (라) 겹치는지 읽는 것과 넣는 것 사이에, 또는 개체가 많아 여러 번에 나눠 읽는 사이에 다른 입력 자료가 같은 값을 넣으면 여전히 저장 실패로 끝난다 (틀린 값이 들어가지는 않는다: 최종 판정은 저장할 때의 겹침 거부다). api 가 Pack 마다 판 처리를 하나씩 하므로 api 를 거치면 생기지 않는다. (마) 판에 든 속성 값의 개체를 모두 읽는다 (이어지는 행의 개체도). 큰 판에서의 비용과 실행 계획은 재지 않았다.
      - 이미 지난 기간을 적은 행이 파일에 남아 있으면 판마다 같은 알림이 나온다. 뒤늦게 등록하는 행의 과거 시작일은 반영되지 않는다. [AD-200] 의 대가다.
    - **core 에 새 카드가 필요한 것.** 아직 시작하지 않은 것을 취소하는 API [AD-198], 종료일을 당기는 API [AD-202]. 그때까지 그런 판은 거부된다.
    - 변동 이벤트의 식별자는 (판, 항목의 키)를 이은 글자다.
    - 판 비교의 시간은 재지 않았다 (앞 판의 기록을 모두 읽어 메모리에서 견준다).
13. (닫힘, AD-321: 실패한 까닭과 다시 처리를 12월에 넣는다. AD-331. 나머지는 AD-335) **변동 이벤트의 표시에서 구현하면서 정한 것과 남은 것 (C-06).**
    - 표시한 때를 남기지 않는다. 실패한 이유의 코드는 비어 있지 않은 글자면 받는다 (목록은 D7 에서). NUL 글자와 짝이 맞지 않는 대리 문자는 받지 않는다.
    - (닫힘) 받은 때가 앞 판보다 이른 판은 투입할 때 거부한다. [AD-208] 한 입력 자료 안에서는 받은 차례와 판 번호의 차례가 같다.
    - 처리되지 않은 것의 목록은 Pack 하나의 것이다. 여러 Pack 을 한꺼번에 읽는 조회는 없다.
    - 변동 이벤트 하나를 읽거나 표시하는 API 는 식별자만 받고 Pack 으로 거르지 않는다. 요청으로 받은 식별자가 그 요청의 Pack 의 것인지는 api 가 확인해야 한다.
    - 받은 때는 마이크로초로 잘라 저장한다 (반올림하지 않는다). 넣을 때와 견줄 때의 값이 같다.
    - 같은 변동 이벤트를 두 곳에서 동시에 처리하는 것을 막지 않는다. 표시는 한 문장으로 바뀌므로 상태가 어긋나지는 않지만, 두 번 계산될 수 있다. 실패의 표시가 동시에 둘 오면 나중에 저장된 쪽의 단계와 이유가 남는다 (어느 쪽이 나중인지는 정해져 있지 않다). 한 번에 하나만 처리하게 하는 일은 api 의 몫이다.
    - 판의 변동과 항목을 읽는 다른 조회(`EditionRecords` 의 것)는 두 문장을 한 시점으로 묶지 않았다. 판은 한 트랜잭션으로 들어가고 뒤에 바뀌지 않으므로 받아들여진 판을 읽을 때는 어긋나지 않는다.
    - (닫힘) 한 Pack 에서는 투입과 처리를 한 번에 하나만 한다. [AD-235] 영향 범위는 rules 가 저장한다 (5번).
    - **api 가 변동 이벤트를 처리하면서 정한 것 (C-06 의 남은 부분).** 맞는지 확인이 필요하다.
      - **실패한 이유의 코드.** 영향 범위 계산 단계: `UNKNOWN_IMPACT_DIRECTION` (영향 방향을 모르는 관계 유형), `STORAGE_FAILURE`, `IMPACT_REJECTED` (그 밖의 오류). 규칙 실행 단계: `RULE_FAILED` (평가에 실패한 규칙이 있다 [AD-227]), `STORAGE_FAILURE`, `RULES_REJECTED` (그 밖의 오류). 이름은 D7 을 쓸 때 확정한다.
      - **실패한 까닭의 자세한 내용 (어느 규칙이 왜 실패했는가)은 서버의 기록(로그)에만 남는다.** 변동 이벤트에는 단계와 코드만 적힌다. 화면에서 보여 주려면 저장할 곳이 필요하다.
      - 투입이 받아들여지지 않으면 (내용이 같거나 거부) 남아 있는 변동을 다시 시도하지 않는다. 받아들여진 투입 때와, 따로 부르는 "남은 변동 처리"에서 다시 시도한다. 다시 시도는 그때의 자료와 그때의 규칙으로 한다 [AD-154].
      - 잠금은 둘이다: 먼저 프로세스 안에서 기다리고 (기다리는 동안 연결을 쥐지 않는다), 그다음 데이터베이스의 권고 잠금을 트랜잭션의 것으로 잡는다 (그 연결의 트랜잭션이 끝나면 반드시 풀린다). 잠금을 잡은 연결 하나를 쥔 채로 일하므로 연결 풀에는 연결이 둘 이상 있어야 한다. 앱이 여럿이면 기다리는 앱마다 연결 하나를 쥔다. 데이터베이스에 "트랜잭션 안에서 쉬는 연결을 끊는" 설정을 두면 잠금이 도중에 풀릴 수 있다: 두지 않는다.
      - 판의 투입은 반드시 이 서비스로 한다. link 의 투입을 직접 부르면 처리 중인 변동과 섞인다.
      - 처리됨이나 실패의 표시 자체를 하지 못하면 (저장소 오류) 그 변동의 상태는 바뀌지 않고, 결과에 `NOT_RECORDED` 로 담아 나머지를 계속 처리한다. 다음 처리에서 다시 시도된다.
      - 판을 받아들인 뒤 변동의 처리를 시작하지 못하면 (남은 변동의 목록을 읽지 못하는 등) 예외를 던지지 않고 투입의 결과와 함께 그 사실을 돌려준다. 변동은 대기로 남는다. 변동 이벤트의 판이 저장소에 없으면 그 변동을 `EDITION_NOT_FOUND` 로 실패 표시한다. 처리는 겹쳐 부를 수 없다 (처리하는 도중에 다시 부르면 오류).
      - 그 밖의 모든 오류(프로그램의 잘못 포함)도 그 변동의 실패(`IMPACT_REJECTED`, `RULES_REJECTED`)로 표시하고 기록에 까닭을 남긴다. 받아들여진 투입 때마다 다시 시도된다. Pack 을 다시 적재하는 일은 이 잠금을 잡지 않는다: 처리하는 도중에 Pack 을 다시 적재하면 그 호출은 시작할 때 읽은 정의로 끝까지 간다.
      - 받은 때는 잠금을 잡은 뒤에 읽는다. 조치의 저장한 때는 변동마다 읽는다.
      - 변동을 저장한 뒤 표시하기 전에 서버가 멈추면, 다음 처리에서 저장된 것을 돌려받아 표시만 한다 [AD-228].
      - 변동이 아주 많은 판은 호출이 오래 걸린다. 시간은 재지 않았다.
14. (닫힘, AD-335. 최대 깊이의 상한: AD-333) **영향 범위와 조치의 저장에서 구현하면서 정한 것과 남은 것 (B-06).** 맞는지 확인이 필요하다.
    - **해시 열.** 긴 식별자를 키에 그대로 넣지 않고 SHA-256 을 열로 둔다 (6절). 조치의 식별자의 해시는 유일하다 [AD-230].
    - **더한 열.** `applies_to` (대상이 영향 대상인가 변동 대상인가), `target_entity_type`, `pack_id` (`impact_scope` 와 `action` 에만). 조치의 `pack_id` 와 `as_of` 가 영향 범위의 것과 같다는 것은 제약으로 걸지 않았다 (저장하는 코드가 같은 값을 넣는다).
    - (닫힘) 근거 조항은 언제나 행의 주 개체다. [AD-229]
    - **저장한 때와 만든 때**는 넘겨받은 시각 하나다. 마이크로초로 자른다.
    - **기준 날짜 둘은 넘겨받지 않고 판의 적용일에서 구한다** (전날, 적용일). 넘겨받은 영향 범위의 경로가 이 두 날짜의 것이 아니면 잘못 부른 것으로 보고 오류로 알린다. 깊이와 경로의 길이가 다르거나, 같은 대상이 두 번 들어 있거나, 깊이가 넘겨받은 최대 깊이보다 크거나, 변동 대상이 영향 대상으로 들어 있어도 같다.
    - **주 개체가 변동 대상에 없거나, 저장소에 없거나, 그 Pack 의 것이 아니면** 잘못 부른 것으로 보고 오류로 알린다. 근거 없는 조치를 만들지 않는다.
    - **변동 이벤트의 식별자와 입력 자료의 식별자에 NUL 이나 짝 없는 대리 문자가 있으면** 잘못 부른 것으로 보고 오류로 알린다. 규칙의 이름이나 문구가 그렇거나 비어 있으면, 또는 같은 번호의 규칙이 둘이면 그 규칙의 실패다 (`INVALID_RULE`). Pack 을 읽을 때 걸러지는 것이라 검증을 거친 정의에서는 생기지 않는다.
    - **기한이 9999-12-31 을 넘으면** 그 규칙의 실패다 (`DUE_DATE_OUT_OF_RANGE`). 변동 전체가 저장되지 않는다 [AD-227].
    - **이미 저장된 변동으로 다시 불리면** 넘겨받은 다른 값(판, 영향 범위, 규칙)을 저장된 것과 견주지 않는다. 저장된 것을 돌려줄 뿐이다 [AD-228]. Pack 만은 견준다: 다른 Pack 의 것으로 저장된 식별자면 잘못 부른 것으로 보고 오류로 알린다.
    - **같은 변동을 두 곳에서 함께 저장하면** 먼저 저장된 것이 남고 뒤의 것은 그것을 돌려받는다. 이것은 READ COMMITTED 에서 성립한다. 부르는 쪽이 더 높은 격리 수준의 트랜잭션 안에서 부르면 뒤의 것은 저장소의 오류가 된다. 부르는 쪽은 그렇게 부르지 않는다.
    - **근거 경로는 대상마다 통째로 저장한다.** 단계의 행 수는 대상들의 깊이의 합이다. 깊이 800 의 사슬 하나(단계 32만 행)를 저장하는 데 4.4초가 걸렸다. 최대 깊이의 상한은 정해져 있지 않다 (Pack 이 적는다).
    - 읽는 조회는 변동 이벤트 하나의 조치와 영향 범위, 그리고 Pack 의 조치 목록이다 (상태와 변동으로 거른다. 기한, 우선순위, 규칙 번호, 대상, 조치의 식별자 순 [AD-243]). 조치 하나를 식별자로 읽는 조회는 없다 (B-07 에서). Pack 의 조치 목록은 `pack_id` 로 찾는데 그 색인이 없다: 측정값이 없어 더하지 않았다. 조치가 아주 많아지면 새 변경 파일로 더한다.
    - 영향 범위의 유형별·깊이별 수는 저장하지 않고 읽을 때 영향 대상에서 센다 (rules).
    - **나눠 읽는 조회** (D-13, [AD-347]): Pack 의 조치 목록과 변동의 영향 대상을 건너뛸 수와 크기로 나눠 읽고, 나누기 전의 전체 수를 함께 준다. 순서는 통째로 읽는 조회와 같다. 영향 범위는 그 쪽의 대상의 단계만 읽고, 전체 수와 유형별·깊이별 수는 영향 범위 전체에서 센다. 개체 하나만 물을 수 있다 (그 개체인 영향 대상만). 전체 수와 그 쪽은 한 시점의 것으로 읽는다. 근거 경로가 깊이와 맞지 않는 대상은 그 대상이 든 쪽을 읽을 때 오류로 알린다 (수에는 들어 있다). 이 조회들의 실행 계획과 큰 건너뛸 수의 비용은 재지 않았다: 정렬에 맞는 색인이 없어 쪽마다 걸러진 것 전체를 정렬한다.
    - 조회와 저장을 감사 기록에 남기는 일은 api 에서 한다 (아직 없다).
    - 잰 것 (시험용 컨테이너): 영향 대상 5,000개와 조치 10,000건의 저장 0.6초, 조치 읽기와 영향 범위 읽기 각 0.05초. 질의 넷은 키의 앞 열로 색인을 탄다. 개발 DB 에서는 보지 못했다 (닿지 않는다).
    - 확정된 조치의 상태가 다시 바뀌지 않는다는 것은 rules 의 코드가 지킨다. 데이터베이스는 이력에 확정이 두 번 들어가는 것만 막는다. 조치의 상태 열을 직접 바꾸는 것은 막지 않는다 (6절 action_history, [AD-249]).
    - **확정과 보류에서 구현하면서 정한 것 (B-07).** 아이디는 200자까지, 글자의 수(코드 포인트)로 센다. 확정의 빈 사유는 없는 것으로 남긴다. 눈에 보이는 글자가 없으면 빈 것으로 본다 (공백, 줄바꿈, 끊지 않는 공백, 폭 없는 글자뿐인 값). 앞뒤의 공백은 다듬지 않고 그대로 적는다. NUL 과 짝 없는 대리 문자가 든 아이디와 사유는 거부한다. 한 때는 0001 ~ 9999 년만 받는다. 확정한 때가 조치를 만든 때나 앞의 이력보다 이른지는 보지 않는다 (밖에서 받은 시각을 그대로 적는다. 이력의 차례는 바꾼 차례다). 아이디의 표기를 맞추는 일 (한글의 정규화 등)은 부르는 쪽이 한다. 부르는 쪽은 READ COMMITTED 보다 높은 격리 수준의 트랜잭션 안에서 부르지 않는다 (같은 조치를 함께 바꾸면 거부가 아니라 저장소의 오류가 된다). 조치 하나를 식별자로 읽는 조회와 이력을 읽는 조회를 뒀다. 확정과 보류를 감사 기록에 남기는 일과, 그 아이디가 실제 사용자이고 권한이 있는지 보는 일은 api 에서 한다 (아직 없다). 확정과 보류는 바뀐 조치와 그 이력을 같은 트랜잭션에서 읽어 함께 돌려주고, 거부는 지금의 상태와 마지막 이력을 함께 알린다. 조치 하나와 이력을 한 시점으로 함께 읽는 조회를 뒀다. 틀린 입력은 어느 항목인지(조치의 식별자, 누가, 사유, 언제)를 함께 알린다: api 가 그것으로 오류의 항목을 가린다. 로그인 전에는 api 가 임시 아이디를 넘긴다 [AD-251].
