# D2 아키텍처 결정 기록

상태: 초안 (대표 확정 전) · 담당: 대표

> 이 문서가 기준입니다. 코드와 다르면 문서를 먼저 봅니다.

> **이 초안을 읽는 법.** 저장소에 이미 적혀 있던 결정만 옮겼다. 대괄호가 출처다. 이유가 저장소에 적혀 있으면 옮겼고, 없으면 "(이유 미기재)"로 두었다. 이유를 지어내지 않았다. 대표가 확정하면 상태 줄을 고치고 출처 표시와 이 안내를 지운다.
>
> 출처 표기: [C n절] 맨 위 `CLAUDE.md`, [모듈 이름] 그 모듈의 `CLAUDE.md`, [규칙 이름] `.claude/rules/` 의 파일, [보드] 개발 보드, [코드] 저장소의 빌드·설정 파일.

## 1. 이 문서를 쓰는 법

- 결정 하나가 한 줄이다. 결정마다 이유를 한 줄 적는다. [보드 D2]
- 모듈 경계, API 계약(D7), 데이터 모델(D5), Pack 형식(D6), 규칙 실행 방식(D8)을 바꾸는 일은 혼자 결정하지 않는다. 대표가 결정하면 이 문서에 한 줄이 추가되고, 그 뒤에 해당 문서와 코드를 같은 변경에서 고친다. [C 7절]
- 새 라이브러리나 새 저장소를 들이는 일도 같은 절차를 거친다. [C 2절]
- 이미 적힌 줄은 고치지 않는다. 결정이 바뀌면 새 줄을 추가하고 앞의 줄 번호를 적는다. ("결정 필요" 6번: 이 규칙은 저장소에 근거가 없어 제안으로 적었다)

## 2. 결정 목록

날짜는 저장소에 적혀 있지 않아 비워 두었다 ("결정 필요" 5번).

### 제품의 모양

| 번호 | 결정 | 이유 | 출처 |
|---|---|---|---|
| AD-01 | 업무 영역 지식은 코드가 아니라 Pack(온톨로지, 제약, 매핑, 규칙, 검증 질문)에 둔다. 엔진 코드에 특정 업무 영역의 용어를 넣지 않는다 | 어떤 업무 영역에도 쓰는 제품이다. 처음 보는 Pack 이 들어와도 코드를 고치지 않고 동작해야 한다 | [C 1절] |
| AD-02 | 엔진(pack, core, link, rules)에서 AI 모델을 부르지 않는다 | 같은 입력에는 같은 결과가 나와야 한다. 엔진은 모델 없이 동작한다 | [C 8절] |
| AD-03 | 엔진 코드에서 외부 네트워크를 부르지 않는다 | (이유 미기재) | [C 8절] |
| AD-04 | 결과에는 근거가 붙는다. 영향 대상에는 따라간 경로, 조치에는 근거 조항과 그 판. 근거 없는 결과를 만들지 않는다 | (이유 미기재) | [C 8절] |
| AD-05 | 조회와 변경은 감사 기록에 남긴다. 감사 기록에 실패하면 그 변경 요청도 실패로 처리한다 | 기록 없이 변경이 남으면 안 된다 | [C 8절] [common] |

### 모듈 경계

| 번호 | 결정 | 이유 | 출처 |
|---|---|---|---|

| AD-18 | 다른 모듈은 그 모듈이 공개한 API 로만 쓴다. 남의 모듈 내부 클래스나 테이블을 직접 건드리지 않는다. 저장은 core 의 공개 API 로만 한다 | (이유 미기재) | [C 4절] [pack] [link] |
| AD-19 | common 은 다른 모듈에 의존하지 않고, 업무 개념(관계, 조치, Pack)을 넣지 않는다 | 다른 모든 모듈이 common 에 기대므로 여기의 변경은 전체에 닿는다 | [common] |

## 4. 결정 필요

1. **변동 이벤트가 rules 에 닿는 길.** 개발 보드의 LINK-05 는 "바뀐 항목을 Core 와 Rules 에 넘긴다"고 하지만, 4절 표에서 link 가 의존해도 되는 모듈은 common, pack, core 뿐이다. link 는 rules 를 부를 수 없다. 변동에서 영향 범위 계산, 규칙 실행으로 이어지는 순서를 누가 잡는가? (api 가 차례로 부른다, 이벤트를 저장해 두고 rules 가 읽는다 등) link 지침은 "뒤 단계가 실패하면 이벤트를 실패로 표시하고 다시 실행할 수 있게 둔다"고 하므로 이벤트는 어딘가에 저장돼야 한다.
2. **pack 과 link 의 경계.** 보드의 PACK-03 은 "검증된 Pack 과 입력 파일을 저장소에 넣는다"고 하고, pack 지침은 "입력 파일의 행을 옮기지 않는다(link)"고 한다. SK-04 의 수용 기준은 "제조 안전 Pack 을 적재하면 개체와 관계가 테이블에 들어간다"다. Pack 적재가 넣는 개체와 관계는 어디서 오는가? (Pack 안에 든 초기 자료인가, link 를 거친 입력 파일인가)
3. **스키마 파일의 자리.** 스키마 변경 파일은 `server/api/src/main/resources/db/migration/` 에 있다. 테이블의 주인은 모듈인데(core 의 관계 테이블, common 의 감사 기록, rules 의 조치) 파일은 api 에 모여 있다. 이대로 두는가? SK-03 은 담당 모듈이 core 인데 api 폴더의 파일을 고치게 된다.
4. **이유가 빠진 줄.** 2절에 "(이유 미기재)"가 17줄이다. 한 줄씩 채워야 한다.
5. **결정 날짜.** 줄마다 날짜를 적을 것인가? 적는다면 지금 있는 줄의 날짜는?
6. **줄을 고치는 방식.** 1절의 마지막 규칙(적힌 줄은 고치지 않고 새 줄을 추가)을 쓸 것인가?
7. **PostgreSQL 버전.** 개발 컨테이너가 `postgres:latest` 다. 설치 대상의 버전과 맞추려면 버전을 정해 고정해야 한다. 어느 버전인가?
8. **모듈 주인 자리.** `CLAUDE.md` 4절은 web 의 주인 자리를 D 로, `web/CLAUDE.md` 는 D, I 로 적는다. 어느 쪽이 맞는가?
