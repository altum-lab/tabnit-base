# D1 제품 정의서

상태: 초안 (2026-11-20 결정 반영, 대표 확정 전) · 담당: 대표

> 이 문서가 기준입니다. 코드와 다르면 문서를 먼저 봅니다.

> **이 초안을 읽는 법.** 문장 끝의 대괄호가 출처다. 저장소에 이미 적혀 있던 문장과, 2026-11-20 에 대표가 정한 것(D2 의 AD-29 부터)만 옮겼다. 영어 이름은 제안이다. 아직 정해지지 않은 곳은 채우지 않고 마지막 절 "결정 필요"에 질문으로 남겼다. 대표가 확정하면 상태 줄을 고치고 출처 표시와 이 안내를 지운다.
>
> 출처 표기: [AD-nn] D2 의 결정 번호 (AD-29 부터는 2026-11-20 에 대표가 정한 것), [C n절] 맨 위 `CLAUDE.md`, [모듈 이름] 그 모듈의 `CLAUDE.md`, [보드] `tools/board/index.html` 의 `BASE` (rev 6, 2026-11-19), [README].

## 1. 무엇을 만드는가

Tabnit Base v1.0. 문서나 규정이 바뀌면(변동) 그 영향이 닿는 대상을 관계를 따라 찾고(영향), 규칙으로 해야 할 일을 만들어(조치) 담당자가 확정하게 하는 엔진과 관리 화면이다. [C 1절]

흐름은 여섯 단계다. [C 1절]

1. Pack 적재
2. 새 판 투입 (Link)
3. 판 비교
4. 영향 범위 계산 (Core)
5. 규칙 실행과 조치 생성 (Rules)
6. 화면에서 확정

제품의 성격 세 가지.

- **어떤 업무 영역에도 쓰는 제품이다.** 시연 앱이 아니다. 저장소에는 예시 Pack 두 개(제조 안전, 퇴직연금)와 시험용 Pack 하나(test-mini)가 있고, [AD-49] 엔진은 처음 보는 Pack 이 들어와도 코드를 고치지 않고 동작해야 한다. [C 1절]
- **업무 영역 지식은 Pack 에 둔다.** 코드에 특정 업무 영역의 용어를 넣지 않는다. [C 1절]
- **엔진은 AI 모델 없이 동작한다.** 같은 입력에는 같은 결과와 같은 순서가 나온다. [C 8절]

## 2. 출시와 일정

- 출시: 2026년 12월 30일. [C 1절]
- 배포: 컨테이너 2개(앱, PostgreSQL), 온프레미스 설치. [C 2절]
- 출시 기준(관문 3): 빈 서버에 설치해 일반 시험과 Pack 세 개의 검증 질문을 전부 통과한다. 구성요소 목록을 완성한다. [보드 M6]
- 출시 뒤 2027년 1월 15일까지는 설치 환경에 맞추는 일만 남긴다. [보드 S7, M7]

## 4. 당김 범위와 1월 범위

범위는 필수, 당김, 1월 세 가지다. 기준은 개발 보드다. [AD-48]

- **필수**: 3절. 출시에 반드시 들어간다.
- **당김**: 원래 1월 범위였던 것을 당겨 만든다. 작업 카드가 있고 필수 범위가 밀리지 않을 때만 만든다. 기능 동결(2026-12-24) 때 끝난 것만 출시에 넣는다. 필수 범위가 지연되면 당김부터 뺀다. [AD-48] [보드 R6, S5]
