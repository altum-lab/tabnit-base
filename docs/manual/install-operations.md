# Tabnit Base 설치·운영 매뉴얼 (초안)

> **초안이다.** 2026-11-28 의 main 을 보고 썼다. 카드 E-14 (D9).
> **만든 PC 에서 한 번 따라 해 봤다** (2026-11-28, Apple 의 arm64 Mac, Docker Desktop): 배포 폴더를 만들어 다른 폴더에 복사하고, 설치하고, 사용자를 만들고, 로그인해 Pack 을 적재하고 검증 질문을 돌리고, 새 폴더로 옮겨 다시 띄운 데까지다 (2 ~ 6절). **다른 PC 에서는 따라 해 보지 않았다**: 카드의 수용 기준("다른 PC 에서 그대로 따라 해 본다")은 아직 채우지 않았다. Linux 서버에서도 해 보지 않았다. 백업, 복원, 되돌리기는 해 보지 않았다.
> 명령이 이 문서와 다르면 스크립트가 맞다: `install.sh` 의 머리에 쓰는 법이 적혀 있다.

## 1. 준비

| | |
|---|---|
| 서버 | Linux, amd64 또는 arm64 |
| 필요한 것 | Docker, Docker 의 compose 플러그인. 그 밖에는 없다 |
| 인터넷 | 필요 없다. 이미지는 배포 폴더에 들어 있다 |
| 여는 포트 | 하나 (기본 8443, HTTPS) |
| 디스크 | 데이터는 Docker 의 볼륨 `tabnit_db-data` 에 쌓인다. 크기는 자료에 달렸다 (참고: 개체 10만, 관계 100만에 2.8GB) |

**배포 폴더**는 제품을 만드는 쪽이 `bash tools/package.sh` 로 만든다. 이름은 `tabnit-base-<버전>-linux-<CPU>` 다. 안에 든 것:

| 파일 | 무엇 |
|---|---|
| `images/tabnit-base-app.tar`, `images/postgres.tar` | 컨테이너 이미지 둘 |
| `install.sh`, `compose.yaml` | 설치 스크립트와 설치 구성 |
| `packs/` | 예시 Pack 들 (지어낸 자료). 고객의 Pack 을 여기에 둔다 |
| `VERSION`, `ARCH`, `SHA256SUMS` | 버전, CPU, 파일의 지문 |
| `COMPONENTS.md`, `components.csv`, `bom.json`, `NOTICE.md` | 구성 요소 목록, 라이선스 표, 고지문 |

서버의 CPU 에 맞는 폴더를 받는다. 다른 CPU 용이면 설치 스크립트가 알리며 멈춘다.

## 2. 설치

배포 폴더를 통째로 서버에 복사한 뒤 그 폴더에서 한다.

```
bash install.sh
```

스크립트가 하는 일: 파일이 상하지 않았는지 지문으로 확인하고, 이미지를 읽어 들이고, 데이터베이스의 비밀번호를 무작위로 만들어 `.env` 에 두고, HTTPS 의 인증서를 마련하고, 컨테이너 둘을 띄운다. 다시 불러도 된다: 있는 것은 그대로 쓴다.

**설치할 때 정하는 것** (환경 변수로 준다. 처음 설치할 때 `.env` 에 적히고, 그 뒤로는 `.env` 의 값을 쓴다):

| 변수 | 뜻 | 없으면 |
|---|---|---|
| `TABNIT_HOST` | 사람들이 접속할 이 서버의 이름이나 주소. 자체 서명 인증서에 적힌다 | 이 서버의 이름 |
| `TABNIT_PORT` | 여는 포트 | 8443 |
| `TABNIT_TIME_ZONE` | 조회 시점을 비웠을 때의 "오늘"을 정하는 시간대 | Asia/Seoul |

예: `TABNIT_HOST=tabnit.example.internal TABNIT_PORT=443 bash install.sh`

**HTTPS 의 인증서**

- 받은 인증서가 있으면 **처음 설치하기 전에** 배포 폴더에 `tls/cert.pem` (인증서, 사슬 포함)과 `tls/key.pem` (개인 키, 암호 없음)으로 둔다.
- 없으면 스크립트가 자체 서명 인증서를 만든다. 브라우저가 경고를 띄운다: 시험과 시연에 쓴다.
- 한 번 설치한 뒤에는 앞서 마련한 인증서를 그대로 쓴다 (다시 불러도 "앞서 만든 자체 서명 인증서를 씁니다"라고 나온다). **설치한 뒤에 자체 서명 인증서를 받은 인증서로 바꾸는 절차는 스크립트에 없다.**

설치가 끝나면 `[확인] 떴습니다: https://<이름>:<포트>` 가 나온다. 그 주소로 접속한다.

**`.env` 를 지키는 것이 중요하다.** 데이터베이스의 비밀번호가 여기에만 있다. 이 파일을 지우면 데이터베이스에 붙을 수 없다. 이 사용자만 읽을 수 있게 만들어진다.

## 3. 사용자

사용자는 서버의 명령으로 만든다. 화면에서는 만들지 못한다. 역할은 둘이다: `ADMIN` (관리자), `OFFICER` (담당자).

```
read -rs TABNIT_NEW_USER_PASSWORD; export TABNIT_NEW_USER_PASSWORD
bash install.sh user 아이디 ADMIN
bash install.sh user 아이디 OFFICER
```

- 비밀번호는 12자 이상이다. 환경 변수로 넘긴다: 명령 줄에 값을 적으면 셸의 기록에 남는다.
- 로그인을 다섯 번 틀리면 15분 동안 막힌다. 바로 풀려면 `bash install.sh unlock 아이디`.
- 비밀번호를 바꾸려면 위와 같이 변수에 새 값을 넣고 `bash install.sh password 아이디`.
- 이 명령들은 감사 기록에 남는다.
- **명령의 결과는 앱이 뜨는 기록의 사이에 한 줄로 나온다.** 잘 됐으면 끝 무렵에 "비밀번호를 바꿨습니다: 아이디 …", "로그인 막힘을 풀었습니다: 아이디 …" 같은 줄이 있고 명령이 0 으로 끝난다. 거부되면 (예: 비밀번호가 12자보다 짧다) "비밀번호가 너무 짧습니다. 12자 이상으로 정하세요." 같은 줄이 오류의 긴 기록과 함께 나오고 명령이 0 이 아닌 값으로 끝난다. 그 한국어 줄을 찾아 읽는다.

## 4. Pack 을 넣고 판을 올린다

1. Pack 의 폴더를 배포 폴더의 `packs/` 에 둔다. 폴더의 이름이 Pack 의 이름이다 (영어 소문자, 숫자, 붙임표). 컨테이너는 이 폴더를 읽기만 한다.
2. 관리자로 로그인해 **Pack 정의** 화면의 "Pack 적재"에서 이름을 골라 적재한다. 틀린 Pack 은 적재하지 않고 문제를 모두 알린다. 적재하는 것은 정의뿐이다.
3. 자료는 **변동 감지** 화면에서 판을 올려 넣는다 (사용자취급설명서 2절).
4. 이미 적재된 Pack 을 고쳐 다시 적재할 때는 한 번 확인을 받는다. 바뀐 정의는 그 뒤의 계산부터 쓰인다.

Pack 을 쓰는 법은 `docs/D6-pack-spec.md` 에 있다.

**설치가 맞게 됐는지 확인하는 법**: 예시 Pack 을 적재하고 그 시나리오의 판을 차례로 올린 뒤, Pack 정의 화면의 "검증 질문 돌리기"를 누른다. 모든 질문이 통과하고 "두 번 물은 결과가 같습니다"가 나오면 된다. 시나리오의 판만 올린 저장소에서만 돈다. 시나리오의 판과 그 차례, 적용일은 그 Pack 의 `questions/S-01.yaml` 의 `steps` 에 적혀 있다 (시험용 Pack `test-mini` 는 판 열 개이고 질문은 열일곱이다: 따라 해 봤을 때 "통과 17 / 17"이 나왔다).

## 5. 운영

| 하는 일 | 명령 (배포 폴더에서) |
|---|---|
| 앱의 로그를 본다 | `bash install.sh logs` |
| 내린다 (데이터는 남는다) | `bash install.sh down` |
| 다시 띄운다 | `bash install.sh` |

**감사 기록**은 관리자가 화면(감사 기록)에서 누가, 언제, 무엇으로 걸러 본다. 고치거나 지울 수 없다.

**백업과 복원: 제품의 명령이 없다** (기능 5-3, 카드 E-13 이 아직 없다). 데이터는 Docker 의 볼륨 `tabnit_db-data` 에 있다. 지금은 PostgreSQL 의 도구로 직접 한다. 아래는 그 일반적인 방법이고 **이 제품에서 해 보지 않았다**:

- 백업: 데이터베이스 컨테이너 안에서 `pg_dump` 로 데이터베이스 `tabnit` 을 파일로 낸다.
- 복원: 빈 데이터베이스에 그 파일을 넣는다.
- `.env` 와 (받은 인증서를 썼다면) `tls/` 를 함께 보관한다.

복원한 뒤에 수가 맞는지 확인하는 장치는 제품에 없다.

## 6. 새 버전으로 올린다

1. 새 버전의 배포 폴더를 서버에 복사한다.
2. 앞서 설치한 폴더의 `.env` 를 (받은 인증서를 썼다면 `tls/` 도, 넣어 둔 Pack 이 있으면 `packs/` 의 그 폴더도) 새 폴더로 복사한다.
3. 옛 폴더에서 `bash install.sh down` 으로 내린다.
4. 새 폴더에서 `bash install.sh` 를 부른다. 데이터는 볼륨에 그대로 있고, 데이터베이스의 모양은 앱이 뜨면서 새 버전에 맞게 고친다.

따라 해 본 것은 **같은 버전의 폴더로 옮기는 것**까지다: 옛 폴더를 내리고 `.env` 를 가진 새 폴더에서 띄우니 적재한 Pack, 올린 판, 감사 기록이 그대로 있었고 검증 질문이 다시 통과했다. 버전이 다른 폴더로 올리는 것(데이터베이스의 모양이 바뀌는 경우)은 해 보지 않았다.

**되돌리기: 절차가 없다.** 데이터베이스의 모양을 옛 버전으로 되돌리는 장치가 없다. 올리기 전에 백업을 받아 두고, 되돌려야 하면 옛 버전을 띄운 뒤 그 백업을 복원하는 것이 길이다. **해 보지 않았다.**

## 7. 설치 설정

`.env` 의 값 말고, 앱의 설정으로 바꿀 수 있는 것이다 (지금의 설치 스크립트는 이것을 묻지 않는다: 바꾸려면 설치 구성을 고쳐야 한다).

| 설정 | 뜻 | 기본 |
|---|---|---|
| `tabnit.time-zone` | "오늘"과 화면의 시각을 정하는 시간대 | Asia/Seoul |
| `tabnit.packs-dir` | Pack 을 둔 폴더 | 컨테이너 안의 `/app/packs` |
| `tabnit.login.max-failures`, `tabnit.login.lock-duration` | 로그인을 몇 번 틀리면 얼마 동안 막는가 | 5번, 15분 |
| `tabnit.exports.max-rows` | 한 번에 내보내는 행의 한도 | 100,000 |
| `tabnit.constraints.max-rows` | 제약의 위반을 검사하는 자료의 한도 | 200,000 |
| `tabnit.relation-path.max-length`, `tabnit.relation-path.max-entities` | 경로 찾기의 한도 | 6, 10,000 |
| `spring.servlet.multipart.max-file-size` | 올리는 파일의 크기의 한도 | 20MB |

로그인한 채로 30분 동안 아무것도 하지 않으면 다시 로그인해야 한다.

## 8. 문제가 생겼을 때

| 증상 | 볼 곳 |
|---|---|
| 설치 스크립트가 "[실패]"로 멈춘다 | 그 줄에 무엇을 하면 되는지가 적혀 있다 |
| "파일이 상했습니다" | 배포 폴더를 다시 복사한다 |
| 브라우저가 인증서를 경고한다 | 자체 서명 인증서다. 받은 인증서는 처음 설치하기 전에 `tls/` 에 두어야 한다 (2절). 설치한 뒤에 바꾸는 절차는 없다 |
| 로그인이 막혔다 | `bash install.sh unlock 아이디` |
| Pack 적재의 칸에 "Pack 폴더가 정해져 있지 않습니다" | 배포 폴더의 `packs/` 가 있는지, 서버가 읽을 수 있는지 본다 |
| 판을 올렸는데 "처리되지 않은 변동"에 남는다 | 관리자가 변동 감지 화면에서 "다시 처리"를 누른다. 까닭은 그 줄과 앱의 로그에 있다 |

## 9. 이 초안에서 하지 않은 것

- 다른 PC 에서, 그리고 Linux 서버에서 따라 해 보지 않았다. 만든 PC (Mac) 에서 한 번 해 본 것이다.
- 버전이 다른 폴더로 올리는 것을 해 보지 않았다.
- 백업, 복원, 되돌리기는 해 보지 않은 일반적인 방법이다.
- 받은 인증서로 설치하는 것을 해 보지 않았다 (자체 서명 인증서로 했다).
- GS 자료가 적은 "규칙 팩 설정 가이드"는 `docs/D6-pack-spec.md` 를 가리킬 뿐이다. "오프라인 피드 절차"는 그 기능이 없어 적지 않았다.
- 설치 설정(7절)을 설치할 때 바꾸는 길이 스크립트에 없다.
