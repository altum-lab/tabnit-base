## 1. 계약을 다루는 법

- **계약이 먼저다.** OpenAPI 규격 파일을 먼저 고치고 그에 맞춰 구현한다. 구현을 먼저 하고 규격을 맞추지 않는다. 규격에 없는 API 를 구현하지 않는다. [AD-09] [api] [스킬 contract-first]
- 형식은 OpenAPI 3.1 이다. [AD-09]
- 규격을 바꾸는 일은 설계 변경 절차를 따른다. [C 7절]
- 화면의 호출 코드는 규격에서 만든다(`npm run gen:api`). 손으로 고치지 않는다. [web] [보드 API-01]
- **규격 파일은 `docs/api/openapi.yaml` 이다.** 서버의 구현과 화면의 호출 코드 생성이 모두 이 파일을 읽는다. [AD-77]
- 이 문서는 규칙과 까닭을 적고, 항목 하나하나의 형식은 규격 파일이 정한다. 둘이 다르면 규격 파일을 이 문서에 맞춘다. (제안)

## 2. 모든 API 에 공통인 규칙

### 조회 시점

- 관계를 읽는 모든 API 는 조회 시점을 받는다. 항목 이름은 `asOf` 다. [api] [스킬 contract-first] [AD-50]
- 조회 시점은 사용자가 고르는 값이고, 엔진에는 기준 날짜로 넘어간다. 값은 같다. [AD-50]
- 형식은 `2026-03-01` 모양의 날짜다. 시각은 없다. [D3 4절]
- 요청에 `asOf` 가 없으면 API 층이 한 번만 오늘로 정해 넘긴다. 오늘은 설치 설정의 시간대에서의 날짜이고, 설정에 적지 않으면 Asia/Seoul 이다. 엔진 안에는 기본값이 없다. [AD-23] [AD-40]
- **응답에는 어느 날짜로 답했는지를 `asOf` 로 반드시 담는다.** 요청에 있었든 없었든 담는다. [api] [AD-23]
- 형식이 틀린 `asOf` 는 거부한다. [보드 CORE-03]

### 순서

- 목록의 정렬 기준은 규격에 적는다. [스킬 contract-first]
- api 는 모듈이 준 순서를 바꾸지 않는다. 화면도 서버가 준 순서를 바꾸지 않고, 수를 다시 세지 않는다. [api] [AD-21]

### 근거

- 결과에는 근거로 가는 연결을 담는다. 영향 대상에는 경로, 조치에는 근거 조항과 그 판. [api] [AD-04]

### 식별자

- 개체와 관계는 `id` 문자열 하나로 가리킨다. [AD-65]
- `id` 는 서버가 만든 것을 그대로 돌려보내는 값이다. 화면은 `id` 를 쪼개거나 만들지 않는다. (제안)
- `id` 에는 세로 막대(`|`)를 비롯해 어떤 글자든 들어갈 수 있다. [D5 1절] 그래서 `id` 는 주소의 일부가 아니라 질의 항목(`?entityId=`)으로 받는다. [AD-78]

### 주소

- 모든 API 의 주소는 `/api/v1` 으로 시작한다. 계약을 깨는 변경이 필요하면 `/api/v2` 를 나란히 둔다. [AD-78]

### 로그인, 역할, 감사 기록

- 모든 요청은 로그인과 역할을 확인하고 감사 기록에 남긴다. 확인과 기록은 api 층이 common 을 불러서 한다. [api] [AD-05]
- 역할은 둘이다. 관리자는 Pack 적재까지, 담당자는 조치 확정까지 할 수 있다. [common]
- 권한이 없는 요청은 거부하고 그 사실도 감사 기록에 남긴다. [common]
- 감사 기록을 남기지 못하면 그 변경 요청도 실패로 처리한다. [AD-05]
- 로그인의 방식(세션, 주소, 응답)은 로그인 작업(E-02)을 시작할 때 정한다 ("결정 필요" 1번).
- **뼈대 단계의 임시 처리**: 로그인(E-02)과 감사 기록(E-03, E-05)이 끝날 때까지 구현은 로그인과 역할을 확인하지 않고 감사 기록도 남기지 않는다. 계약에는 401 과 403 을 그대로 둔다. 이 상태의 API 는 개발 환경에서만 쓴다. [AD-80]

### 오류

- 오류는 공통 오류 형식으로 낸다. 내부 예외 문구나 스택을 그대로 내보내지 않는다. [api]
- 사용자에게 보이는 문구는 한국어로, 무엇을 하면 되는지까지 적는다. [C 8절]
- 입력이 틀렸을 때는 어느 항목인지 알려 준다. [C 8절]
- 공통 오류 형식은 RFC 9457 (`application/problem+json`)에 `code` 와 `field` 를 더한 것이다. [AD-79]

| 항목 | 뜻 | 예 |
|---|---|---|
| `type` | 오류 종류의 주소. 따로 정하지 않은 오류는 `about:blank` | `about:blank` |
| `title` | 오류 종류의 짧은 이름 | "잘못된 요청" |
| `status` | HTTP 상태 | 400 |
| `detail` | 사용자에게 보이는 문구. 한국어로, 무엇을 하면 되는지까지 | "조회 시점의 형식이 틀렸습니다. 2026-03-01 과 같이 적어 다시 보내세요." |
| `code` | 오류의 종류. 화면이 이것으로 가른다. 바뀌지 않는 값이다 | `INVALID_AS_OF` |
| `field` | 틀린 항목의 이름. 입력 오류일 때만 | `asOf` |

`type`, `title` 에 넣을 값과 `code` 의 이름은 제안이다.

| 상황 | HTTP 상태 | `code` (제안) |
|---|---|---|
| 입력의 형식이 틀림 | 400 | `INVALID_AS_OF` 처럼 항목마다 |
| 로그인하지 않음 | 401 | `UNAUTHENTICATED` |
| 권한이 없음 | 403 | `FORBIDDEN` |
| 대상이 없음 | 404 | `ENTITY_NOT_FOUND` 처럼 대상마다 |
| 서버 쪽의 문제 | 500 | `INTERNAL` |

- 서버가 기본으로 내는 오류(없는 주소, 허용하지 않는 방식 등)도 이 형식으로 낸다. (제안. 아직 구현하지 않았다. 지금은 `code` 없이 나간다)
- 결과가 없는 것은 오류가 아니다. 빈 목록으로 답한다. 화면은 "영향 없음"처럼 없다는 사실을 말한다. [web]
- 없는 개체를 조회한 것은 결과가 없는 것과 다르다. 오류로 알린다. [보드 CORE-02]

### 값의 표기

- 날짜는 `2026-03-01`, 시각은 `2026-01-01T00:00:00Z` (협정 세계시) 모양으로 적는다. (제안)
- 항목 이름은 `validFrom` 처럼 낙타 표기로 적는다. (제안)
- 종료일이 없는 것은 `validTo` 를 `null` 로 적는다. 항목을 빼지 않는다. (제안)

## 4. 시점 조회

개체 하나의 관계 가운데 조회 시점에 유효한 것을 돌려준다. core 의 `RelationQuery.relationsAsOf` 를 그대로 연다. [보드 CORE-03] [D3 5절]

### 요청

```
GET /api/v1/relations?entityId={개체의 id}&asOf={조회 시점}
```

[AD-78]

| 항목 | 반드시 | 뜻 | 근거 |
|---|---|---|---|
| `entityId` | 예 | 개체의 `id` | [AD-65] |
| `asOf` | 아니오 | 조회 시점. 없으면 오늘 | [AD-23] [AD-40] |

### 응답 (200)

```json
{
  "asOf": "2026-03-01",
  "entityId": "p|T|ga",
  "relations": [
    {
      "id": "p|T|ga|T|na|R|src|1|2026-03-01",
      "relationType": "R",
      "sourceEntityId": "p|T|ga",
      "targetEntityId": "p|T|na",
      "validFrom": "2026-03-01",
      "validTo": "2026-06-01",
      "provenance": { "inputSourceId": "src", "editionNo": 1 },
      "recordedAt": "2026-01-01T00:00:00Z"
    }
  ]
}
```

항목의 이름과 묶음은 제안이다. 값은 지어낸 것이다.

- `asOf`: 답에 쓴 날짜. 반드시 있다. [AD-23]
- `relations`: 조회 시점에 유효한 관계. 개체가 출발 쪽이든 도착 쪽이든 들어 있다. 유효한 것이 없으면 빈 목록이다. [AD-29] [D3 5절]
- **순서**: 관계 유형, 상대 개체의 `id`, 관계의 `id` 차례이고 모두 글자 코드 순이다. [AD-38]
- 관계마다 유효기간, 출처(입력 자료와 판), 기록한 때가 들어 있다. [AD-30] [AD-31]
- 유효기간은 시작일 포함, 종료일 제외다. `validTo` 가 조회 시점과 같은 관계는 들어 있지 않다. [D3 4절]
- 출처가 달라 겹쳐 저장된 관계는 둘 다 들어 있다. [D3 3절] 하나로 합쳐 보여 줄지는 "결정 필요" 4번.
- 상대 개체의 표시 이름은 아직 없다. 속성 값이 구현되면 넣는다. [AD-70] ("결정 필요" 5번)

### 오류

| 상황 | HTTP 상태 | `code` (제안) | 근거 |
|---|---|---|---|
| `entityId` 가 없음 | 400 | `MISSING_ENTITY_ID` | [C 8절] |
| `asOf` 의 형식이 틀림 | 400 | `INVALID_AS_OF` | [보드 CORE-03] |
| 그런 개체가 없음 | 404 | `ENTITY_NOT_FOUND` | [보드 CORE-02] |
| 로그인하지 않음, 권한이 없음 | 401, 403 | 2절. 뼈대 단계에는 확인하지 않는다 | [api] [AD-80] |

### 규격

`docs/api/openapi.yaml` 의 `getRelationsAsOf` 가 이 API 의 규격이다. 항목의 형식은 그 파일을 본다.

## 5. 판 올리기

파일 하나를 입력 자료의 새 판으로 올린다. 받아들인 판은 앞 판과 비교해 바뀐 항목(변동)을 찾고, 이어서 변동마다 영향 범위를 계산해 조치를 만들어 저장한다. 응답이 오면 그 판의 조치가 만들어져 있다. [AD-234] api 의 서비스(`EditionProcessing`)를 그대로 연다. [AD-233] [AD-237]

- 한 Pack 에서는 한 번에 하나만 처리한다. 뒤에 온 요청은 앞의 것이 끝날 때까지 기다린다. [AD-235]
- 담당자와 관리자가 부를 수 있다. [AD-240] 뼈대 단계에는 확인하지 않는다. [AD-80]
- 지난 판의 변동을 다시 보는 조회 API 는 아직 없다. 바뀐 항목은 올린 응답에 담아 준다. [AD-237]

### 요청

```
POST /api/v1/editions
Content-Type: multipart/form-data
```

[AD-238]

| 항목 | 반드시 | 뜻 | 근거 |
|---|---|---|---|
| `packId` | 예 | Pack 의 식별자 | [AD-74] |
| `inputSourceId` | 예 | 입력 자료의 식별자. 그 Pack 의 매핑 가운데 하나 | [AD-41] |
| `effectiveDate` | 예 | 판의 적용일. `2026-03-01` 모양 | [AD-42] |
| `file` | 예 | 올리는 파일. 파일의 이름은 기록에 남긴다 (폴더 부분은 뗀다) | [AD-84] |

- 식별자는 주소에 넣지 않고 폼의 항목으로 받는다. [AD-78]
- 파일 크기의 한도는 설치 설정 `spring.servlet.multipart.max-file-size` 하나로 정한다. 기본은 20MB 다. 요청 전체의 한도(`max-request-size`)는 그보다 조금 크게 둔다. 한도를 넘는 파일은 서버가 본문을 다 읽기 전에 거부한다 (413). 이 경우는 투입 기록에 남지 않는다. (구현하면서 정한 것, "결정 필요" 8번)

### 응답 (200)

```json
{
  "outcome": "ACCEPTED",
  "editionId": "p|src|2",
  "packId": "p",
  "inputSourceId": "src",
  "editionNo": 2,
  "effectiveDate": "2026-03-01",
  "itemCount": 3,
  "changes": [
    {
      "changeEventId": "p\\|src\\|2|ga",
      "itemKey": "ga",
      "kind": "CHANGED",
      "primaryEntityId": "p|T|ga",
      "targetEntityIds": ["p|T|ga"],
      "processing": { "status": "PROCESSED", "failedStage": null, "failureCode": null, "actionCount": 2 }
    }
  ],
  "notices": [],
  "retriedChanges": [],
  "processingNotStarted": false
}
```

항목의 이름과 묶음은 제안이다. 값은 지어낸 것이다.

- `outcome`: `ACCEPTED` 는 새 판을 만들었다. `UNCHANGED` 는 내용이 바로 앞 판과 같아 판을 만들지 않았다 [AD-155]: 이때 `editionId`, `editionNo`, `effectiveDate` 는 그 앞 판의 것이고 `changes` 와 `notices` 는 비어 있다.
- `changes`: 앞 판과 비교해 바뀐 항목. **순서**는 항목의 키의 글자 코드 순이다. 첫 판이면 비어 있다. [AD-148] [AD-122]
- `changes[].processing`: 그 변동을 조치까지 처리한 결과. `PROCESSED` 는 영향 범위와 조치를 저장했다. `FAILED` 는 실패했고 (단계와 이유의 코드가 붙는다) 다음에 받아들여진 판을 올릴 때 다시 시도된다. `PENDING` 은 아직 처리하지 못했다. 변동 하나가 실패해도 나머지는 처리된다. [AD-236]
- `notices`: 투입의 알림 (건너뛴 행 등). 문구가 아니라 종류와 이유의 코드와 값이다. **순서**는 행 번호, 종류, 코드, 내용 순이다. [AD-153]
- `retriedChanges`: 이 요청이 함께 다시 처리한, 앞선 판의 변동. 전에 실패해 남아 있던 것이다. **순서**는 처리한 차례다. [AD-207] [AD-234]
- `processingNotStarted`: 판은 받아들였지만 변동의 처리를 시작하지 못했다. 드문 일이다 (저장소 오류).
- 조치의 내용과 영향 범위는 이 응답에 없다. 조치를 보는 API 에서 준다 (뒤에).

### 오류

## 6. 조치와 그 근거 보기

저장된 조치와, 그 조치를 낳은 변동의 영향 범위를 읽는다. rules 의 `ActionRecords` 를 연다. 화면(web)은 아직 잇지 않았다. [AD-241]

- 조치와 영향 범위는 판을 올린 직후에 그때의 자료로 한 번 계산해 저장한 것이다. 뒤에 자료나 규칙이 바뀌어도 달라지지 않는다. [AD-119] [AD-226]
- 담당자와 관리자가 부를 수 있다. 뼈대 단계에는 확인하지 않는다. [AD-80]
- 개체는 `id` 와 개체 유형으로 준다. 표시 이름은 아직 없다. [AD-244] ("결정 필요" 5번)

### 조치 목록

```
GET /api/v1/actions?packId={Pack 의 식별자}&status={상태}&changeEventId={변동 이벤트의 id}
```

| 항목 | 반드시 | 뜻 | 근거 |
|---|---|---|---|
| `packId` | 예 | Pack 의 식별자 | [AD-74] |
| `status` | 아니오 | `PENDING`, `CONFIRMED`, `ON_HOLD` 가운데 하나. 없으면 가리지 않는다 | [AD-242] [AD-47] |
| `changeEventId` | 아니오 | 이 변동 이벤트에서 나온 조치만. 없으면 가리지 않는다 | [AD-60] |

```json
{
  "packId": "p",
  "status": "PENDING",
  "changeEventId": null,
  "total": 1,
  "actions": [
    {
      "id": "p\\|src\\|2\\|ga|0001|p\\|T\\|na",
      "changeEventId": "p\\|src\\|2|ga",
      "ruleNo": "0001",
      "ruleLabel": "규칙의 이름",
      "actionText": "해야 할 일",
      "priority": 1,
      "dueDate": "2026-03-15",
      "status": "PENDING",
      "appliesTo": "IMPACT_TARGET",
      "target": { "entityId": "p|T|na", "entityType": "T" },
      "basis": {
        "entity": { "entityId": "p|T|ga", "entityType": "T" },
        "inputSourceId": "src",
        "editionNo": 2,
        "effectiveDate": "2026-03-01"
      },
      "createdAt": "2026-03-01T00:00:00Z"
    }
  ]

```

항목의 이름과 묶음은 제안이다. 값은 지어낸 것이다.

- **거른 조치를 한 번에 모두 준다.** 쪽을 나누지 않는다. `total` 은 `actions` 의 수다. 쪽 나누기는 목록이 실제로 커지는 것을 본 뒤에 더한다. [AD-242] ("결정 필요" 6번)
- **순서**: 기한이 이른 것부터. 같으면 우선순위(수가 작은 것부터), 규칙 번호, 대상 개체의 `id`, 조치의 `id` 차례이고 글자는 모두 글자 코드 순이다. 변동 하나로 걸러도 같은 기준이다. [AD-243]
- `basis`: 근거 조항(변동이 생긴 행의 주 개체)과, 그 변동이 나온 입력 자료의 판. 반드시 있다. [AD-04] [AD-229] [AD-98]
- `ruleLabel`, `actionText`, `priority`, `dueDate` 는 조치를 만들 때의 값이다. 뒤에 규칙을 고쳐도 바뀌지 않는다. [AD-226]
- `appliesTo` 가 `IMPACT_TARGET` 인 조치는 그 변동의 영향 범위(아래)에 대상의 근거 경로가 있다. `CHANGE_TARGET` 인 조치는 대상이 바뀐 개체 자신이라 근거 경로가 없다. [AD-102] [AD-211]
- 서로 다른 변동이 같은 대상에 같은 규칙을 걸면 조치가 각각 나온다. 묶어 보여 주는 일은 화면의 몫이다. [AD-60] (D8 "결정 필요" 3번)
- 해당하는 것이 없으면 빈 목록이다. 그 Pack 의 것이 아닌 변동 이벤트로 거른 것도 빈 목록이다 (다른 Pack 의 조치를 주지 않는다).

|---|---|---|
| `packId` 가 없음 | 400 | `MISSING_PACK_ID` |
| `status` 가 셋 가운데 하나가 아님 | 400 | `INVALID_STATUS` |
| `changeEventId` 항목이 있는데 값이 비었거나 쓸 수 없는 글자가 있음 | 400 | `INVALID_CHANGE_EVENT_ID` |
| 그런 Pack 이 없음 | 404 | `PACK_NOT_FOUND` |

```

{

  "asOfEffective": "2026-03-01",

      }
    }
  ]

```

- **두 날짜로 본 것이다.** 판의 적용일 전날(`asOfPrevious`)과 적용일(`asOfEffective`)의 관계로 각각 따라가 합쳤다. 경로마다 어느 날짜의 관계로 닿았는지가 `path.asOf` 에 있다: 전날이면 그 판에서 없어진 관계로 닿은 것이다. [AD-100] [AD-116] 조회 시점 하나로 보는 영향 범위(아직 없다)와는 다른 API 다. (D8 "결정 필요" 6번의 한 부분)
- **순서**: 영향 대상은 깊이, 개체 유형, 개체의 `id` 차례. `countsByType` 은 개체 유형의 글자 코드 순, `countsByDepth` 는 깊이 순. 경로의 단계는 변동 대상 쪽부터. [AD-61] [AD-36]
- `total` 과 두 수의 합계는 영향 대상의 수와 같다. 변동 대상 자신은 세지 않는다. 수는 서버가 센다 (rules). [AD-63] [AD-34] [AD-21]
- 영향 대상마다 근거 경로가 반드시 있다. 단계의 수는 깊이와 같다. [AD-04]
- 단계의 출발과 도착은 그 관계에 적힌 방향이다. 따라간 방향이 아니다. 관계의 내용은 계산할 때의 값이다. [AD-212]
- `truncated`: 최대 깊이에서 멈췄고 그 너머에 아직 찾지 못한 대상이 있다. [AD-62] [AD-117]
- 영향 범위는 변동 이벤트의 `id` 만으로 읽는다. Pack 으로 거르지 않는다 (응답에 `packId` 가 있다). 로그인을 붙일 때 Pack 단위의 접근 범위와 함께 다시 본다.

| 상황 | HTTP 상태 | `code` (제안) |
|---|---|---|
| `changeEventId` 가 없음 | 400 | `MISSING_CHANGE_EVENT_ID` |
| `changeEventId` 에 쓸 수 없는 글자가 있음 | 400 | `INVALID_CHANGE_EVENT_ID` |
| 그 변동 이벤트의 저장된 영향 범위가 없음 (없는 변동, 아직 처리되지 않았거나 처리에 실패한 변동) | 404 | `IMPACT_SCOPE_NOT_FOUND` |

`docs/api/openapi.yaml` 의 `listActions` 와 `getChangeImpactScope` 가 이 API 들의 규격이다.

## 7. 결정 필요

2026-11-20 의 결정으로 SK-07 을 막던 질문은 닫혔다 (AD-77 ~ AD-81). 남은 것은 그 API 를 만드는 작업 전에 정하면 된다.

1. **로그인의 방식.** 세션을 쿠키로 하는가, 토큰으로 하는가? 로그인, 로그아웃, 내 정보의 주소와 응답은? 로그인 작업(E-02)을 시작할 때 정하기로 했다 (2026-11-20). D5 "결정 필요" 8번과 함께 정한다.
2. **역할과 API.** (일부 닫힘) 새 판을 올리는 것은 담당자와 관리자가 모두 한다 [AD-240]. 남은 것: 관리자는 조치를 확정할 수 있는가? common 지침은 "관리자(Pack 적재까지), 담당자(조치 확정까지)"라고만 한다.
3. **Pack 적재의 길.** 설정 화면(Pack 올리기)은 당김 범위다. 필수 범위에서 Pack 은 어떻게 적재하는가? (API 만 두고 화면 없이 부른다, 설치할 때 명령으로 넣는다 등)
4. **겹쳐 저장된 관계의 표시.** 출처가 달라 같은 두 개체, 같은 유형의 관계가 둘 저장된 경우, API 가 둘 다 주고 화면이 출처와 함께 두 줄로 보여 주는가, API 가 하나로 합쳐 주는가? 합치면 유효기간과 출처를 어떻게 합치는지 규칙이 필요하다. (D3 "결정 필요" 3번)
5. **상대 개체의 정보.** 관계 목록에 상대 개체의 `id` 만 주는가, 개체 유형과 키와 표시 이름도 함께 주는가? 함께 주지 않으면 화면이 `id` 를 그대로 보여 주거나 개체마다 다시 물어야 한다.
6. **큰 목록.** 관계가 수천 개인 개체의 목록을 한 번에 다 주는가, 나눠 주는가(쪽 나누기)? 나눠 주면 화면이 수를 다시 세지 않도록 전체 수를 함께 줘야 한다.
7. **뼈대 단계의 임시 처리를 끝내는 때.** 로그인 없이 연 API [AD-80] 를 언제까지 두는가? E-02 와 E-05 가 끝나는 변경에서 함께 닫는 것으로 보았다. 그 전에 개발 환경 밖에 설치하지 않는다는 것을 어디서 막는가?
8. **판 올리기에서 구현하면서 정한 것 (D-05 의 서버 쪽).** 맞는지 확인이 필요하다.
   - 응답의 항목 이름과 묶음 (5절). 오류의 `code` 이름.
   - 파일 크기의 한도는 `spring.servlet.multipart.max-file-size` 하나로 정하고 link 의 투입에도 같은 값을 넘긴다. 서버가 먼저 막으므로 한도를 넘는 파일은 보통 투입 기록에 남지 않는다. link 가 크기로 거부한 것(서버를 거치지 않고 부른 경우)도 413 으로 답한다.
   - 거부한 이유의 문구는 api 가 코드마다 가진다. link 는 코드와 값만 돌려준다. 문구를 둔 것은 link 가 파일 전체를 거부할 때 내는 코드 열둘이다 (`NOT_UTF8`, `NO_HEADER`, `INVALID_HEADER`, `BLANK_COLUMN_NAME`, `INVALID_COLUMN_NAME`, `DUPLICATE_COLUMN_NAME`, `UNCLOSED_QUOTE`, `MISSING_COLUMN`, `EFFECTIVE_DATE_NOT_AFTER_PREVIOUS`, `CANNOT_END`, `UNSUPPORTED_FORMAT`, `RECEIVED_BEFORE_PREVIOUS`). 그 밖의 코드가 오면 코드와 값을 그대로 넣은 문구로 나간다. link 에 거부의 코드가 늘면 여기도 함께 늘려야 한다.
   - **몇 번째 행인지, 어느 열인지를 문구에 넣지 못하는 거부가 있다.** link 는 `UNCLOSED_QUOTE`, `BLANK_COLUMN_NAME`, `DUPLICATE_COLUMN_NAME`, `INVALID_HEADER`, `INVALID_COLUMN_NAME` 의 위치를 예외의 문구에만 담고 이유의 값으로는 돌려주지 않는다. 투입 기록에도 남지 않는다. link 가 이유의 값을 채워야 한다 (link 의 변경).
   - 투입의 알림(`notices`)은 문구 없이 코드와 값으로 준다. 화면이 풀어 보여 줘야 한다.
   - 파일의 이름은 폴더 부분을 떼고 남긴다. 이름이 없으면 남기지 않는다.
   - 요청이 multipart 가 아니거나 주소·방식이 틀린 오류는 프레임워크가 내는 형식 그대로다 (`code` 없음, 2절).
   - 한 요청이 오래 걸릴 수 있다 (변동이 많은 판, 같은 Pack 의 앞 요청을 기다림). 시간 제한은 두지 않았다.
   - `spring.servlet.multipart.max-file-size` 를 0 이하(한도 없음)로 두면 서버가 뜨지 않는다. 판의 원본을 저장소에 담으므로 한도가 반드시 있어야 한다.
   - **로그인을 붙일 때 이 API 에서 챙길 것** (보안 검토의 참고 사항, 2026-11-21): Pack 이나 입력 자료 단위의 접근 범위 (지금은 `packId` 만 알면 올리고 그 Pack 의 변동을 받는다), 권한 확인을 Pack 조회보다 먼저 두기 (404 의 구분으로 Pack 과 입력 자료가 있는지 드러난다), 쿠키로 로그인하면 CSRF 방어 (multipart 요청은 다른 사이트의 폼으로도 보낼 수 있다), 투입 기록에 올린 사람 남기기, 저장된 파일 이름을 화면이나 내려받기에 쓸 때의 처리.
9. **조치와 영향 범위 보기에서 구현하면서 정한 것 (D-06 의 서버 쪽).** 맞는지 확인이 필요하다.
   - 응답의 항목 이름과 묶음 (6절). 오류의 `code` 이름. 주소 (`/api/v1/actions`, `/api/v1/impact-scopes`).
   - 조치를 변동 하나로 걸러도 순서는 Pack 의 목록과 같은 기준(기한이 먼저)이다. 엔진이 한 변동의 조치를 돌려주는 순서 [AD-222] 와는 첫 기준이 다르다.
   - **근거 조항의 개체 유형은 조치에 저장되어 있지 않아 core 의 개체 조회로 읽어 담는다.** 대상의 유형은 조치를 만들 때의 값(저장)이고 근거의 유형은 읽을 때의 값이다. 개체는 지워지지 않고 유형은 식별자의 일부라 값이 달라질 길은 없지만, 그 개체가 저장소에 없으면 그 Pack 의 목록 전체가 서버 쪽의 문제(500)가 된다. 조치에 근거의 유형을 저장하려면 새 스키마 변경 파일이 필요하다 (D5 의 변경).
   - Pack 이 있는지 보려고 Pack 의 정의 전체를 읽는다. 시간은 재지 않았다.
   - 저장된 영향 대상의 경로가 깊이와 맞지 않으면 (저장소가 어긋난 경우) 근거 없이 내보내지 않고 서버 쪽의 문제(500)로 답한다.
   - 영향 범위는 영향 대상과 경로를 한 번에 모두 준다. 영향 대상이 아주 많거나 경로가 깊으면 응답이 크다.
   - Pack 의 조치 목록 조회에는 색인을 더하지 않았다 (측정값이 없다). 조치가 아주 많아지면 느려질 수 있다.
   - 조치 하나를 `id` 로 읽는 API 는 없다 (확정과 보류를 만들 때 함께).
   - **로그인을 붙일 때 이 두 API 에서 챙길 것** (보안 검토의 참고 사항, 2026-11-21): 영향 범위는 변동 이벤트의 `id` 만 알면 어느 Pack 의 것이든 읽힌다. 읽은 영향 범위의 Pack 에 부른 사람의 권한이 있는지 확인하고, 없으면 "없음"과 구별되지 않게 답한다. 조치 목록은 `packId` 에 대한 권한을 확인한다 (없는 Pack 과 권한 없음의 응답을 같게 할지 정한다). 조회도 감사 기록에 남긴다 (부른 사람, Pack, 변동 이벤트). 화면은 오류의 `detail` 을 글자로만 그린다 (요청의 `packId` 가 문구에 들어 있다).
10. **확정과 보류의 API 를 만들 때 챙길 것 (D-07 의 서버 쪽. B-07 의 보안 검토와 사전 검토의 참고 사항, 2026-11-21).**
    - **누가 했는지(`decidedBy`)는 요청에서 받지 않는다.** 로그인한 사람에서만 채운다. 요청에서 받으면 이력의 "누가"를 누구나 지어낼 수 있다. 로그인이 붙기 전에 이 API 를 열면 그 값은 믿을 수 없다: 그 전에 열지 않거나, 열더라도 개발 환경 밖에 두지 않는다 [AD-80].
    - **언제 했는지는 서버의 시계에서 읽어 넘긴다.** 요청에서 받지 않는다.
    - 권한 확인은 확정과 보류뿐 아니라 조치 하나와 이력을 읽는 데에도 건다. 거부의 응답이 조치의 지금 상태를 알려 준다.
    - 조치의 `id` 는 길이의 한도가 없고 줄바꿈과 제어 글자가 들 수 있다. 오류 문구와 로그에 담기 전에 가린다.
    - 확정과 보류는 READ COMMITTED 보다 높은 격리 수준이나 읽기 전용인 트랜잭션 안에서 부르지 않는다 (rules 의 `ActionDecisions`).
    - 확정은 됐는데 응답을 받지 못해 다시 보낸 요청은 거부를 받는다. 자기가 한 것인지는 이력의 마지막 줄로 안다. 이것을 어떻게 답할지 정한다.
    - 쿠키로 로그인하면 CSRF 방어를 건다. 확정과 보류를 감사 기록에 남긴다 [AD-05].
    - 사유와 아이디는 화면에 글자로만 그린다. 표 파일로 내보내는 기능이 생기면 수식으로 읽히는 값(`=`, `+`, `-`, `@` 로 시작)을 막는다.
