# D1 제품 정의서

상태: 초안 (대표 확정 전) · 담당: 대표

> 이 문서가 기준입니다. 코드와 다르면 문서를 먼저 봅니다.

> **이 초안을 읽는 법.** 저장소에 이미 적혀 있던 문장만 옮겼다. 문장 끝의 대괄호가 출처다. 새로 정한 것은 없다. 저장소에 근거가 없거나 서로 어긋나는 곳은 채우지 않고 마지막 절 "결정 필요"에 질문으로 남겼다. 대표가 확정하면 상태 줄을 고치고 출처 표시와 이 안내를 지운다.
>
> 출처 표기: [C n절] 맨 위 `CLAUDE.md`, [모듈 이름] 그 모듈의 `CLAUDE.md`, [보드] `tools/board/index.html` 의 `BASE` (rev 6, 2026-11-19), [README].

## 1. 무엇을 만드는가

Tabnit Base v1.0. 문서나 규정이 바뀌면(변동) 그 영향이 닿는 대상을 관계를 따라 찾고(영향), 규칙으로 해야 할 일을 만들어(조치) 담당자가 확정하게 하는 엔진과 관리 화면이다. [C 1절]

흐름은 여섯 단계다. [C 1절]

1. Pack 적재
2. 새 판 투입 (Link)
3. 판 비교
4. 영향 범위 계산 (Core)
5. 규칙 실행과 조치 생성 (Rules)
6. 화면에서 확정

제품의 성격 세 가지.

- **어떤 업무 영역에도 쓰는 제품이다.** 시연 앱이 아니다. 저장소의 Pack 은 예시이고, 엔진은 처음 보는 Pack 이 들어와도 코드를 고치지 않고 동작해야 한다. [C 1절]
- **업무 영역 지식은 Pack 에 둔다.** 코드에 특정 업무 영역의 용어를 넣지 않는다. [C 1절]
- **엔진은 AI 모델 없이 동작한다.** 같은 입력에는 같은 결과와 같은 순서가 나온다. [C 8절]

## 2. 출시와 일정

- 출시: 2026년 12월 30일. [C 1절]
- 배포: 컨테이너 2개(앱, PostgreSQL), 온프레미스 설치. [C 2절]
- 출시 기준(관문 3): 빈 서버에 설치해 일반 시험과 Pack 세 개의 검증 질문을 전부 통과한다. 구성요소 목록을 완성한다. [보드 M6]
- 출시 뒤 2027년 1월 15일까지는 설치 환경에 맞추는 일만 남긴다. [보드 S7, M7]

## 3. 필수 범위

출시에 반드시 들어가는 것. 기능 번호는 개발 보드의 기능 목록이다. 기능마다의 입력, 출력, 예외 처리는 보드에 있고, 정의는 D3, 형식과 계약은 D5 ~ D8 이 정한다.

| 모듈 | 기능 | 한 줄 설명 [보드] |
|---|---|---|
| pack | PACK-01 Pack 읽기 | Pack 폴더의 파일(온톨로지, 제약, 매핑, 규칙, 검증 질문)을 읽어 내부 모델로 만든다 |
| pack | PACK-02 Pack 검증 | 읽은 Pack 이 서로 맞는지 확인한다. 오류가 하나라도 있으면 적재하지 않는다 |
| pack | PACK-03 Pack 적재 | 검증된 Pack 을 저장소에 넣는다. 도중에 실패하면 전체를 되돌린다 |
| core | CORE-01 관계 저장 | 개체와 관계를 유효기간, 출처와 함께 저장한다 |
| core | CORE-02 관계 기본 조회 | 개체 하나의 관계 목록을 돌려준다 |
| core | CORE-03 시점 조회 | 기준 날짜에 유효한 관계만 돌려준다 |
| core | CORE-04 영향 범위 계산 | 변동이 생긴 대상에서 관계를 따라가며 영향받는 대상을 찾고 근거 경로를 남긴다 |
| core | CORE-05 관계 지도 조회 | 화면의 관계 지도가 그릴 노드와 간선을 돌려준다 |
| link | LINK-01 파일 커넥터 | 표 형식 파일을 읽어 행 단위로 넘긴다 |
| link | LINK-02 매핑 실행 | 행을 매핑 정의에 따라 개체와 관계로 바꿔 적재한다 |
| link | LINK-03 원본 보관과 적재 이력 | 받은 파일 원본과 처리 결과를 남긴다 |
| link | LINK-04 판 비교 | 새 판을 이전 판과 항목 단위로 비교한다 |
| link | LINK-05 변동 이벤트 발행 | 바뀐 항목을 뒤 단계에 넘긴다 |
| rules | RULE-01 규칙 실행 | 영향 범위에 규칙을 적용해 해당하는 규칙을 고른다 |
| rules | RULE-02 조치 생성 | 해당 규칙에서 조치를 만든다 (근거 조항, 기한, 우선순위) |
| rules | RULE-03 확정, 보류, 이력 | 담당자가 조치를 확정하거나 보류하고 그 이력을 남긴다 |
| api, web | API-01 API 계약과 호출 코드 | D7 규격에서 화면이 쓰는 호출 코드를 만든다 |
| web | WEB-01 변동 감지 화면 | 새 판을 올리고 바뀐 항목을 본다 |
| web | WEB-02 영향 범위 화면 | 영향받는 대상의 수와 목록, 근거 경로를 본다 |
| web | WEB-03 조치와 확정 화면 | 조치 목록과 근거를 보고 확정하거나 보류한다 |
| web | WEB-04 관계 지도와 시점 막대 | 관계를 그림으로 보고 시점을 옮겨 본다 |
| web | WEB-05 공통 오류와 로딩 처리 | API 실패와 대기 상태를 모든 화면에서 같은 방식으로 보여 준다 |
| common | COM-01 로그인과 세션 | 로그인하지 않으면 API 와 화면을 쓸 수 없다 |
| common | COM-02 역할 | 관리자와 담당자가 할 수 있는 일을 나눈다 |
| common | COM-03 감사 기록 | 누가 언제 무엇을 조회하고 바꿨는지 남긴다 |
| common | COM-04 설치와 컨테이너 | 빈 서버에 스크립트 하나로 설치한다 |
| verify | VER-01 검증 질문 실행기 | Pack 의 검증 질문을 돌려 정답과 비교한다. 같은 데이터로 두 번 돌려 결과가 같은지 본다 |
| verify | VER-02 화면 전체 흐름 시험 | 새 판 투입부터 확정까지 화면에서 자동으로 돌린다 |

## 5. 용어

같은 것을 다른 이름으로 부르지 않는다. 코드의 이름은 영어, 주석과 문서와 사용자 문구는 한국어다. [C 8절] 영어 이름은 아직 정해지지 않았다 ("결정 필요" 4번).

|---|---|---|
| Pack | 업무 영역 하나의 지식 묶음. 온톨로지, 제약, 매핑, 규칙, 검증 질문으로 이루어진다 | [pack] [C 1절] |

| 검증 질문 | Pack 에 들어 있는 질문과 정답. 그 Pack 에서 엔진이 맞게 동작하는지 본다. 정답은 대표가 정한다 | [verify] |

## 6. 결정 필요

1. **1월 범위와 "당김".** 4절의 항목 대부분이 개발 보드에는 범위 "당김"인 작업으로 올라 있다 (C-11, C-12, B-11, B-12, B-13, A-11, A-12, D-11, D-12, E-13, E-14). 보드의 일정은 S3, S4 에 이것을 만들고 기능 동결 때 "끝난 것만 출시에 넣는다"고 한다. 반면 `CLAUDE.md` 1절은 "1월 범위로 적힌 것은 만들지 않는다"고 하고, 모듈 지침 파일은 이 항목들을 "하지 않는 것"에 둔다. 어느 쪽이 기준인가? 당김이 기준이면 `CLAUDE.md` 1절과 모듈 지침 여섯 곳을 같이 고쳐야 한다. 백업과 복원(E-13), 설치 매뉴얼(E-14)은 모듈 지침에 없다.
2. **Pack 의 수.** `CLAUDE.md` 1절은 "저장소의 Pack 두 개는 예시"라고 하고, 3절과 출시 기준은 세 개(제조 안전, 퇴직연금, 시험용)를 든다. 시험용 Pack 을 예시 Pack 으로 세는가, 따로 부르는가?
3. **"기준 날짜"와 "조회 시점".** core 와 `CLAUDE.md` 8절은 "기준 날짜", api 와 web 지침은 "조회 시점"이라고 쓴다. 같은 것인가? 같다면 어느 이름으로 통일하는가? 다르다면(예: API 가 받는 값과 엔진이 받는 값) 각각의 뜻은?
4. **용어의 영어 이름.** 코드에 쓸 영어 이름이 정해져 있지 않다. 코드에는 지금 `ValidityPeriod` (유효기간) 하나만 있다.
5. **"판"의 단위.** 판은 파일 하나의 판인가, 문서 하나의 판인가, 한 번 투입한 묶음인가? 조치에 붙는 "근거 조항과 그 판"의 판과 입력 파일의 판은 같은 것인가?
6. **"변동"의 대상.** 변동은 입력의 항목(행)에 생기는가, 개체에 생기는가? 영향 범위 계산의 입력은 "변동 대상"인데, 바뀐 항목에서 변동 대상 개체를 정하는 규칙이 저장소에 없다. (D3 "결정 필요"와 같은 질문)
7. **쓰는 사람.** 역할 두 가지(관리자, 담당자) 말고, 누가 어떤 상황에서 쓰는 제품인지에 대한 설명이 저장소에 없다. D1 에 넣을 것인가?
