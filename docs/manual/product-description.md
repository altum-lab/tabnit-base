# Tabnit Base 제품설명서 (초안)

> **초안이다.** 2026-11-28 의 main 을 보고 썼다. 카드 E-24 (D9). 기능이 바뀌면 이 문서도 고친다.
> 판정(충족, 부분, 없음)의 기준은 `docs/D1-product-definition.md` 3절이다: 이 문서가 그것과 다르면 D1 이 맞다.
> 제출하기 전에 대표가 읽고 확정한다. 인증의 범위(아래 2절)는 대표가 정한 것이 아니라 지금의 제품을 적은 것이다.

## 1. 무엇을 하는 제품인가

Tabnit Base 는 **문서나 규정이 바뀌었을 때 그 영향이 어디까지 닿는지를 찾아 해야 할 일을 만들어 주는** 엔진과 관리 화면이다.

일은 네 단계로 흐른다.

| 단계 | 하는 일 | 화면 |
|---|---|---|
| 변동 | 새 판의 파일을 올리면 앞 판과 견줘 바뀐 항목을 찾는다 | 변동 감지 |
| 영향 | 바뀐 항목에서 관계를 따라가 영향을 받는 대상을 찾고, 대상마다 따라간 경로를 남긴다 | 영향 범위 |
| 조치 | 규칙으로 해야 할 일을 만든다. 조치마다 근거가 된 항목과 그 판이 붙는다 | 조치 |
| 확정 | 담당자가 조치를 확정하거나 보류한다. 누가 언제 했는지가 남는다 | 조치 |

특징 셋이다.

- **같은 입력에는 같은 결과가 나온다.** 엔진은 AI 모델을 부르지 않는다. 같은 자료를 두 번 넣으면 목록의 순서까지 같다.
- **모든 것에 시점이 있다.** 관계와 속성 값에는 유효기간이 있고 (시작일은 포함, 종료일은 제외), 모든 조회는 조회 시점을 받는다. 지난 날짜의 상태를 그대로 다시 볼 수 있다.
- **모든 결과에 근거가 붙는다.** 영향 대상에는 따라간 경로가, 조치에는 근거 항목과 그 판이 붙는다. 조회와 변경은 감사 기록에 남는다.

## 2. 제품의 범위

**제품에 들어 있는 것**

- 서버(엔진과 API)와 관리 화면. 컨테이너 둘(앱, PostgreSQL)로 고객의 서버에 설치한다. 인터넷이 없어도 설치하고 쓸 수 있다.
- 설치 스크립트와 계정 관리 명령.
- 검증 질문을 돌리는 실행기 (명령줄, 그리고 관리자의 화면).

**Pack 은 고객마다 바꾸는 설정 데이터다.** 업무 영역의 지식(어떤 유형의 개체가 있는지, 무엇이 무엇과 이어지는지, 파일의 어느 열이 무엇인지, 어떤 변동에 어떤 일을 해야 하는지, 정답을 아는 검증 질문)은 제품의 코드가 아니라 Pack 이라는 파일의 묶음에 있다. 엔진은 처음 보는 Pack 이 들어와도 코드를 고치지 않고 동작한다. 제품과 함께 나가는 Pack 셋(제조 안전, 퇴직연금, 시험용)은 **예시**이고 그 안의 자료는 모두 지어낸 것이다.

**제품에 들어 있지 않은 것**: 고객의 자료, 고객의 Pack 을 만들어 주는 일, 다른 시스템과의 자동 연결(파일을 사람이 올린다).

## 3. 기능

GS 사전상담 자료의 기능 30개에 맞춰 적는다. 판정은 D1 3절의 것이다 (2026-11-28).

| 영역 | 충족 | 부분 | 없음 |
|---|---|---|---|
| 1. 수집과 정의 (7) | 1-7 시점 버전 관리 | 1-1 소스 연결, 1-3 정제·식별자 매핑, 1-4 품질 규칙 검사, 1-5 온톨로지 정의 관리, 1-6 데이터 계약 관리 | 1-2 수집 스케줄·증분 |
| 2. 관계와 조회 (6) | 2-4 시점 조회 | 2-1 관계 지도, 2-2 검색·필터, 2-3 경로 추적, 2-5 관계 API, 2-6 내보내기 | |
| 3. 변동과 영향 (6) | 3-1 변동 이벤트, 3-2 문서 반입·버전 등록, 3-4 버전 비교, 3-5 영향 범위 산출, 3-6 영향 목록·이력 | | 3-3 오프라인 변동 피드 |
| 4. 규칙과 조치 (7) | 4-2 규칙 평가·조치 생성, 4-7 조치 이력·근거 | 4-1 규칙 팩 관리, 4-5 확정·처리 상태 추적 | 4-3 담당자 배정, 4-4 알림, 4-6 규칙 시뮬레이션 |
| 5. 운영 (4) | | 5-1 로그인·사용자·권한, 5-2 감사 로그, 5-4 설정 관리 | 5-3 백업·복원 |

충족 9, 부분 15, 없음 6 이다.

**"부분"이 뜻하는 것** (자세한 까닭은 D1 3절과 `docs/scope-crosscheck.md`):

- **파일로만 받는다.** CSV 와 엑셀 파일을 사람이 화면에서 올린다. 데이터베이스나 다른 시스템의 API 에 직접 붙지 않는다 (1-1).
- **Pack 은 보기만 한다.** 화면에서 Pack 의 정의(유형, 관계, 매핑, 규칙, 제약)를 볼 수 있고, 서버에 둔 Pack 을 골라 적재할 수 있다. 화면에서 고치지는 못한다: 파일을 고쳐 다시 적재한다 (1-5, 4-1, 5-4).
- **역할은 둘이다**: 담당자와 관리자. 사용자는 서버의 명령으로 만든다. 화면에서 사용자를 관리하지 못한다 (5-1).
- **감사 기록은 걸러 볼 수 있다.** 고치지 못하게 데이터베이스가 막지만, 훼손을 찾아내는 해시의 사슬은 없다 (5-2).
- **조치의 상태는 셋이다**: 대기, 보류, 확정. 확정한 조치는 바꾸지 못한다 (4-5).

## 4. 알려진 한계

제품이 하지 않는 것이다. 숨기지 않고 적는다.

- **없는 기능 여섯**: 수집의 스케줄과 증분 (1-2), 오프라인 변동 피드 (3-3), 담당자 배정 (4-3), 알림 (4-4), 규칙 시뮬레이션 (4-6), 백업과 복원 (5-3).
- **백업과 복원의 명령이 없다.** 데이터는 Docker 의 볼륨에 있다. 지금은 PostgreSQL 의 도구로 직접 한다 (설치·운영 매뉴얼 5절).
- **관계 지도는 노드를 200개까지 그린다.** 넘으면 가까운 것부터 200개를 그리고 잘렸다고 알린다. Pack 전체 보기는 넘으면 유형별로 묶는다.
- **영향 범위의 최대 깊이는 Pack 이 정한다.** 그 너머에 대상이 더 있으면 잘렸다고 알린다.
- **저장된 영향 범위와 조치는 판을 올린 그때의 자료로 계산한 것이다.** 뒤에 자료가 바뀌어도 달라지지 않는다. 지금의 자료로 다시 묻는 것은 "개체로 영향 묻기"로 한다 (저장하지 않는다).
- **한 번에 내보내는 행은 100,000 개까지다** (설치 설정으로 바꾼다). 넘으면 일부만 주지 않고 거부한다.
- **파일의 크기는 20MB 까지다** (설치 설정으로 바꾼다).
- **화면은 Chromium 계열 브라우저로만 시험했다.**
- **성능의 값은 개발용 PC 한 대에서 한 번 잰 것이다** (`docs/D5-data-model.md` 1절의 표). 설치할 서버의 값이 아니다.
- **라이선스의 판단은 법률 검토가 아니다** (`COMPONENTS.md`, `NOTICE.md`).

## 5. 동작 환경

| | |
|---|---|
| 서버 | Linux (amd64 또는 arm64). Docker 와 compose 플러그인 |
| 컨테이너 | 앱 하나 (Java 21, Spring Boot), PostgreSQL 18 하나 |
| 접속 | HTTPS. 기본 포트 8443. 인증서가 없으면 자체 서명 인증서를 만든다 |
| 브라우저 | Chromium 계열 |
| 네트워크 | 설치와 실행에 인터넷이 필요 없다. 엔진은 바깥을 부르지 않는다 |

## 7. 이 초안에서 정해지지 않은 것

- 인증의 범위를 어디까지로 할지 (기능 30개 가운데 무엇을 내는지).
- 제품의 버전의 이름. 지금 빌드의 버전은 `0.0.1-SNAPSHOT` 이다.
- GS 자료가 적은 역할 넷(데이터 관리자, 규칙 관리자, 현업 담당자, 시스템 운영자)과 제품의 역할 둘의 차이를 어떻게 할지 (범위 대조 문서의 질문 21).
