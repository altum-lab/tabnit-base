#### B-07 확정, 보류, 이력

- 모듈: rules
- 수용 기준: 조치를 확정하거나 보류하면 누가 언제 했는지 남는다

### 화면 (D)

#### D-05 변동 감지 화면 연결

- 모듈: web, api
- 수용 기준: 새 판을 올리면 바뀐 항목이 화면에 나온다
- 선행 작업: C-05, D-02
- 진행 (2026-11-21): 서버 쪽 가운데 판을 올리는 API 를 만들었다 (D2 AD-237 ~ AD-240, D7 5절, 규격의 `submitEdition`). 응답에 바뀐 항목과 변동마다의 처리 결과를 담는다. 화면의 호출 코드(형식)를 규격에서 다시 만들었다. 수용 기준은 아직 확인되지 않는다: 화면(web)을 잇는 일과, 지난 판의 변동을 다시 보는 조회 API 가 남았다. 선행 작업 D-02 (API 규격에서 호출 코드 생성)는 이 저장소에 호출 코드를 만드는 명령이 이미 있다 (AD-82).
- 진행 (2026-11-21, 둘째): 변동 감지 화면을 만들어 올리는 API 에 붙였다 (D2 AD-255 ~ AD-258). 화면을 오가는 뼈대(React Router), 공통 오류 문구 처리, Pack 과 입력 자료의 목록 API (D7 8절, 규격의 `listPacks`)를 함께 만들었다. 수용 기준은 화면 시험(`web/tests/changes.spec.ts`)으로 확인된다: 판을 올리면 바뀐 항목과 처리 결과와 조치의 수가 화면에 나온다. 모양은 꾸밈 없이 두었다 (시연 앱의 모양은 D-01 에서). 지난 판의 변동을 다시 보는 조회 API 와 화면은 없다.

#### D-06 조치 화면 연결

- 모듈: web, api (조회는 rules)
- 수용 기준: 조치 목록과 근거가 실제 API에서 온다
- 선행 작업: B-06, D-02
- 진행 (2026-11-21): 서버 쪽의 조회 API 둘을 만들었다 (D2 AD-241 ~ AD-244, D7 6절, 규격의 `listActions` 와 `getChangeImpactScope`). rules 에 Pack 의 조치 목록 조회와 영향 범위의 유형별·깊이별 수를 더했다. 화면의 호출 코드(형식)를 규격에서 다시 만들었다. 수용 기준은 아직 확인되지 않는다: 화면(web)을 잇는 일이 남았다.
