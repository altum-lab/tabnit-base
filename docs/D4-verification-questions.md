## 1. 시험은 두 겹이다

| 겹 | 무엇을 보는가 | 어디에 있는가 |
|---|---|---|
| 일반 시험 | 엔진이 일반적으로 맞는가. Pack 과 무관한 지어낸 작은 값으로 본다: 빈 입력, 경계, 큰 입력, 잘못된 입력 | 각 모듈의 시험 코드 |
| 검증 질문 | 그 Pack 에서 엔진이 맞게 동작하는가. Pack 에 든 질문을 돌려 정답과 견준다 | Pack 의 `questions/` |

[C 8절] [verify]

- 둘 다 있어야 한다. 검증 질문만 통과시키는 구현은 끝난 것이 아니다. 예시 Pack 이 통과해도 일반 시험이 없으면 끝난 것이 아니다. [C 8절] [core]
- 기능 하나가 예시 Pack 하나에서만 확인됐다면 다른 Pack 이나 지어낸 작은 자료로 한 번 더 확인한다. [C 8절]
- 검증 질문의 통과 수가 줄면 끝난 것이 아니다. [C 6절]
- 출시 기준은 일반 시험과 Pack 세 개(예시 Pack 둘, 시험용 Pack 하나)의 검증 질문이 전부 통과하는 것이다. [보드 M6] [AD-49]

## 2. 모듈별 일반 시험

모듈마다 반드시 있어야 하는 일반 시험의 최소 목록이다. 작업의 수용 기준에 따라 더 늘어난다. [스킬 tdd-ac] [보드 T-01 ~ T-06]

| 모듈 | 반드시 있어야 하는 경우 | 근거 |
|---|---|---|
| core | 빈 저장소, 관계가 없는 개체, 돌아오는 관계, 한 대상에 이르는 경로 여럿, 깊이 한계, 유효기간 경계(시작일 당일, 종료일 전날, 종료일 당일), 과거·현재·미래 시점 | [core] [보드 T-01] |
| pack | 빈 Pack, 유형 하나뿐인 Pack, 참조가 끊긴 Pack, 같은 Pack 다시 넣기 | [보드 T-04] |
| link | 빈 파일, 첫 판, 바뀐 것 없는 판, 전부 바뀐 판, 행 순서만 바뀐 판, 잘못된 행이 섞인 파일, 같은 파일 두 번 | [link] [보드 T-02] |
| rules | 규칙 없는 Pack, 해당하는 규칙 없음, 한 대상에 규칙 여럿, 같은 우선순위, 평가에 실패하는 규칙, 근거 조항이 빠진 규칙 | [rules] [보드 T-03] |
| api, web | 결과 없음, 권한 없음, 서버 오류, 잘못된 조회 시점 | [보드 T-06] |

모든 모듈에 공통인 것:

- 같은 데이터로 두 번 돌린 결과를 견주는 시험을 하나 둔다. 목록은 순서까지 같아야 한다. [스킬 tdd-ac] [C 6절]
- 시험 자료는 지어낸 작은 값이다. 예시 Pack 의 값이나 정답 숫자를 시험 코드에 베끼지 않는다. [스킬 tdd-ac] [C 8절]
- 데이터베이스가 필요한 시험은 Testcontainers 의 실제 PostgreSQL 로 돌린다. 메모리 데이터베이스로 바꾸지 않는다. [AD-10] [스킬 tdd-ac]
- 시험을 통과시키려고 시험을 지우거나 약하게 고치지 않는다. [C 8절]

## 3. 검증 질문

### 어디에, 어떤 형식으로

- 검증 질문과 정답은 Pack 의 `questions/` 폴더에 둔다. [AD-85] [D6 2절]
- 형식은 YAML 이다. 질문과 정답은 정의가 아니라 시험 자료다. [AD-107]
- 파일은 UTF-8 이다. 파일 하나에 시나리오 하나와 그 시나리오의 질문들을 적는다. 확장자는 `.yaml` 이나 `.yml` 이다. (제안)
- **값은 적힌 글자 그대로 읽는다.** 실행기는 따옴표 없이 적은 `007` 을 수 7 로, `yes` 를 참으로, `2026-01-01` 을 시각으로 바꿔 읽지 않는다. 키와 유형의 이름은 글자다. 비어 있음(`null`)만 그대로 읽는다. 날짜와 수가 필요한 자리(적용일, 단계의 번호 등)는 실행기가 글자에서 푼다.
- **실행기와 엔진 코드에는 정답이 들어가지 않는다.** 질문과 정답은 Pack 안에만 있다. 실행기는 Pack 을 가리지 않는다. [verify]

### 시나리오

질문을 돌리기 전의 자료는 Pack 이 시나리오로 적는다: 어느 예시 입력 파일을, 어떤 적용일로, 어떤 차례로 투입하는가. [AD-110]

```yaml
scenario:
  id: S-01
  title: 시나리오의 이름
  steps:
    - step: 1
      inputSource: source-a          # 입력 자료의 식별자 (매핑 정의에 있는 것)
      file: data/source-a-v1.csv     # Pack 폴더 기준 경로
      effectiveDate: 2026-01-01      # 판의 적용일
    - step: 2
      inputSource: source-a
      file: data/source-a-v2.csv
      effectiveDate: 2026-03-01
    - step: 3
      inputSource: source-a
      file: data/source-a-v3.csv
      effectiveDate: 2026-06-01
```

항목의 이름은 제안이다.

- 실행기는 빈 저장소에 Pack 을 적재하고, 시나리오의 차례대로 판을 투입한 뒤 질문을 돌린다. 언제 돌려도 같은 상태에서 시작한다. [AD-110]
- 입력 파일은 Pack 의 `data/` 에 있는 예시 입력 파일이다. 가상 데이터만 쓴다. [AD-45] [packs]
- 시나리오에는 판이 셋 이상 있어야 한다. 그래야 현재와 과거 두 시점을 물을 수 있다. [AD-112]
- 기록한 때처럼 밖에서 넘기는 시각은 실행기가 고정한 값을 넘긴다. 실행한 날에 따라 결과가 달라지지 않는다. [AD-26] (제안)

### 질문의 종류

흐름의 네 단계를 모두 묻는다. [AD-108]

| 종류 | 묻는 것 | 정답에 적는 것 (제안) |
|---|---|---|
| 시점 조회 | 어떤 날짜에 어떤 개체의 유효한 관계 | 관계의 목록 (관계 유형, 출발 개체, 도착 개체, 시작일, 종료일) |
| 변동 | 시나리오의 어느 단계에서 나온 변동 | 바뀐 항목의 목록 (항목의 키, 추가·변경·삭제) |
| 영향 범위 | 어느 변동의 영향 범위 | 영향 대상의 목록 (개체, 깊이, 근거 경로), 개체 유형별 수, 깊이별 수, 한계에서 멈췄는지 |
| 조치 | 어느 변동에서 만들어진 조치 | 조치의 목록 (근거 규칙, 대상, 근거 조항과 그 판, 근거 경로, 기한, 우선순위) |

```yaml
questions:
  - id: Q-001
    kind: relations-as-of
    title: 질문을 한 줄로
    asOf: 2026-02-01
    entity: { type: TypeA, key: key-1 }
    expect:
      relations:
        - { type: relatesTo, source: { type: TypeA, key: key-1 }, target: { type: TypeB, key: key-9 }, validFrom: 2026-01-01, validTo: null }

  - id: Q-002
    kind: impact
    title: 질문을 한 줄로
    change: { step: 2, itemKey: [key-1] }    # 시나리오의 2단계에서 이 항목에 생긴 변동. 키 열이 여럿이면 차례대로 적는다
    expect:
      targets:
        - entity: { type: TypeB, key: key-9 }
          depth: 1
          path:                                  # 근거 경로: 시작한 변동 대상, 어느 날짜의 관계인지, 거친 관계
            from: { type: TypeA, key: key-1 }
            asOf: 2026-03-01
            relations:
              - { type: relatesTo, source: { type: TypeA, key: key-1 }, target: { type: TypeB, key: key-9 } }
      countsByType: { TypeB: 1 }
      countsByDepth: { 1: 1 }
      truncated: false
```

항목의 이름과 모양은 제안이다. 값은 자리만 잡은 것이다.

- 개체는 유형의 이름과 입력의 키로 가리킨다. Pack 식별자는 그 Pack 이므로 적지 않는다. [D6 5절] (제안)
- **모든 질문은 날짜를 적는다.** 시점 조회는 `asOf` 를, 변동·영향 범위·조치는 시나리오의 단계를 적는다(그 단계의 적용일이 날짜다). "오늘"에 기대는 질문은 없다. [AD-23] (제안)
- 질문에는 겹치지 않는 번호가 있다. 보고는 번호로 한다. [스킬 verify-questions]
- 질문마다 정답의 근거(어느 행, 어느 관계, 어느 날짜 때문인지)를 주석으로 적는다. 정답이 틀렸는지 따질 때 본다. (제안)
- 조치의 정답에는 근거 규칙, 우선순위, 대상, 기한, 근거 조항(개체와 그 판: 입력 자료와 판 번호)을 적는다. (제안)
- 질문은 시나리오의 모든 단계를 투입한 뒤에 돌린다. 다만 **영향 범위와 조치는 판을 투입한 직후에 계산해 저장한 것**을 묻는다. 같은 날의 판이라도 투입하는 차례가 정답에 닿으므로, 시나리오의 `steps` 는 차례를 뜻한다. [AD-119]
- 조치의 근거 조항은 변동이 생긴 행의 주 개체다. [AD-120]
- 항목의 키는 키 열의 값을 차례대로 적은 목록으로 적는다. 실행기가 식별자와 같은 규칙으로 이어 견준다. [AD-122]
- 형식을 실제로 적어 본 것이 `packs/test-mini/questions/S-01.yaml` 이다. 질문 14개와 정답 초안이 있다.

### 서로 다른 시점

- Pack 마다 **현재와 과거 두 시점**, 셋 이상의 시점을 묻는다. 시나리오에 판이 셋 이상 있고, 마지막 판 뒤의 날짜(현재)와 그 앞의 판들 사이의 날짜들(과거)을 묻는다. [verify] [AD-112]
- "현재"는 실행한 날이 아니라 시나리오가 정한 날짜다. [AD-112]
- 같은 개체를 판이 바뀌기 전과 뒤의 날짜로 각각 묻는다. 한 번 바뀐 것이 또 바뀌는 경우를 포함한다. (제안)
- 유효기간의 경계 날짜(시작일 당일, 종료일 전날, 종료일 당일)를 묻는 질문을 포함한다. [core] (검증 질문에도 넣는 것은 제안)

### 질문의 수

- Pack 마다 질문은 10개 이상이다. 네 종류(시점 조회, 변동, 영향 범위, 조치)마다 2개 이상이다. 예시 Pack 둘과 시험용 Pack 모두 같다. [AD-113]
- 실행기는 이 최소 수를 확인해, 모자라면 알린다. [AD-113]

## 4. 정답과 견주기

- **목록은 항목도 순서도 같아야 통과다.** 수와 날짜도 정확히 같아야 한다. [AD-109]
- 정답에 적지 않은 항목은 견주지 않는다 (예: 기록한 때). [AD-109]
- **근거까지 견준다.** 영향 범위의 정답에는 영향 대상마다 근거 경로(시작한 변동 대상과 거친 관계)를, 조치의 정답에는 근거 조항과 그 판을 적고 견준다. 대상은 맞는데 경로가 틀린 것도 실패다. [AD-114] [AD-04]
- 영향 범위와 조치의 질문에서 근거를 빼고 적은 정답은 형식이 틀린 것으로 본다. (제안)
- 견주는 순서는 **제품이 내놓는 순서**다 (HTTP API 의 순서, D7): 시점 조회는 관계 유형·상대 개체·관계 식별자 [AD-38], 변동은 항목의 키 [AD-122], 영향 대상은 깊이·개체 유형·개체 식별자 [AD-61], 조치는 기한·우선순위·규칙 번호·대상 식별자 [AD-243]. 정답을 적는 사람이 이 순서로 적는다. [AD-282] 조치만 엔진이 돌려주는 순서(우선순위가 먼저, AD-222)와 다르다: 엔진의 순서는 rules 의 시험이 본다.
- **정답을 고쳐 통과시키지 않는다.** 정답은 대표가 정한다. 결과가 정답과 다르면 코드를 의심한다. 정답이 틀렸다고 판단되면 근거(조문, 경로, 날짜)를 적어 묻는다. [verify] [packs] [스킬 verify-questions]

## 5. 실행기

검증 질문을 돌리는 것은 verify 모듈이다. [verify] [보드 VER-01]

### 하는 일

1. 저장소의 Pack 을 모두 찾는다. Pack 을 가리지 않는다. [verify]
2. Pack 마다, 시나리오마다: 빈 저장소에 Pack 을 적재하고 시나리오대로 판을 투입한다. [AD-110]
3. 질문을 번호 순으로 돌려 정답과 견준다. [AD-109]
4. 같은 일을 한 번 더 해서 두 번의 결과가 같은지 본다. 다르면 어느 질문이 달랐는지 남긴다. 이것은 결함이다. [verify] [보드 VER-01.1]
5. 질문별 통과·실패 목록을 낸다. 통과 수만 내지 않는다. [verify]

### 지킬 것

- 질문을 건너뛰거나 끄지 않는다. 질문 하나가 오류를 내도 나머지는 계속 돌린다. [verify]
- **아직 만들지 않은 종류의 질문은 실패로 보고한다.** 건너뛰지 않는다. [AD-108]
- 실패한 질문에는 번호, 기대한 값, 실제 값, 날짜를 적는다. [스킬 verify-questions]
- Pack 별 통과 수와 전체 수를 낸다. 직전 main 의 통과 수와의 차이를 본다. [스킬 verify-questions]
- 실행기는 모듈의 내부나 테이블을 직접 보지 않는다. [C 4절]
- **묻는 길**: 모두 HTTP 다. Pack 적재(`POST /api/v1/pack-loads`), 판 투입(`POST /api/v1/editions`), 시점 조회(`GET /api/v1/relations`), 변동(판 투입의 응답에 담긴 바뀐 항목), 영향 범위(`GET /api/v1/impact-scopes`), 조치(`GET /api/v1/actions`). 실행기는 제품을 띄워 관리자로 로그인하고 묻는다. [AD-111] [AD-279] 띄운 제품의 첫 관리자만 common 의 공개 API 로 만든다 (사용자를 만드는 HTTP API 가 없다).
- 어느 길로 물었는지를 보고에 적는다. 지금은 "모두 HTTP"다.
- 명령은 `bash verify/run.sh` 다. [C 3절] 변경마다 도는 구성과 밤 통합이 이 명령을 돌린다. [.github/workflows/ci.yml] [.github/workflows/nightly.yml] 하나라도 실패하거나 두 번의 결과가 다르면 0 이 아닌 값으로 끝난다. 보고는 `verify/build/verify-report.txt` 에도 남는다. [AD-283]
- 정의 파일(`pack.ttl`)이 없는 Pack 폴더는 "아직 내용이 없는 Pack"으로 알리기만 한다. 내용이 있는 Pack 이 질문이 없거나 최소 수에 모자라면 실패다. [AD-281]
- 구현: `verify/` 의 Java 모듈 (서버의 Gradle 빌드에 이어져 있다). [AD-280] 실행기의 일반 시험은 `verify/src/test` 에 있다 (제품을 띄우지 않는다).

## 6. 결정 필요

2026-11-20 의 결정으로 실행기의 첫 작업(SK-06)을 막던 질문 4건은 닫혔다 (AD-111 ~ AD-114). 시험용 Pack 의 질문과 정답 초안을 적어 보면서 나온 질문 넷도 닫혔다 (AD-119 ~ AD-122).

### 시험용 Pack 의 정답을 확정하기 전에

1. **정답의 확정.** `packs/test-mini/questions/S-01.yaml` 의 정답은 초안이다. 규칙대로 손으로 계산했고 근거를 주석으로 적었다. 대표가 확정해야 한다. 앞 초안의 질문 넷(계산하는 때, 근거 조항, 삭제된 행의 속성 값, 항목의 키)은 닫혔고 (AD-119 ~ AD-122), 정답 Q-10 과 Q-14 를 그 결정대로 고쳤다.

### 받아야 하는 것

2. (일부 닫힘) **예시 Pack 의 질문과 정답.** 세 Pack 모두에 질문이 있다. **제조 안전 Pack**: 시나리오 하나(27단계)와 질문 26개를 넣었다 (규칙의 형식을 넓히며 단계 하나와 질문 넷을 더하고, 좁혀진 규칙에 맞춰 정답을 같은 계산으로 다시 만들었다. D2 AD-289) (`packs/manufacturing-safety/questions/S-01.yaml`). **정답은 초안이다**: 자료가 커서 손으로 적지 않고, 예시 입력 파일에서 문서의 규칙을 엔진과 따로 구현한 계산으로 만들었다 (`tools/packs/manufacturing-safety-build.py`) [AD-288]. 대표가 확정해야 한다. 제조 안전 Pack 의 계산은 길이가 같은 근거 경로가 둘인 경우와, 관계 유형과 상대 개체가 같은 관계가 둘인 경우(관계 식별자로 가리는 규칙)를 구현하지 않아, 이 Pack 의 질문은 그 두 경우를 묻지 않는다. 그 규칙은 엔진의 일반 시험과 시험용 Pack 의 질문이 본다. 시연의 검증 질문 가운데 격리(CQ-09)와 가림(CQ-10)은 옮기지 못했다 (엔진에 없다). **퇴직연금 Pack**: 시나리오 하나(25단계)와 질문 30개를 넣었다 (`packs/retirement-pension/questions/S-01.yaml`, D2 AD-294 ~ AD-298). 정답은 초안이고 같은 방법으로 만들었다 (`tools/packs/retirement-pension-build.py`). 이 계산은 길이가 같은 근거 경로를 관계 식별자로 가리는 규칙을 구현했고, 이 Pack 의 영향 범위 질문에는 그런 대상이 여럿 있다. 관계 유형과 상대 개체가 같은 관계가 둘인 경우는 묻지 않는다. 시연의 규칙 가운데 집계와 산술을 쓰는 것은 옮기지 못했다 (D8 "결정 필요" 12번).

### 뒤에 정해도 되는 것

3. **넓게 잡히는 영향 범위.** 참조로만 등장한 개체도 변동 대상으로 하기로 했다 (AD-59). 시험용 Pack 의 Q-11 이 그 결과를 보여 준다: 사업 P-03 하나가 바뀌었는데 P-01 에 이어진 대상까지 영향 범위에 든다. 예시 Pack 에서도 기대와 맞는지 확인한다 (D3 "결정 필요" 2번).
4. **화면 흐름 시험과의 관계.** 화면 전체 흐름 시험(E-08, 새 판 투입부터 확정까지)이 같은 시나리오를 쓰는가? 쓰면 자료와 정답을 한 곳에서 관리할 수 있다.
5. **큰 자료.** 성능 점검용 큰 자료(T-07)는 지어낸 자료를 만들어 내는 것이라 검증 질문과 따로다. 큰 자료에도 정답을 견주는 질문을 두는가?
6. (닫힘) **HTTP 로 옮기는 때.** 실행기는 처음부터 모두 HTTP 로 묻는다 [AD-279]. 보고의 "묻는 길" 줄이 그것을 보여 준다.
7. **실행기를 만들면서 정한 것 (SK-06, E-04).** 맞는지 확인이 필요하다.
   - **직전 main 의 통과 수와의 차이는 내지 않는다** [AD-283]. 보고는 이번 실행의 통과 수만 낸다. 견주려면 앞 실행의 결과를 어딘가에 남겨야 한다.
   - 빈 저장소는 실행마다 새 PostgreSQL 컨테이너다 (`postgres:latest`, 서버 시험과 같다). 시나리오 하나에 제품을 두 번 띄운다.
   - 제품의 시계는 실행기가 고정한 것으로 바꿔 띄운다 (2026-07-01 에서 시작해 읽을 때마다 1초씩 간다). 실행한 날에 결과가 달라지지 않는다. 제품의 다른 설정은 기본값이다.
   - 두 번 돌린 결과는 질문마다 통과 여부와 제품의 답(견주는 모양으로 적은 것)이 같은지로 본다. 기록한 때 같은, 정답에 적지 않는 값은 보지 않는다.
   - 영향 범위의 정답에서 영향 대상과 근거 경로는 반드시 적어야 하고, 유형별 수·깊이별 수·한계에서 멈췄는지는 적었을 때만 견준다. 조치의 정답은 근거 규칙, 우선순위, 대상, 기한, 근거 조항과 그 판을 견준다. 조치의 근거 경로는 견주지 않는다 (조치의 API 가 주지 않는다).
   - 변동의 종류는 정답에 `added`, `changed`, `removed` 로 적고 대소문자를 가리지 않고 견준다.
   - 정답 파일의 값은 모두 글자로 읽으므로, 견줄 때 제품의 답의 수와 참거짓도 글자로 바꿔 견준다 (정답의 `1` 과 제품의 수 1 은 같다). 묶음째로 견준다: 글자로 이어 적은 것은 보고에만 쓴다.
   - 실행기는 시나리오의 단계가 3개 이상인지 본다 (AD-112 의 "판이 셋 이상"을 단계의 수로 본다). 시점이 셋 이상인지, 경계 날짜를 묻는지는 보지 않는다.
   - 질문 파일은 있는데 정의 파일(`pack.ttl`)이 없는 폴더는 "내용이 없는 Pack"으로 넘기지 않고 실패로 낸다.
   - 한 Pack 의 질문 번호는 그 Pack 의 모든 질문 파일에 걸쳐 겹치지 않아야 한다. 최소 수는 Pack 의 모든 파일을 합쳐 센다.
   - 질문을 묻기 전에 막히면 (제품이 뜨지 않음, Pack 적재 실패, 시나리오의 파일이 없음) 그 시나리오의 모든 질문을 실패로 낸다. 판 투입이 거부된 단계를 묻는 질문만 실패다.
   - 실행기가 개체와 항목의 식별자를 만드는 규칙(D5 1절)을 따로 갖고 있다. core 와 link 의 그 규칙은 공개 API 가 아니다.
   - 시험용 Pack 의 정답은 여전히 초안이다 (1번). 이번에 고친 것은 Q-12 의 줄의 차례뿐이다 [AD-282].
