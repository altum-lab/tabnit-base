# 시연 대본

두 예시 Pack 의 시나리오를 화면으로 처음부터 끝까지 보여 주는 차례다 (D-10). 화면 시험 `web/tests/rehearsal.spec.ts` 가 이 차례 그대로 돈다.
아래의 수는 그 시험이 화면에서 읽은 값이다 (시험이 `web/test-results/rehearsal/` 에 남긴 기록에서 옮겼다. 2026-11-27 에 다시 돌려 표 둘의 모든 줄이 같은 것을 봤다, 카드 D-19). 값이 맞는지는 검증 질문과 전수 대조가 따로 본다 (`bash verify/run.sh`).
자료나 규칙을 바꾸면 수가 달라진다. 그때는 시험을 다시 돌려 이 문서를 고친다. 모든 이름과 값은 지어낸 것이다.

## 준비

- 제품을 띄우고 두 Pack 을 적재해 둔다 (관리자). 판은 하나도 올리지 않은 상태에서 시작한다: 같은 시나리오를 두 번 올릴 수는 없다 (적용일이 앞 판보다 늦어야 한다).
- 담당자로 로그인한다. 올릴 파일은 저장소의 `packs/<Pack>/data/` 에 있다.
- 화면은 여섯이다: 변동 감지, 영향 범위, 조치, 관계 지도, Pack 정의, 감사 기록 (감사 기록은 관리자에게만 보인다). 위의 메뉴로 오간다. 리허설 화면 시험이 지나가는 것은 앞의 넷이다: 나머지와 그 뒤에 더한 것(개체 찾기, 경로 찾기, 내보내기, 두 판의 비교 따위)은 아래 "시연 가이드의 시나리오"에 적었다.
- 아래 표의 "입력 자료"는 식별자다. 화면에서는 이름표와 함께 보인다 (예: `safety-sheet` 는 "물질안전자료 목록 (safety-sheet, CSV)").

## 화면에서 하는 일

1. **변동 감지**에서 Pack 과 입력 자료를 고르고, 적용일을 넣고, 파일을 골라 "올리기"를 누른다. "새 판을 받아들였습니다"와 받아들인 항목의 수가 나온다.
2. 첫 판에는 바뀐 항목이 없다 (견줄 앞 판이 없다). 둘째 판부터 "바뀐 항목" 표에 추가, 변경, 삭제와 바뀐 값(이전 값 → 새 값)이 나온다.
3. 바뀐 항목의 "영향 범위 보기"를 누르면 **영향 범위**: 영향 대상의 수, 유형별·깊이별 수, 대상마다 근거 경로.
4. 영향 대상의 "관계 지도"를 누르면 **관계 지도**: 그 개체를 가운데에 둔 그림과 관계 목록. 시점 막대로 날짜를 옮겨 본다.
5. 영향 범위 화면의 "이 변동의 조치 보기"를 누르면 **조치**: 기한, 우선순위, 해야 할 일, 대상, 근거 조항과 그 판.
6. 조치의 "근거와 이력 보기"를 열어 근거 경로를 확인하고 "확정"을 누른다 (보류는 사유를 적는다). 상태가 바뀌고 이력에 누가 했는지 남는다.
   - 근거 경로를 보여 주려면 **대상이 근거 조항과 다른 조치**를 연다 (대상이 작업인원, 공정설비, 연금계좌 같은 것). 바뀐 개체 자신에게 건 조치에는 "근거 경로가 없습니다"가 나온다 (예: 제조 안전 27단계의 실란 자료에서는 목록의 맨 위 조치가 그렇다).

7. 지난 판을 다시 본다: **변동 감지** 화면에서 Pack 을 고르면 아래에 "지난 판"이 최근에 받은 것부터 나온다. 판의 "결과 보기"를 누르면 그때의 바뀐 항목, 바뀐 값, 알림이 목록의 위에 나온다. 다음 파일을 올린 뒤에도, 다른 화면에 다녀와도 볼 수 있다.
8. 제약의 위반을 본다: **변동 감지** 화면에서 Pack 을 고르면 "제약의 위반"이 나온다. 두 예시 Pack 의 자료는 제 제약을 지키므로 "위반이 없습니다"가 조회 시점과 함께 보인다. 조회 시점을 바꿔도 같다 (그 날짜에 값도 관계도 없는 개체는 검사하지 않는다). 위반을 보여 주려면 제약을 어기는 자료를 올려야 한다 (예: 범위를 벗어난 값).

## 시연 가이드의 시나리오 S0 ~ S10

시연 앱의 가이드가 적은 시나리오 열하나를 지금의 제품과 제조 안전 Pack 으로 어디까지 따라갈 수 있는지다 (카드 D-19). 범위 대조 문서(`docs/scope-crosscheck.md`) 2.2 절의 재현표를 0·1단계의 카드가 병합된 뒤의 제품(main, 2026-11-27)으로 다시 적었다. 그 표의 판정(재현 1, 부분 5, 안 됨 5)은 바뀌지 않았다: 따라갈 수 있는 단계가 늘었을 뿐이다.

단계마다 붙인 표시:

- **[리허설]**: 리허설 화면 시험(`web/tests/rehearsal.spec.ts`)이 이 Pack 의 자료로 그 단계를 화면에서 지나간다.
- **[리허설 밖: 시험]**: 리허설은 지나가지 않는다. 적힌 화면 시험이 그 화면을 본다. 그 시험의 자료는 시험용 서버가 넣는 지어낸 자료이고 (제조 안전 Pack 이 아니다), 시연에서 보일 값이 맞는지는 적힌 검증 질문이 본다.
- **[시험 없음]**: 화면에서 할 수는 있으나 그 흐름을 지나가는 화면 시험이 없다.

리허설 화면 시험이 지나가는 길은 하나다: 시나리오의 판을 차례대로 모두 올린다 (단계마다 받아들인 항목과 바뀐 항목의 수를 읽는다) → 마지막으로 조치가 나온 단계의 변동 하나의 영향 범위 → 영향 대상 하나의 관계 지도 → 그 변동의 조치와 근거, 확정 → 조치의 근거에서 그 변동의 영향 범위로 → 지난 판에서 그 판의 결과 다시 보기. 제약의 위반은 화면이 아니라 API 로 묻는다.

### S0 설계도 먼저 (부분)

제품에서 따라가는 길:

1. **Pack 정의**에서 Pack 을 골라 유형, 속성, 관계 유형과 영향 방향, 제약(글 그대로), 입력 자료와 매핑, 규칙을 본다. [리허설 밖: `pack-definition.spec.ts`]
2. **변동 감지**의 "제약의 위반"에서 위반이 없는 것을 조회 시점과 함께 본다. [리허설 밖: `constraint-violations.spec.ts`. 리허설은 같은 것을 API 로만 묻는다]
3. **관계 지도**의 "Pack 전체 보기"에서 이어진 개체와 유형마다의 수를 본다. 이어진 개체가 한도(200) 안이면 개체와 관계가, 넘으면 유형의 묶음이 나온다: 제조 안전 Pack 이 어느 쪽인지는 이 Pack 으로 열어 확인하지 않았다. [리허설 밖: `pack-map.spec.ts`]
4. 관계 지도에서 유형과 관계 유형을 켜고 끈다. [리허설 밖: `relation-map-filter.spec.ts`]

아직 안 되는 단계: 제약을 어긴 입력을 400 으로 거부하는 것 (들어가고 보고된다). 계층 상자와 격리, 인스펙터. 온톨로지를 그림으로 보는 것 (표로 본다). 계약의 호환성 판정. 정의를 화면에서 고치는 것.
